# Red / Blue 稳定原则

本文只保留跨协议仍然成立的原则，不定义下一代的题量、轮次、Profile、Session API、评分
公式或模块配额。

## Red 必须攻击什么

- 这项复杂度是否必要，以及有没有更简单的方案；
- 隐含假设、状态 Owner、边界和不可逆副作用；
- 失败、重试、恢复、幂等、安全、规模、成本和可观测性；
- 替代方案、可替换性、删除条件和反转条件；
- 声称成立所需的代码、测试、Trace、Eval 或外部证据。

Red 只能提出攻击、反例和证据要求，不能把推荐设计偷偷写进问题。

## Blue 必须证明什么

Blue 必须用普通工程语言回答：

1. 为什么需要它？
2. 为什么 Library、Worker、已有 OSS 或外部 Host 不够？
3. 谁拥有状态和决策？
4. 失败时发生什么，如何重试和恢复？
5. 如何授权、观测和测试？
6. 什么证据会让我们把它简化、替换或删除？

“企业级”“最佳实践”“未来扩展”和“看起来更完整”不能替代证明。Blue 的候选修改也不能
自动成为 Canonical；必须经过适用的用户 Gate、ADR 和文档治理。

## 共同边界

- Historical、Current、Target、Hypothesis 和 Future 必须分开；
- Red/Blue 工作材料不拥有正式事实或架构真相；
- 复杂度引入者承担举证责任；
- Interview Ready 不等于 Production Ready；
- 不保存隐藏思维链，只记录可审计的问题、回答、决定、证据和摘要。

## 不在本文定义

`100Q`、`11+1`、Batch/Live Profile、Closure 字段、Session API、评分公式和最终模块或服务
数量都属于未来具体 Protocol（如果未来仍然需要），不属于稳定原则。
