# 交付演进假设

本文件描述可供红蓝队攻击的交付演进模型。除非用户确认或仓库有证据，每个阶段都标为 `[BLUE_PROPOSAL]`，不能当作 Zuno 已经经历的历史。

## 候选阶段

| 阶段 | 目标 | 新增复杂度 |
|---|---|---|
| V0 | 业务研究、用户流程和人工基线 | 明确问题、范围和验收 |
| V1 | 最小 RAG 或单任务 AI 辅助 | 解析、检索、引用和人工确认 |
| V2 | 解决召回、版本、证据和质量问题 | Hybrid、Rerank、评测和可追溯性 |
| V3 | 长任务、Memory 和受控 Agent | Plan、恢复、记忆治理和预算 |
| V4 | 外部工具与安全治理 | Permission、Approval、Idempotency、Reconciliation |
| V5 | 生产治理 | 多租户、容量、灾备、发布和持续评测 |

每个阶段都要记录：用户痛点、为什么上一阶段不够、新增能力、实现复杂度、真实 Owner、验收指标、失败兜底以及 Current / Target / Future 边界。

## 最小落地路径

```text
一个真实场景
  ↓
一个可观察工作流
  ↓
一个人工确认点
  ↓
一组可复现指标
  ↓
再决定是否增加 Agent、Memory、Graph、Tool 或分布式治理
```

红队必须问：如果只剩一周、一个用户和一名开发者，第一版留下什么？如果方案不能回答，就可能存在 `OVERENGINEERING_GAP`。

## 交付过程检查

- 需求如何进入、谁排序、谁拒绝；
- 设计怎样评审，代码怎样验证；
- 数据和模型如何版本化；
- 上线、观测、回滚和人工兜底如何完成；
- 线上反馈如何进入下一个实验，而不是直接变成训练数据。
