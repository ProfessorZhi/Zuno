# Zuno 项目：从智慧司法研究到可验证的法律智能 Agent 平台

Zuno 是南京大学软件学院 LIPLAB 智慧司法研究与工程化背景下的法律智能 Agent 平台，面向天津法院智慧平台相关场景。它所处理的不是单纯的“让模型回答一个法律问题”，而是怎样把研究成果、案件材料、模型与算法、人工判断以及业务系统连接起来，使一项法律工作在持续演进的材料和长时间运行的任务中仍然能够被解释、复核和恢复。

理解 Zuno，需要把两件事分开。第一件事是项目为什么出现、经历过什么、参与者实际做过什么；第二件事是今天经过系统化整理以后，认为这类系统应该怎样设计。前者属于项目历史，后者属于目标架构。二者互相关联，却不能相互替代：今天的架构不能反写过去，历史上的 Pilot 也不能自动证明今天已经具备生产能力。

本章先讲项目本身。当前实现证据由 [`docs/evidence/`](../evidence/README.md) 维护；跨模块的目标设计进入 [`docs/architecture/architecture.md`](../architecture/architecture.md)；某一个责任域内部的状态、失败和恢复，则继续进入 [`docs/modules/`](../modules/README.md)。

## 1. Zuno 是什么

如果把 Zuno 简单介绍成“基于 LangGraph 的 Agent 平台”或“带 GraphRAG 的法律知识库”，会把项目说窄。LangGraph、GraphRAG、Memory、模型网关和向量数据库都只是实现某些能力的工具，它们本身并不能说明这个项目为什么成立。

更准确的描述是：**Zuno 试图把法律智能研究能力、法律材料处理、受控 Agent 执行和可追溯的法律工作成果连接成一个专业工程系统。** 对简单问题，它可以退化为普通的受控检索和生成；对需要多材料、多步骤、人工复核、正式结果和故障恢复的任务，它再逐步引入更强的领域状态和运行机制。

这里有三个事实边界必须先说明。Zuno 是智慧法院相关体系中的一个具体产品，不等于整个智慧法院项目；它与天津法院智慧平台相关场景存在合作背景，但现有材料不足以证明全部 22 家法院都正式部署或日常使用 Zuno。项目历史上进入过法院侧测试和 Pilot Validation（试点验证），但目前没有证据把它描述为正式 Production（生产系统）。产品方向存在、试点发生过、生产资格成立，是三个完全不同的结论。

## 2. 项目缘起：为什么会有这个项目

Zuno 的起点不是“Agent 很流行，所以做一个 Agent 平台”，而是两条已经存在多年的线在工程上相遇。

一条线来自法院侧的法律智能化需求。法律工作面对的材料往往数量多、版本多、关系复杂，专业人员不仅要找到一段文本，还要判断材料是否齐全、不同陈述是否冲突、证据是否足够、哪些法律依据适用，以及最终结论是否值得被正式采用。只要工作从“找到答案”进入“形成可复核结果”，系统就开始承担比搜索和生成更长的责任链。

另一条线来自 LIPLAB 和葛季栋团队长期积累的智慧司法研究。现有公开背景能够支持团队在裁判文书文本抽取、事件抽取与事件对齐、冲突检测、证据链、类案相似度、法条推荐和法律语言模型评测等方向拥有研究积累，也长期参与天津法院信息化和智能司法技术落地。

研究成果与业务系统之间并不存在一条自动完成的道路。一篇论文可以证明某个方法在给定数据集上有效，一个 Demo 可以证明某条链路能够运行，但真正进入长期业务，还需要稳定的输入输出、版本、权限、状态、失败语义、恢复、审计、评测和人机协作。事件抽取模型即使在论文指标上表现很好，也只有在这些工程条件被补齐以后，才可能成为一个可被业务系统长期依赖的能力。

因此，Zuno 的立项价值不主要来自“再做一个聊天机器人”，而来自补上研究成果和长期法律工作之间缺少的工程层。

这个工程层最容易被忽略，因为在 Demo 阶段很多问题并不会立即出现。单次演示里，材料通常已经准备好，模型调用大多成功，流程也不会持续很久；但真实业务会不断引入新版本、新权限、新用户和失败重试。系统一旦需要跨天保存结果、允许不同专业人员复核、在服务重启后继续执行，或者向外部系统产生不可逆动作，原来隐藏的版本和责任问题就会集中出现。Zuno 的架构工作，本质上是在这些问题真正发生之前把它们变成明确、可测试的工程边界。

## 3. 从问答系统到法律工作系统

并不是所有法律问题都需要复杂 Agent。用户如果只是询问“合同第 8 条写了什么”，或“这份判决书中原告提出了什么诉求”，受控检索、引用和一次模型生成往往已经足够。对这种任务强行加入动态规划、多智能体、长期记忆和图检索，只会增加时延、成本和故障点。

困难出现在另一类工作中。设想一个案件事项同时包含起诉状、答辩材料、合同、补充协议、扫描附件、沟通记录和后续补交证据。某份材料可能刚刚换了新版本，一份关键扫描件还没有完成 OCR。系统不能只看“文件已经上传”，而要判断当前任务实际上能使用哪些材料，以及缺失的部分会不会影响结论。

材料可用以后，系统还要从中检索和提取候选事实、事件与证据，比较双方陈述，识别冲突，寻找法条和类案，再形成分析建议。此时机器产生的只是候选结果；如果这些内容要进入正式工作成果，还需要专业规则和人工判断。随后新的证据可能再次进入，已经形成的结论需要被重新检查。任务如果持续几十分钟，还可能遇到权限变化、服务重启、模型失败和外部系统超时。

于是问题发生了变化：系统不再只需要回答“模型说了什么”，还要回答“依据的是哪一版材料”“哪些只是候选”“哪些已经正式成立”“谁批准了什么”“旧结果为什么失效”“崩溃以后从什么事实恢复”“外部动作到底有没有发生”。从这一刻开始，它已经不再只是问答系统，而是一个长期、专业、可审计的法律工作系统。

这种变化也解释了为什么一些看似基础的工程问题在法律场景里会变得重要。缓存是否命中、任务是否完成、模型是否返回结果，本来只是运行信息；当系统的输出可能被专业人员采用并继续流转时，这些状态就不能越权替代业务事实。一个“完成”到底是谁宣布的、基于什么版本、能不能被重放、出现新材料以后是否仍有效，都会直接影响后续责任和恢复。

## 4. 通用平台的边界：为什么不直接用 Dify、Coze

成熟的通用 Agent 平台很有价值。它们通常已经能够提供用户入口、会话、工作流、模型调用、RAG、Tool Calling、页面交互和部分运行观测。对大量简单问答和通用流程，这些能力没有必要由 Zuno 重新实现。

因此，Zuno 和通用宿主并不是天然的替代关系。一种合理形态是直接使用通用宿主和法律能力；另一种形态是让通用宿主继续负责 UI、会话和通用编排，而 Zuno 只作为法律后端提供专业语义和长期业务状态。只有当任务确实需要更强的计划控制、故障恢复和正式领域状态时，完整的 Zuno 原生运行时才有存在理由。

这个判断很重要，因为它把“产品边界”从技术喜好拉回业务责任。是否使用 LangGraph、是否保存长期 Memory、是否启用 GraphRAG，都不应该先决定系统是什么；相反，应该先确认任务需要保护哪些长期事实，再选择最轻的实现方式。这样才能避免因为某个框架流行，就反过来制造本来不存在的需求。

真正不能简单外包给“平台 Feature List”的，是项目必须自己承担的业务责任。通用平台可以保存工作流状态，却不会自动替一个法律项目定义什么是正式证据；可以提供 RAG，却不会自动决定一代索引是否足以支持当前案件范围；可以重试工具调用，却不会自动知道某个外部提交超时以后现实动作是否已经发生。这些问题不是平台强弱之争，而是专业语义最终由谁负责的问题。

所以 Zuno 的边界不是“别人做不到的都自己做”，而是：**通用能力优先复用；只有长期属于法律业务、事实权威和故障恢复的责任，才由 Zuno 自己拥有。**

## 5. Zuno 必须自己承担的工程责任

### 5.1 材料版本与知识就绪

文件进入系统以后，原始材料首先需要稳定的版本身份。随后 OCR、切分、向量、图结构和其他检索表示可以围绕这份材料生成，也可以因为算法升级而重新生成。

这里最重要的区别是：知识处理“做完了”不等于当前任务“可以放心使用”。一百份材料中九十八份已经处理完成，对查询某一份合同条款可能已经足够；但如果剩下两份恰好决定争议金额，就不能据此给出“全案材料已经齐全”的结论。Zuno 因此把正式材料版本、可重建的知识生成版本，以及面向具体任务的就绪判断分开。工程上分别用 `DocumentVersion`、`KnowledgeGeneration` 和 task-level `ReadinessDecision` 表达这些概念。

### 5.2 机器候选与正式业务事实

检索命中、模型生成和专业算法输出都可能有价值，但它们首先只是机器候选。材料可能过期，检索可能只覆盖部分范围，模型可能理解错误，算法也可能只适用于特定案件类型。

因此，机器可以产生 `EvidenceCandidate`、Finding Proposal 或其他建议，但正式 Evidence、Finding 和 WorkProduct 必须由法律领域规则和必要的人审决定。这里最重要的不是对象名字，而是把“机器认为可能成立”和“业务正式承认已经成立”分开。

### 5.3 长期引用与结果失效

检索阶段的引用主要说明“为什么这一次找到了这段内容”；正式工作成果则需要说明“当时到底采用了哪一版材料、哪个稳定位置以及哪些专业判断”。这两种引用的生命周期不同。索引、切分器、Embedding 和 Reranker 可以重建，历史成果所依据的材料不能跟着重建结果一起漂移。

同样，正式成果也不是一经形成就永远有效。新材料进入以后，旧 Finding 或 WorkProduct 可能需要复核。系统应该保留旧版本作为历史事实，同时沿依赖关系标记哪些结果已经 stale / review-required，而不是悄悄覆盖历史，或者每次新增材料都全案重算。

### 5.4 现实副作用与对账恢复

纯计算失败时，重新执行往往没有问题；现实动作却不同。假设系统向外围法院系统提交一份正式结果，请求发送以后连接超时。本地此时不知道远端到底有没有成功。如果直接再次 POST，可能制造重复业务记录。

因此，Zuno 把动作准备、实际尝试、结果确认和结果未知后的对账分开。工程上可以表达为 `PreparedAction`、`ToolAttempt`、`EffectReceipt` 和 `ReconciliationReceipt`。这些名称的目的不是增加状态，而是避免把“没有收到响应”错误地解释成“现实动作一定没有发生”。

### 5.5 从研究成果到稳定专业能力

研究模型、算法脚本、规则实现、LLM 或外部 API 都可能完成同一类专业任务，但业务系统不应该直接依赖某一篇论文或某一个 SDK。更稳定的做法是先定义“事件抽取”“冲突检测”“类案检索”这类专业能力承诺，再让不同实现作为版本化 Provider 去满足它。

Zuno 因此把 Research Artifact、Domain Capability、Versioned Provider、Conformance、Eval 和 Eligibility 区分开来。一个实现“能够调用”只是起点；只有接口符合要求、评测达到门槛，并且适合当前数据和任务范围时，它才有资格被运行时选择。

### 5.6 专业质量不能用 HTTP 200 代替

模型调用成功、JSON Schema 正确、Top-K 有结果，都只能证明计算链路完成，不能证明法律质量。真正需要关心的是证据是否充分、引用是否正确、是否存在无依据主张、结论是否适用、人工是否接受，以及故障恢复、时延和成本是否在可接受范围内。

这也是为什么 GraphRAG、长期 Memory、Reflection、Specialist Agent 和 Native Runtime 都不能因为“已经做出来”就永久保留。复杂机制需要用真实任务证明收益，否则更简单的方案应该重新成为默认选择。

## 6. 一个复杂法律任务怎样流过系统

仍然以上面的案件为例。任务开始时，应用层先确定事项、用户身份和任务范围，再确认允许访问哪些正式材料版本。知识系统检查这些材料的处理状态和当前任务所需的最低条件；如果关键附件缺失，系统应该等待、缩小范围或明确阻断，而不是悄悄使用不完整材料生成完整结论。

材料可用以后，Knowledge 层负责检索和构造候选证据，专业 Capability 可以进行事件抽取、对齐、冲突检测、证据比较和适用性分析，模型也可以参与提取、推理、批判和综合。这一阶段可以产生大量中间结果，但这些结果仍然是候选。

当任务需要多个步骤时，Agent Runtime 负责计划、依赖、并行、预算、等待和重规划；简单任务则可以继续保持单步路径。候选结果真正准备进入正式业务状态时，Legal Domain 才执行正式准入，需要人工判断的地方由专业人员审核。成功以后，WorkProduct 可以回到当时采用的材料、证据、结论和人工决定。

如果后续进入新证据，Domain 判断哪些正式结果已经需要复核；Application / Integration 负责把这个变化交付给外部消费者。若任务还需要向外围系统创建记录、提交结果或触发流程，Tool Runtime 再负责现实动作的执行和对账，Security & Governance 则在每个高风险边界上判断当前是否仍允许继续。

九个逻辑责任域正是从这条工作链中逐渐出现的。它们不是九个必须依次经过的站点，而是当某一类事实必须被长期保存和恢复时，系统需要知道谁最终说了算。

这个划分还解决了一个常见的工程误区：把“组件在哪里”误认为“事实归谁负责”。例如 Runtime 和 Domain 都可能把数据写入 PostgreSQL，但前者记录任务执行到哪里，后者记录法律业务上什么已经正式成立；二者使用同一种数据库，并不意味着它们拥有同一种事实。相反，如果一个运行检查点能够随意覆盖正式业务结果，或者一个向量索引的完成状态能够直接宣布案件已经具备全部知识，系统就会在故障和重放时产生无法解释的结果。

因此，Zuno 更关心的是事实生命周期，而不是技术栈列表。模型、检索、工作流引擎和数据库都可以替换，只要替换以后仍然能够回答：材料版本由谁维护，候选何时升级为正式事实，长任务从哪里恢复，权限由谁重新判断，外部动作结果未知时怎样确认现实状态。这些问题才构成系统长期稳定的骨架。

## 7. 三种产品形态与工程取舍

从复用成熟能力的角度，Zuno 至少允许三种合理形态。

**通用宿主 + 法律 Skills / Capabilities。** 对简单问答、轻量检索和少量专业能力，这往往已经足够。Zuno 没有理由为了统一技术栈接管全部运行控制和领域状态。

**通用宿主 + Zuno Legal Backend。** 通用宿主继续负责 UI、会话和基础工作流，Zuno 负责材料版本、专业能力、正式领域状态、恢复和专业评测。这种组合能够保留成熟宿主的产品能力，同时让法律业务语义拥有独立边界。

**Zuno Native Runtime + 一等领域状态。** 只有复杂任务确实需要动态计划、可恢复的多步骤执行、安全并行、人工中断、持续授权和更强运行控制时，才值得承担原生运行时的复杂度。

三者不是从低到高的产品等级。正确选择取决于任务质量、故障恢复、人工接受率、时延、Token、成本和维护复杂度。如果中间形态已经满足业务要求，继续建设完整原生运行时反而可能是过度设计。

这三种形态也说明了 Zuno 和通用平台之间更准确的关系：Zuno 不需要成为另一个“什么都有”的平台。一个成熟宿主已经提供得足够好的入口、会话、通用工作流和模型管理应该继续复用；Zuno 只在法律业务真正需要长期权威和恢复语义的地方增加自己的边界。这样做的收益不仅是减少重复建设，也使未来的替换更容易：Host 可以换，模型可以换，检索实现可以换，但法律领域状态和恢复规则不应该随着某个框架的版本一起漂移。

## 8. 什么时候完整 Zuno 反而不值得使用

成熟的架构不仅要说明自己解决什么，也要说明什么时候应该退回简单方案。

如果任务是一问一答，材料范围稳定，不需要长期业务状态，不发生高风险副作用，结果也不需要正式准入，那么普通 RAG 或通用 Agent 平台通常更简单、更便宜、更容易维护。

如果 GraphRAG 对目标问题没有比 Hybrid Retrieval 带来稳定收益，就应该缩小甚至取消图检索；如果长期 Memory 没有证明对连续工作有价值，短期上下文和显式 Domain State 可能已经足够；如果 Specialist Agent 相比普通并行 Step 或 Subgraph 没有稳定提升，就没有必要建设更复杂的自治 Multi-Agent Runtime。

同样，九个逻辑责任域也不等于九个微服务。只要独立扩缩容、安全隔离、故障半径、团队边界或部署生命周期没有形成明确需求，它们完全可以继续共处模块化 Python 后端和必要的 Worker 中。

逻辑边界和物理部署是两个层次。前者解决“谁拥有事实”，后者解决“代码和进程怎样运行”。先把这两层分开，可以让系统在规模尚小时保持简单，也保留以后根据负载、安全或组织边界再拆服务的空间。

## 9. 项目演进：项目是怎样发展到今天的

今天的架构推导不能用来反写历史。根据目前能够恢复的材料，项目历史更像是一条逐步工程化和验证的路径：

```text
已有产品和代码
  → Agent / Memory / Tool 等方向继续开发
  → Internal Demo
  → 客户侧 / 智慧法院项目组 Demo
  → 客户反馈：回答质量需要提高
  → 后续迭代
  → Court-side Testing
  → Pilot Validation
```

### 9.1 加入项目时，系统已经存在

我约在 2026 年 3 月加入。加入时项目已经有代码和一个比较简单的自研前端，因此这不是 Greenfield（从零新建）项目，项目前期产品方向和第一版系统也不能算作个人成果。

这更接近真实工程中的接手与演进：先理解已有系统和数据，再在不破坏现有链路的情况下接入能力、调试问题和继续迭代。历史第一条需求、最早提交、第一版正式产品名称和当时完整技术栈尚未恢复，今天 `main` 的目录与依赖不能自动成为历史版本说明。

### 9.2 Internal Demo 证明链路进入内部验证

Internal Demo 是目前能够恢复的第一个重要阶段。它说明已有产品和能力曾进入项目组内部演示和迭代验证，但具体日期、参与人、环境、脚本和每项能力的完成程度还没有恢复。

因此，这一阶段可以证明“产品链路进入内部验证”，不能据此声称已经达到某个准确率或正式质量门槛。

### 9.3 客户侧 Demo 暴露了回答质量问题

之后项目进行过客户侧或智慧法院项目组 Demo。当前能够确认的一条反馈是：**回答质量还需要提高。**

现有材料不足以把根因直接归结到 Prompt、Retrieval、Model、Memory、Tool、引用或数据处理中的某一层，也没有恢复前后准确率、Bad Case 集合和具体修复指标。这段历史最有价值的下一步不是编造一个漂亮结论，而是恢复原始错误、复现路径、根因、修改、回归测试和前后指标。

### 9.4 法院侧测试进入了更真实的使用环境

客户反馈以后，项目继续迭代并进入法院侧人员测试。这个阶段比 Demo 更接近真实工作，因为实际用户会暴露专业术语、材料表达、引用习惯、权限和工作流程问题。

但测试题数量、参与法院、人员角色、参考答案、Reviewer 协议、环境和性能数据目前仍然没有恢复。真实人员参与本身很有价值，却还不足以形成可比较的产品质量证据。

### 9.5 Pilot Validation 是试点，不是生产资格

项目后来进入 Pilot Validation。当前可以确认“走到过试点验证”，但没有资料支持正式 Production、稳定用户规模、部署 Endpoint、SLA、QPS、Latency、Token、Cost、HA 或 DR。

因此，Pilot 最值得恢复的是部署位置、参与人员、使用时长、任务类型、数据外发限制、真实故障、回滚方式、人工兜底和成功标准。在这些证据出现以前，“进入 Pilot”和“Production Ready”必须严格分开。

## 10. 团队与个人参与：团队是什么形态，我在里面做了什么

目前能够恢复的核心研发规模约为 7–8 人。一名学硕学长承担主要技术负责人和任务协调角色，并把我带入项目。现有材料不足以把他定义成 CTO、总架构师或合同负责人，也不足以恢复每个方向的正式 Owner。

团队涉及 Agent、Knowledge / Retrieval、法律智能能力、Memory / Context、Tool Integration、后端、前端、测试和部署等方向。它更像研究成果工程化过程中形成的小型研发团队，成员会跨越算法、Agent、知识、后端和业务联调边界，而不是每个人只维护一个完全独立的服务。

目前能够明确描述的个人参与包括：部分 Agent 开发；Memory 相关的第一批重要工作；OpenViking 在 Memory / Context 区域的接入；Tool Calling Strategy 相关开发；以及进入数据库查看或调试实际数据。开发期间也学习和接触过 LangGraph、GraphRAG，但这些事实不能推出完整 Agent Runtime、整个 GraphRAG、全部 RAG 或整个后端都是个人独立实现。

这里必须区分“接触过、参与过、负责过、主导过”。当前能够稳定证明的是方向级参与；任务级输入输出、具体代码、Bug、测试和结果，仍需要继续从历史提交、任务记录和个人回忆中恢复。

今天仓库里的总体架构、九模块文档、ADR 和文档治理经过后续系统化整理。这能够证明今天对整套 Target Architecture 的理解和维护能力，但不能倒推“2026 年 3 月加入时就是整套总体架构的历史 Owner”。项目不是从零由个人搭建，这个边界应该始终保持清楚。

## 11. 四条事实线：History、Current、Target 与 Unknown

Zuno 文档体系刻意把四类信息分开，因为它们回答的是不同问题。

**History** 记录项目为什么出现、经历过什么、谁参与过什么。客户侧 Demo、回答质量反馈、Pilot Validation、OpenViking 接入等属于这一层。

**Current** 只表示今天 `main` 能由代码、Migration、测试、Trace、Eval 或真实运行证明的事实。当前仓库已经存在 Python 后端、Web / API、Agent、Knowledge / Retrieval、Memory、Capability / Tool、数据库和测试入口，也存在部分运行与观测基础，但目录存在不等于九模块 Target 已完整实现，更不等于 Production Ready。Current 的具体边界必须回到 [`docs/evidence/`](../evidence/README.md)。

**Target** 表示今天接受的目标设计，例如九个逻辑责任域、七对象最小领域内核、Knowledge Readiness、Single Controller、Formal Admission、Effect Recovery 和持续授权。这些设计规定未来实现应该怎样收敛，却不能被用来声称历史 Pilot 已经拥有同样机制。

**Unknown** 则表示目前还没有可靠证据。历史第一版正式产品名称和第一条需求原文、直接合同甲方、完整参与法院名单、历史完整权限模型、每篇论文具体进入哪个产品版本、客户质量问题的根因和修复指标、Pilot 的真实用户量与运行数据、历史 QPS / Latency / Cost / HA / DR，以及个人任务对应的具体 PR、接口、SQL、Bug 和测试闭环，都仍然属于 Unknown。

不知道的事情保持不知道，是这套项目叙事可信度的一部分。更严格的事实台账由 [`docs/governance/project-fact-provenance.md`](../governance/project-fact-provenance.md) 维护。

这四条事实线在阅读时经常会交叉，但不能混合使用。历史告诉我们系统为什么会走到这里，却不保证今天仍然采用当时的实现；Current 说明今天代码和测试能够证明什么，却不能说明目标设计已经完成；Target 给出未来收敛方向，却不应该被写成已经部署的能力；Unknown 则提醒读者哪些空白仍需取证。对于研究型工程项目来说，这种边界尤其重要，因为论文能力、Demo 能力、Pilot 能力和生产能力之间往往隔着多层工程条件。

## 12. 已知与未知：相比通用方案，我们今天到底证明了什么

今天能够确认的是：Zuno 的目标设计已经把一批长期法律业务责任说清楚，包括正式领域状态、材料版本和知识就绪、候选与正式证据分离、正式准入、历史引用、新证据失效传播、现实副作用恢复、研究成果工程化和专业质量评测。

今天还不能无条件声称 Zuno 比 Dify、Coze 或其他通用平台准确率更高；不能声称 Native Runtime 已经证明对所有任务更稳定；不能声称 GraphRAG 已经显著优于 Hybrid / Vector / BM25；不能声称 Multi-Agent 已经优于 Single Controller + 并行 Step；也不能因为历史上进入 Pilot 就把系统描述成已经获得生产资格。

要把“设计差异”升级为“已证明优势”，至少需要在相同任务、语料、模型和近似预算下比较三种形态：通用宿主 + 法律能力、通用宿主 + Zuno Legal Backend、Zuno Native Runtime + 一等领域状态。比较指标除了法律质量和引用，还应该包括人工接受、故障恢复、时延、Token、成本和维护复杂度。

如果测量最终证明某个复杂机制没有稳定收益，删掉或缩小它就是合理的工程收敛，而不是项目失败。

这种克制也影响项目叙事本身。我们可以说“目标架构针对这些风险建立了明确边界”，却不能跳过测量直接说“因此产品一定更准确、更稳定、更便宜”。架构可以证明一套设计能够避免某些类别的错误推断，例如把 Checkpoint completed 当成 Domain commit，或把 HTTP timeout 当成外部动作失败；但真实业务收益仍然需要实验和运行数据。把设计正确性和产品效果分开，是后续所有评测工作的前提。

## 13. 仍需恢复的工程证据

项目和架构文档已经能够解释大量设计问题，下一步提升可信度最有价值的不是继续增加术语，而是恢复少量真正完整的工程闭环。

第一类是**质量闭环**：找到一到两个真实 Bad Case，恢复原始输入、错误表现、复现方法、根因、修改、回归测试和前后指标。这样“客户反馈回答质量需要提高”才能从历史描述变成可以深入讨论的工程案例。

完整的质量闭环比单独一个指标更有价值。一个准确率数字只能说明某次测量结果，而原始错误、根因和修复过程能够解释系统真正在哪里失效，也能检验“为什么需要某个架构边界”是否来自真实问题。对 Zuno 来说，未来最有价值的证据不是再增加一张架构图，而是把少数典型错误从输入一直追到修复和回归。

第二类是**个人任务闭环**：从 Agent、Memory / OpenViking、Tool Calling 或数据库调试中恢复一到两个任务，明确原需求、个人责任、输入输出、关键接口、异常、测试和最终结果。

这一类证据同时保护项目叙事和个人 Ownership。团队完成过某项能力，不代表个人完成了整条链；个人参与过一个方向，也不等于拥有整个模块。把任务拆到需求、代码、Bug 和验证结果，能够把“参与过”进一步落实成可核对的工程事实。

第三类是**Pilot 闭环**：恢复环境、参与人员、任务量、运行时长、评价方式、真实故障、数据外发限制、人工兜底和验收条件。它决定历史项目究竟离正式生产还有多远。

第四类是**对照测量**：用统一数据集比较三种产品形态，并对 GraphRAG、Memory、Specialist Agent 和 Native Runtime 做消融实验。只有这样，架构假设才会逐步转化成工程证据。

## 14. 从项目叙事进入总体架构

到这里，项目层已经完成了自己的任务：说明 Zuno 从哪里来，面对什么业务问题，为什么普通 RAG 和通用平台仍然留下专业工程责任，项目历史走到了哪里，以及今天哪些结论可以相信。

下一层问题不再是“为什么立项”，而是“这些责任怎样组织成一个可以长期运行和恢复的系统”。这进入 [`docs/architecture/architecture.md`](../architecture/architecture.md)。总体架构负责解释跨模块的事实边界、正常流程和恢复原则；[`docs/modules/`](../modules/README.md) 再把这些原则落实到九个责任域；当问题变成“今天到底实现了多少”，则回到 [`docs/evidence/`](../evidence/README.md)。

这三层分别回答项目因果、目标设计和当前证据。把它们分开，才能既把系统讲完整，又不把尚未实现或尚未证明的内容写成事实。
