# Red Interview Behavior Evidence — 2026-09

status: workflow-research-input
owner: Red/Blue Harness Maintainer
purpose: calibrate interviewer behavior; not a per-round Red question source

这份材料记录一次针对 AI Agent / LLM 应用研发面经的定性抽样。它不拥有 Zuno 项目事实，也不作为每轮 Red 的直接题库。Red Skill 只吸收其中稳定的 interviewer behavior；具体公司题目、候选人答案和网页内容不直接复制进正式 Round。

## 观察到的稳定模式

### 面试先让候选人自己暴露技术主线

多份一面记录都从自我介绍、项目介绍或“你最近最有难度的项目”开始。面试官不会一上来把完整评分框架念给候选人，而是先听候选人怎样组织项目，再从他说出的技术、数字、困难和选择里挑线索。

### 深挖通常沿上一句连续推进

淘天一组 AI Agent 面经里，一条多 Agent 线连续出现了：为什么拆子 Agent、skill 能不能替代、候选人说不能完全替代以后继续问局限、再改变前提追问本质区别、再问多 Agent 什么时候会出错、最后要求真实经验。这个序列的重要特征不是题目本身，而是后一问依赖前一答。

去哪儿的一份记录也明确提到，面试官会根据候选人说出的关键词继续提问。字节的一份 AI 应用一面记录描述为前面了解个人经历和项目，后面根据项目细节不断追问。

### 真人追问往往很短

真实记录里大量问题只是“为什么这么拆？”、“具体怎么做的？”、“数据什么样？”、“准确度现在什么水位？”、“这个数字怎么来的？”、“你自己完全负责吗？”、“真遇到过这种问题吗？”这种单意图短问句。深度来自连续追问，而不是单个问题里同时塞背景、算法、测试、故障和 Trade-off。

### 一场面试不会平均覆盖所有简历 Claim

很多 45–65 分钟的一面会围绕一个主要项目长时间追，随后切到一段基础知识、算法题或场景题。面试官可能因为候选人某个回答有意思而继续，也可能发现不熟后直接换线程。完整覆盖是题库目标，不是真实会话目标。

### 基础题可以突然出现，但通常有岗位或项目上下文

近期 Agent / AI 应用面经中常见从项目切到并发、网络、Redis、数据库、TCP、协程或算法题。它们不一定都能严格从上一句话推导，但整体仍服务于岗位基础判断。Red 不应为了形式上的“每题必须能指回一个 Claim”而把普通基础题包装成很长的项目场景。

### 面试官并不总是比候选人更懂细节

一份覆盖多家公司、约半年 LLM 应用面试的个人总结提到，不同公司的面试官对 RAG / Agent 深度差异很大，很多问题仍然是工程实践、效果评估、是否真的做过和方案取舍。Red 应模拟合理的岗位面试官，而不是一个提前知道隐藏正确答案的架构审判者。

### 过度原子化本身会显得不像人

有候选人专门吐槽 AI 面试官会把一个普通回答无限拆到没有信息价值的原子细节。这个反例说明“继续追问”必须有新的判断价值；追得更细不自动等于更真实、更难或更专业。

## 对 Red Skill 的直接约束

1. Live interview 不使用固定 30 问线性脚本。
2. 先用少量 seed question 让候选人暴露主线，再按回答动态选 follow-up。
3. 一次只问一个主要意图；复杂验证拆成连续几轮。
4. Follow-up 优先复用候选人刚说过的名词、数字、选择、困难或不确定点。
5. 同一 thread 连续 3–6 个自然短问句通常比一个四层复合长问更像真人。
6. Thread 没有新信息增益时及时换题；Kill Switch 属于 Controller policy，不作为面试官话术展示。
7. Pressure suite 可以保持 100 问做覆盖，但必须与 live interview conversation 分离。
8. 人工 Review 重点检查“如果候选人这样答，下一问会不会自然”，而不只检查每题是否技术正确。

## Evidence boundary

这是定性样本，不代表所有公司、所有面试官或所有 Agent 岗位。Skill 只采用跨来源重复出现、且与用户真实面试反馈一致的行为模式。后续若用户提供新的真实面试记录，以用户本人实际经历优先更新。
