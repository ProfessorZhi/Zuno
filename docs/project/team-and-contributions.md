# 团队与开发分工

## 团队情况

目前能够恢复的核心研发规模约为 7–8 人。团队由一名学硕学长承担主要技术负责人角色，他把用户带入项目并在技术工作中承担较强的方案和任务协调责任。这里不把他描述成 CTO、总架构师或合同负责人，因为这些正式 Title 没有材料支持。

项目整体涉及 Agent、Knowledge / Retrieval、法律智能能力、Memory / Context、Tool Integration、后端、前端、测试和部署等方向。不过，历史完整人员名单、正式职称、每个方向的人数和明确 Owner 目前没有恢复，因此这些只能作为团队涉及的工作方向，不能写成已经确认的正式组织结构。

从工程合作形态看，这更像一个研究成果工程化过程中形成的小型研发团队：成员需要跨越算法、Agent、知识、后端和业务联调边界，而不是每个人只维护一个完全独立的大厂式服务。这个判断可以帮助理解为什么用户会同时接触 Agent、Memory、Tool 和数据库，但不能据此反推出每个人的完整职责表。

## 我什么时候加入

用户约在 2026 年 3 月加入，身份是研究生工程参与者。加入时项目已经存在，手上已有代码和一个比较简单的自研前端，因此用户不是从零开始立项开发，也不能把项目前期形成的产品和架构全部归为个人成果。

这个起点反而适合用来解释实际工程能力：加入一个已有系统后，需要先理解现有代码和数据，再在不破坏已有链路的情况下完成新能力接入、调试和迭代。等历史任务级材料恢复以后，个人项目介绍应该更多讲“接手什么问题、怎样定位边界、做了什么修改、怎样验证”，而不是用“从零搭建整个系统”这种无法证明的表述。

## 我实际参与过什么

目前可以明确描述的参与方向包括：

- 部分 Agent 开发；
- Memory 相关的第一批重要工作；
- OpenViking 在 Memory / Context 区域的接入；
- Tool Calling Strategy 相关开发；
- 进入数据库查看或调试数据。

这些描述说明参与过相应方向的工程工作，但还没有恢复到具体任务、文件和提交的程度。当前仓库中存在某段代码，也不能自动证明它就是用户在历史项目中编写的。

这里最好把“方向级贡献”和“任务级贡献”分开。方向级贡献可以说“参与了 Memory / Context 接入”“参与了 Tool Calling Strategy”；任务级贡献则需要进一步回答输入输出是什么、改了哪些接口、遇到什么失败、为什么采用某个方案、怎样测试。只有后一层材料恢复以后，才适合把简历 bullet 写得非常具体。

## 学习接触与实际职责

用户在开发期间学习和接触过 LangGraph、GraphRAG。这些经历能够说明当时接触过相关技术，但不能据此说用户完整实现了 Agent Runtime、GraphRAG、全部 RAG 或整个后端。类似地，数据库查看和调试不等于负责数据库总体设计。

同样需要区分“为了完成任务主动学习某项技术”和“成为该模块的长期 Owner”。前者本身是有价值的工程经历：面对现有系统，需要快速理解 LangGraph、GraphRAG 或数据库中的真实数据才能完成调试；但如果没有提交、设计记录和长期维护证据，就不应把它升级成“主导某模块架构”。

## 当前文档维护角色和历史项目角色必须分开

今天仓库中的总体架构、九模块文档、ADR 整理和文档治理经过了后续系统化重构。这些文档可以帮助用户深入理解项目，也可以作为后续实现的架构基线，但不能倒推“用户在 2026 年 3 月加入历史项目时就是这套总体架构的 Owner”。

面试官如果问“这个架构是谁设计的”，应先区分历史项目阶段和当前仓库整理阶段。历史个人贡献只从能够恢复的历史任务说；当前架构则可以作为用户今天真正理解、参与整理和能够深入讨论的目标设计。两者混在一起，会让个人经历看起来更强，却经不起提交历史和时间线追问。

## 面试时怎样描述参与深度

比较稳妥的表达方式是从“我参与了什么问题”开始，而不是从一个过大的职位名称开始。例如：

> 我加入时项目已经有代码和简单前端，我后续主要参与 Agent、Memory / Context 和 Tool Calling 一带的工程工作，也会进数据库看实际数据。Memory 方向参与过 OpenViking 接入；LangGraph 和 GraphRAG 是开发过程中为了理解和推进相关任务学习接触的。现在任务级提交还在继续恢复，所以我不会把整个 Runtime 或 GraphRAG 都说成自己独立实现。

这类表达并不会削弱项目含金量。相反，它给面试官留下了继续追问真实工程问题的空间，并且把“参与过”“负责过”“主导过”“独立实现”四个强度等级分开。

如果以后恢复出一个明确任务，例如某段 Memory 写入 / 召回路径或某个 Tool Calling 故障，就可以再升级成：问题是什么 → 自己负责哪部分 → 关键设计 → Bug / 边界 → 测试 → 结果。那时贡献深度由证据自然体现，不需要靠夸大的 Owner 名称。

## 目前不能扩大描述的范围

现有资料不支持把用户描述成整个项目负责人、总体架构负责人、完整后端 Owner、完整 GraphRAG Owner、数据库总体设计者、法律算法负责人或 Production / Deployment Owner。简历或面试中的个人表述应停留在已经能够说明的参与方向，直到任务级材料恢复。

同理，项目进入过 Pilot 也不能自动写成“我负责生产部署”；客户反馈回答质量需要提高，也不能自动写成“我通过某项方案把准确率提升 X%”。只要 Cause → Fix → Metric 还没有恢复，就应该说事实本身并说明目前能确认到哪一步。

## 还缺哪些任务级信息

目前尚不能恢复用户第一项具体开发任务、改过的具体逻辑、输入输出、OpenViking 使用的 SDK / API / Adapter 形态、Memory 的写入和召回路径、实际使用过的 Tool、具体 SQL，以及某个 Bug 从发现到修复和验证的完整链路。这些内容适合以后根据提交、代码记录或用户回忆逐项补充。

下一步最有价值的是恢复一到两个深案例，而不是把所有方向都写得更宽。理想案例应该同时拥有需求背景、自己的责任边界、代码或配置变化、失败路径、测试和最终结果。如果还能对应客户 Bad Case 或 Pilot 反馈，就能把“个人贡献”“产品价值”和“工程证据”三层真正连起来。

历史贡献一旦恢复，应先更新本文件和 `project-fact-provenance.md`，实现 / 测量证据再进入 `docs/evidence/`。不要把新的个人事实只写进简历或聊天而不回到项目事实层。
