# Zuno 项目：把法律 AI 从“能回答”带到“能长期负责”

Zuno 是南京大学软件学院 LIPLAB 智慧司法研究与工程化背景下的法律智能 Agent 平台，面向天津法院智慧平台相关场景。它连接案件材料、检索与研究能力、模型、专业人员判断和业务系统，让机器能力能够进入一条可复核、可追踪、可恢复的法律工作链。

理解这个项目，最先要回答的不是用了什么 Agent 框架，而是**法律 AI 在真实工作里究竟卡在哪里**。普通大模型已经很会生成文字，RAG 也能让答案带上外部材料；真正困难的是，当答案可能被专业人员采用、材料会继续变化、任务会运行很久、系统还会把结果送到外部业务系统时，怎样保证机器没有把“看起来合理”冒充成“值得长期负责”。

外部研究反复报告几类问题：RAG 会漏掉关键材料或选错来源文档；法律语料中大量相似文档会增加检索错配；模型可能编造事实、案例或法条；自动化偏见会让人过度相信流畅输出；模型和检索链路又很难天然提供稳定的责任与审计路径。相关研究整理见 [`docs/research/legal-ai-pain-point-evidence.md`](../research/legal-ai-pain-point-evidence.md)。这些文献证明的是**领域问题真实存在**，不等于 Zuno 历史上已经逐项遇到或解决了它们。

Zuno 自己的历史证据更克制。目前能够确认项目经历过 Internal Demo、客户侧 / 智慧法院项目组 Demo、法院侧人员测试和 Pilot Validation；客户侧 Demo 留下过“回答质量还需要提高”的反馈。现有材料还不足以恢复这条质量问题究竟来自 Prompt、Retrieval、Model、Memory、Tool、引用还是数据处理，也没有前后准确率或 Bad Case 集合。因此，Project 文档可以说明 Zuno 面对的是怎样一类问题，却不能把今天的 Target 设计反写成当年已经验证过的根因和解决方案。

## Zuno 选择解决的六个痛点

法律工作真正进入复杂场景以后，痛点会沿着同一条任务链连续出现。

**第一，材料很多、很杂，而且会继续变化；“上传成功”远远不等于“足够回答”。** 一个案件可能同时有起诉状、答辩材料、合同、补充协议、扫描附件、聊天记录和后续补交证据。OCR 尚未完成、材料版本变化、来源范围不完整时，检索仍然可能返回一段非常相关的文本。系统必须知道当前处理到了哪里、缺了什么，以及这些缺口会不会影响正在回答的具体问题。

这也暴露了普通 RAG 的第一个边界。Retriever 找到 Top-K，只能证明“当前检索找到了这些”；它不能证明关键材料没有漏，也不能把一次 retrieval miss 写成“全案不存在”。法律数据中结构相似的文档还会造成来源文档错配。Zuno 因此把材料身份、加工版本、任务就绪、候选证据和稳定引用当成长期问题，而不只把知识层理解成一个向量库。

**第二，模型会生成很流畅的答案，但流畅不等于专业可靠。** 法律 AI 的错误往往不是语法错误，而是错误事实、错误引用、遗漏限定条件、把部分证据写成确定结论，或者使用已经失效的法律依据。RAG 可以缓解一部分幻觉，却没有消除检索错误和模型误读。

Zuno 因而把机器输出定位为帮助专业人员工作的候选。检索、研究模型、LLM、规则系统都可以提出事实、事件、证据和分析建议；需要长期保存和继续流转的法律工作成果，还需要业务规则和必要的人审。项目解决的痛点不是“让 AI 代替法律判断”，而是让机器建议和人类最终承担责任的结果之间拥有清楚边界。

**第三，法律结果必须能回答“当时为什么这样判断”。** 如果系统只保存最后一段答案，几周以后很难解释它用了哪版材料、引用来自哪里、模型当时返回了什么、专业人员改了什么、为什么接受这版而不是另一版。更麻烦的是，新证据进入以后，昨天的结论可能今天已经不适合继续使用，但昨天确实发生过的判断和交付又不能被覆盖掉。

Zuno 因而需要把来源、版本、人工判断、正式工作成果和后续失效串成一条历史。这里解决的是**可追溯与可审计**，不是承诺未来重新调用一次模型还能逐字复现旧答案。

**第四，研究模型和 Demo 到长期业务之间有一层很厚的工程鸿沟。** LIPLAB 的研究积累覆盖裁判文书文本抽取、事件抽取与事件对齐、冲突检测、证据链、类案相似度、法条推荐和法律语言模型评测等方向。一篇论文可以证明某个方法在数据集上有效，一个 Demo 可以证明链路能跑，但业务系统还需要稳定输入输出、版本、权限、失败语义、恢复、替换机制、审计和持续评测。

Zuno 因此承担“研究能力工程化”的角色：业务依赖稳定的专业能力语义，而不是依赖某一篇论文、某个 Python class 或某个模型名称。新的研究实现只有在接口、适用范围和质量上获得足够证据以后，才应该进入长期路径。

**第五，一次真正的法律任务可能持续几十分钟甚至跨越多次人工等待，单次 request/response 不够描述它。** 分析过程中会有新材料进入、旧计算晚到、模型限流、人工暂停、服务重启、权限变化。此时“最后一次模型调用成功”并不能回答整个任务现在进行到哪里，更不能证明正式法律结果已经成立。

Zuno 因而需要长期任务控制和恢复能力。它要记住当前计划和已经完成的步骤，也要允许输入改变后重新规划；同时，运行进度不能越权覆盖正式业务事实。服务崩溃以后，系统应该先寻找已经真正发生的业务事实，再修复运行进度，而不是机械地把旧 Checkpoint 重放一遍。

**第六，系统一旦和外部法院或第三方系统发生交互，网络失败会变成现实世界的不确定性。** 一个 POST timeout 只说明本地没有拿到响应，远端可能没有执行，也可能已经成功。把 timeout 直接当成 Failed 再重试，会把一次网络问题变成第二次业务动作。

Zuno 因而单独管理会改变外部世界的动作和结果：发送以前稳定动作身份，发送以后区分“确定没发生”“已经发生”和“暂时不知道”。结果未知时先对账，需要撤回时再执行新的受控补偿动作，而不是假装现实世界随着本地 workflow 一起回滚。

这六个痛点构成 Zuno 的产品边界。简单条款问答不需要全部机制；受控 RAG 已经能解决的问题继续用 RAG。只有任务跨越材料版本、证据充分性、人工责任、长期运行、正式成果和现实副作用时，更强的 Zuno 能力才开始有价值。

## 为什么通用 Agent 平台还不能替 Zuno 决定这些事情

成熟的通用 Agent 平台已经能提供 UI、会话、工作流、模型调用、RAG、Tool Calling 和运行观测。Zuno 没有理由重做这些通用机制。简单法律问答只需要受控检索、稳定引用和一次生成时，通用宿主加少量法律能力就是合理方案。

剩下的问题都带着法律业务语义。通用 Checkpoint 能告诉系统流程走到哪一步，却不能决定一份法律工作成果是否已经正式成立；向量数据库能返回相似文本，却不能决定尚未处理的关键材料是否让当前问题没有资格得出完整结论；模型网关可以告诉系统某次 API 调用成功，却不能决定专业人员是否应该接受这次分析；HTTP client 能看到 timeout，却不能宣布法院侧现实动作一定没发生。

Zuno 因而只长期拥有这些通用基础设施无法替业务回答的问题。PostgreSQL、Object Store、Queue、Secret Manager、OpenTelemetry、模型 SDK、身份系统和通用 Agent Host 都优先复用。法律材料什么时候足以支持当前任务、机器候选什么时候可以进入正式成果、旧成果什么时候失效、现实副作用如何恢复，这些语义才是 Zuno 自己需要负责的部分。

## 任务复杂度决定需要多少 Zuno

用户只问“合同第 8 条约定了什么”时，最短路径仍然是权限检查、材料读取、检索、引用和生成。任务结束后没有正式成果需要长期维护，也没有现实副作用需要确认，普通受控 RAG 就可以保持简单。

多材料争议分析开始要求更长的责任链。系统要先判断当前问题是否拥有足够材料，再从材料中形成候选事实、事件和证据，由专业能力和模型协助比较与分析；需要成为长期工作成果的内容再进入业务接纳和必要人审。服务重启、补交证据或权限变化以后，系统还要能够说明哪些结果仍然成立，以及应该从什么事实继续。

如果任务继续向外围系统写入结果，问题又增加一层。系统要在动作发生前确认当前授权和必要审批，动作发生后确认现实结果；网络超时不能直接触发盲目重试。复杂度由这些业务边界逐层增加，而不是由“用了多少 Agent”决定。

同一组法律责任可以落在三种产品形态。

**通用宿主 + 法律 Skills / Capabilities。** 对简单问答、轻量检索和少量专业能力，这通常已经足够。成熟宿主继续承担会话、页面和通用工作流，法律能力只提供专业处理。

**通用宿主 + Zuno Legal Backend。** 当材料版本、正式成果、长期失效和恢复开始成为业务要求时，通用宿主仍可负责产品入口，Zuno 后端负责这些法律语义。这个形态保留成熟宿主能力，也避免为了一个专业后端接管整个平台。

**Zuno Native Runtime + 一等领域状态。** 只有任务确实需要动态计划、长期等待、可恢复的多步骤执行、安全并行、人工中断和持续授权时，原生运行时的额外成本才有依据。

三种形态没有从低到高的等级关系。选择取决于法律质量、人工接受率、故障恢复、时延、Token、成本和维护复杂度。中间形态已经满足约束时，继续建设完整原生运行时就是多余复杂度。

复杂机制因此都需要退出条件。GraphRAG 如果长期不能优于更简单的 Hybrid Retrieval，就不应留在默认主路径；长期 Memory 没有稳定收益时，应缩回短期上下文；Reflection、Specialist 或 Native Runtime 没有改善质量或恢复正确性时，也应关闭或降级。已经实现只能证明代码存在，不能证明设计应该永久存在。

逻辑责任与物理部署同样保持分离。九个责任域不等于九个微服务；在独立扩缩容、安全隔离、故障半径、团队边界或部署生命周期形成真实需求以前，它们可以继续共处模块化 Python 后端和必要 Worker 中。系统先保护事实边界，再根据证据决定是否拆服务。

## 项目真实走过的阶段

今天的痛点归纳和 Target Architecture 不能用来反写历史。根据目前能够恢复的材料，项目历史更像是一条逐步工程化和验证的路径：

```text
已有产品和代码
  → Agent / Memory / Tool 等方向继续开发
  → Internal Demo
  → 客户侧 / 智慧法院项目组 Demo
  → 客户反馈：回答质量需要提高
  → 后续迭代
  → Court-side Testing
  → Pilot Validation
```

**加入项目时，系统已经存在。**

我约在 2026 年 3 月加入。加入时项目已经有代码和一个比较简单的自研前端，因此这不是 Greenfield（从零新建）项目，项目前期产品方向和第一版系统也不能算作个人成果。

这更接近真实工程中的接手与演进：先理解已有系统和数据，再在不破坏现有链路的情况下接入能力、调试问题和继续迭代。历史第一条需求、最早提交、第一版正式产品名称和当时完整技术栈尚未恢复，今天 `main` 的目录与依赖不能自动成为历史版本说明。

**Internal Demo 把链路带入内部验证。**

Internal Demo 是目前能够恢复的第一个重要阶段。它说明已有产品和能力曾进入项目组内部演示和迭代验证，但具体日期、参与人、环境、脚本和每项能力的完成程度还没有恢复。

因此，这一阶段可以证明“产品链路进入内部验证”，不能据此声称已经达到某个准确率或正式质量门槛。

**客户侧 Demo 暴露回答质量问题。**

之后项目进行过客户侧或智慧法院项目组 Demo。当前能够确认的一条反馈是：**回答质量还需要提高。**

现有材料不足以把根因直接归结到 Prompt、Retrieval、Model、Memory、Tool、引用或数据处理中的某一层，也没有恢复前后准确率、Bad Case 集合和具体修复指标。这正是为什么前面的六类痛点必须区分“领域已知问题”和“Zuno 历史已证明问题”：我们知道法律 AI 常见失败在哪里，却还需要原始 Bad Case 才能证明当时 Zuno 的质量问题具体属于哪一层。

**法院侧测试进入更真实的使用环境。**

客户反馈以后，项目继续迭代并进入法院侧人员测试。这个阶段比 Demo 更接近真实工作，因为实际用户会暴露专业术语、材料表达、引用习惯、权限和工作流程问题。

但测试题数量、参与法院、人员角色、参考答案、Reviewer 协议、环境和性能数据目前仍然没有恢复。真实人员参与本身很有价值，却还不足以形成可比较的产品质量证据。

**Pilot Validation 仍属于试点。**

项目后来进入 Pilot Validation。当前可以确认“走到过试点验证”，但没有资料支持正式 Production、稳定用户规模、部署 Endpoint、SLA、QPS、Latency、Token、Cost、HA 或 DR。

因此，Pilot 最值得恢复的是部署位置、参与人员、使用时长、任务类型、数据外发限制、真实故障、回滚方式、人工兜底和成功标准。在这些证据出现以前，“进入 Pilot”和“Production Ready”必须严格分开。

## 团队与个人参与的边界

目前能够恢复的核心研发规模约为 7–8 人。一名学硕学长承担主要技术负责人和任务协调角色，并把我带入项目。现有材料不足以把他定义成 CTO、总架构师或合同负责人，也不足以恢复每个方向的正式 Owner。

团队涉及 Agent、Knowledge / Retrieval、法律智能能力、Memory / Context、Tool Integration、后端、前端、测试和部署等方向。它更像研究成果工程化过程中形成的小型研发团队，成员会跨越算法、Agent、知识、后端和业务联调边界，而不是每个人只维护一个完全独立的服务。

目前能够明确描述的个人参与包括：部分 Agent 开发；Memory 相关的第一批重要工作；OpenViking 在 Memory / Context 区域的接入；Tool Calling Strategy 相关开发；以及进入数据库查看或调试实际数据。开发期间也学习和接触过 LangGraph、GraphRAG，但这些事实不能推出完整 Agent Runtime、整个 GraphRAG、全部 RAG 或整个后端都是个人独立实现。

这里必须区分“接触过、参与过、负责过、主导过”。当前能够稳定证明的是方向级参与；任务级输入输出、具体代码、Bug、测试和结果，仍需要继续从历史提交、任务记录和个人回忆中恢复。

今天仓库里的总体架构、九模块文档、ADR 和文档治理经过后续系统化整理。这能够证明今天对整套 Target Architecture 的理解和维护能力，但不能倒推“2026 年 3 月加入时就是整套总体架构的历史 Owner”。项目不是从零由个人搭建，这个边界应该始终保持清楚。

## 今天能够相信什么

Zuno 文档体系把四类信息分开，因为它们回答的是不同问题。

**History** 记录项目为什么出现、经历过什么、谁参与过什么。客户侧 Demo、回答质量反馈、Pilot Validation、OpenViking 接入等属于这一层。

**Current** 只表示今天 `main` 能由代码、Migration、测试、Trace、Eval 或真实运行证明的事实。当前仓库已经存在 Python 后端、Web / API、Agent、Knowledge / Retrieval、Memory、Capability / Tool、数据库和测试入口，也存在部分运行与观测基础，但目录存在不等于九模块 Target 已完整实现，更不等于 Production Ready。Current 的具体边界必须回到 [`docs/evidence/`](../evidence/README.md)。

**Target** 表示今天接受的目标设计，例如九个逻辑责任域、七对象最小领域内核、Knowledge Readiness、Single Controller、Formal Admission、Effect Recovery 和持续授权。这些设计规定未来实现应该怎样收敛，却不能被用来声称历史 Pilot 已经拥有同样机制。

**Unknown** 表示目前还没有可靠证据。历史第一版正式产品名称和第一条需求原文、直接合同甲方、完整参与法院名单、历史完整权限模型、每篇论文具体进入哪个产品版本、客户质量问题的根因和修复指标、Pilot 的真实用户量与运行数据、历史 QPS / Latency / Cost / HA / DR，以及个人任务对应的具体 PR、接口、SQL、Bug 和测试闭环，都仍然属于 Unknown。

不知道的事情保持不知道，是这套项目叙事可信度的一部分。更严格的事实台账由 [`docs/governance/project-fact-provenance.md`](../governance/project-fact-provenance.md) 维护。

**设计已经说清痛点与责任，产品优势仍需要测量。**

今天能够确认的是：Zuno 的 Target 已经针对材料完整性与版本、检索可靠性、候选与正式结果分离、人工责任、长期恢复、现实副作用、研究成果工程化和专业质量评测建立了明确边界。相关外部领域证据见 [`docs/research/legal-ai-pain-point-evidence.md`](../research/legal-ai-pain-point-evidence.md)。

今天还不能无条件声称 Zuno 比 Dify、Coze 或其他通用平台准确率更高；不能声称 Native Runtime 已经证明对所有任务更稳定；不能声称 GraphRAG 已经显著优于 Hybrid / Vector / BM25；不能声称 Multi-Agent 已经优于 Single Controller + 并行 Step；也不能因为历史上进入 Pilot 就把系统描述成已经获得生产资格。

要把“设计差异”升级为“已证明优势”，至少需要在相同任务、语料、模型和近似预算下比较三种形态：通用宿主 + 法律能力、通用宿主 + Zuno Legal Backend、Zuno Native Runtime + 一等领域状态。比较指标除了法律质量和引用，还应该包括人工接受、故障恢复、时延、Token、成本和维护复杂度。

如果测量最终证明某个复杂机制没有稳定收益，删掉或缩小它就是合理的工程收敛，而不是项目失败。

## 下一步最缺的是痛点到修复的工程闭环

项目和架构文档现在可以解释“为什么这些问题值得设计”，下一步提升可信度最有价值的不是继续增加术语，而是恢复少量真实工程闭环。

第一类是**质量闭环**：找到一到两个真实 Bad Case，恢复原始输入、错误表现、复现方法、根因、修改、回归测试和前后指标。这样“客户反馈回答质量需要提高”才能进一步回答：究竟是检索漏召回、来源错配、模型幻觉、引用错误、上下文管理还是其他问题。

第二类是**个人任务闭环**：从 Agent、Memory / OpenViking、Tool Calling 或数据库调试中恢复一到两个任务，明确原需求、个人责任、输入输出、关键接口、异常、测试和最终结果。

第三类是**Pilot 闭环**：恢复环境、参与人员、任务量、运行时长、评价方式、真实故障、数据外发限制、人工兜底和验收条件。它决定历史项目究竟离正式生产还有多远。

第四类是**对照测量**：用统一数据集比较三种产品形态，并对 GraphRAG、Memory、Specialist Agent 和 Native Runtime 做消融实验。只有这样，架构假设才会逐步转化成工程证据。

这些项目事实把后续架构问题限定得很清楚：普通 RAG 和通用宿主已经足以覆盖简单任务；材料版本、检索可信度、正式业务事实、长期恢复和现实副作用则需要更明确的系统责任。[`docs/architecture/architecture.md`](../architecture/architecture.md) 从这些痛点继续推导 Target Architecture，[`docs/modules/`](../modules/README.md) 再把责任落实到九个逻辑域。今天究竟实现了多少仍由 [`docs/evidence/`](../evidence/README.md) 回答。
