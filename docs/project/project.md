# Zuno 项目：从智慧司法研究到可验证的法律智能 Agent 平台

Zuno 是南京大学软件学院 LIPLAB 智慧司法研究与工程化背景下的法律智能 Agent 平台，面向天津法院智慧平台相关场景。项目希望把课题组长期积累的智慧司法研究成果，逐步整理成能够被 Agent、业务系统和法律专业人员组合使用的专业能力，并让复杂法律工作不只“得到一段模型回答”，还能够留下材料版本、证据依据、人工判断、正式工作成果和可恢复的执行记录。

这篇文档是 `docs/project/` 的人类主文档。它试图连续回答一组项目级问题：为什么会有 Zuno，为什么已经有通用大模型平台仍值得做，项目和普通 RAG 有什么不同，项目经历了什么，我在其中参与了什么，以及今天哪些说法有证据、哪些仍然只是目标或假设。

它**不是**当前实现清单，也不是总体架构规格。要判断“现在代码到底实现了什么”，必须看 [`docs/evidence/`](../evidence/README.md)；要判断“系统为什么按九个责任域设计”，看 [`docs/architecture/architecture.md`](../architecture/architecture.md)；要追到某一个责任域内部的状态、失败和恢复，再进入 [`docs/modules/`](../modules/README.md)。

> **第一次阅读只抓一条主线。** 先看研究能力为什么需要工程化，再看普通 RAG 和通用 Agent 平台已经解决了什么；随后只追问那些仍然需要 Zuno 自己承担的专业语义、正式事实和恢复责任。理解了这条设计因果以后，再切回真实项目历史、个人 Ownership、Current / Target / Unknown。这样不会把“今天的 Target 设计”误读成“当年项目就是按今天的九模块一步步实现”。

## 1. 先用一句话说清 Zuno 是什么

如果只把 Zuno 介绍成“一个基于 LangGraph 的 Agent 平台”或者“一个 GraphRAG 知识库”，会把项目真正有价值的部分说窄。

更准确的说法是：**Zuno 是把法律智能研究能力、法律材料知识处理、受控 Agent 执行和可追溯法律工作成果连接起来的专业平台。** 它既可以自己承载复杂任务，也可以作为法律后端嵌入已有法院系统或通用 Agent 宿主。

这里有三个边界需要从一开始就说明。

第一，Zuno 是智慧法院相关体系里的一个具体产品，不是整个智慧法院项目。项目与天津法院智慧平台相关场景有合作背景，但现有材料不足以证明全部 22 家法院都正式部署或日常使用 Zuno。

第二，Zuno 的产品方向从一开始就包含法律智能平台、多专业 Agent 和可组合的专业能力，但“产品方向存在”不等于历史每个版本都已经完成全部目标能力。

第三，项目曾经进入过法院侧测试和 Pilot Validation（试点验证），但目前没有足够材料把它描述成正式 Production（生产系统）。Pilot、正式验收、稳定生产服务和生产级 SLA 是不同证据门槛。

## 2. 为什么会有这个项目

Zuno 的起点不是“Agent 很火，所以做一个 Agent 平台”，而是两条长期存在的线在工程上相遇。

一条线来自法院侧的法律智能化需求。法律材料多、版本多、专业判断链条长，工作人员不仅要找到文本，还需要理解材料之间的关系、判断证据是否足够、识别冲突、寻找法律依据，并最终形成能够被专业人员复核的结果。

另一条线来自 LIPLAB 和葛季栋团队长期积累的智慧司法研究。公开资料能够说明团队在裁判文书文本抽取、事件抽取与事件对齐、冲突检测、证据链、类案相似度、法条推荐和法律语言模型评测等方向拥有研究背景。南京大学软件学院对 LIPLAB 的公开介绍也显示团队长期参与天津法院信息化建设和智能司法技术落地。

这两条线之间存在一个很典型的研究工程化缺口：**论文、算法或 Demo 能证明某个局部问题“可以做”，但真正进入长期业务，还需要版本、接口、权限、状态、恢复、审计、评测和人机协作。**

例如，一个事件抽取模型在论文数据集上取得不错指标，不代表它已经是一个可在不同案件、不同材料版本和不同业务流程里稳定复用的产品能力。它还需要明确输入输出、Provider 版本、失败语义、兼容性、评测门槛，以及当模型结果被专业人员拒绝或新材料出现时怎样处理。

因此，Zuno 的立项价值并不主要来自“再做一个聊天机器人”，而来自把已有研究资产和真实法律工作之间缺少的工程层补起来。

## 3. 为什么普通知识库问答不足以覆盖目标工作

先承认一个事实：**很多问题根本不需要复杂 Agent。**

如果用户问“合同第 8 条写了什么”“这份判决书里原告的诉求是什么”，受控检索、引用和一次模型生成往往就足够。为了统一技术栈而强迫这类问题进入动态规划、Multi-Agent（多智能体）、长期记忆或复杂 GraphRAG，只会增加时延、成本和失败面。

Zuno 真正需要独立设计，是因为还有另一类任务。

假设一个事项包含原告材料、被告材料、补充协议、扫描件、沟通记录和后续补交证据。某一份材料可能出现新版本，某个扫描件的关键附件还没有 OCR 完成。系统需要先判断当前任务到底可以使用哪些材料，再从中检索和提取候选事实、事件或证据，然后比较双方陈述，识别冲突，寻找法条或类案，形成专业分析建议，最后由专业人员审核并决定哪些内容进入正式工作成果。

在这条链上，下面这些问题都不是“模型再聪明一点”就能自然解决的：

- 当前任务依据的是哪一版材料；
- 文件上传成功以后，这次任务是否真的已经具备足够知识；
- 检索到的一段文字只是候选，还是已经被业务正式接纳为 Evidence（证据）；
- 模型生成的结论只是 Proposal（建议），还是已经成为正式 Finding（结论）；
- 最终工作成果到底引用了什么不可变材料版本和稳定位置；
- 专业人员接受、修改或拒绝了什么；
- 新证据进入以后，旧结论和旧工作成果哪些部分已经需要复核；
- 系统崩溃以后，运行检查点和正式业务提交谁才是更权威的事实；
- 如果向外围系统提交一个有副作用的动作时请求超时，到底能不能重试；
- 权限在一个十分钟长任务中途变化，后续步骤还能不能继续；
- GraphRAG、Memory、Reflection 或 Specialist Agent 增加的复杂度究竟有没有带来稳定收益。

这组问题共同把“普通 RAG 问答”推向了一个长期、专业、可审计的法律工作系统。

---

**到这里，第一个问题已经回答完：不是所有法律任务都需要复杂 Agent。接下来真正要划的是平台边界。** 普通 RAG 能解决检索问答，通用 Agent Host 也能解决大量会话、Workflow、Tool Calling 和运行原语；只有在这些 baseline 之上仍然存在的长期专业责任，才有资格成为 Zuno 自己的边界。

## 4. 为什么不直接用 Dify、Coze 或其他通用 Agent 平台

这个问题最容易被回答成“通用平台做不到”，但这种回答既不准确，也容易在技术面试里被继续追问击穿。

Generic Host（通用 Agent 宿主）本身非常有价值。一个成熟的通用宿主通常已经能够提供用户入口、会话、任务提交、基础 Workflow（工作流）、模型调用、RAG、Tool Calling（工具调用）、页面交互和部分运行观测。很多场景下，这些能力完全没有必要由 Zuno 再做一遍。

所以 Zuno 与通用宿主不是天然竞争关系。对简单问答或通用流程，直接使用成熟宿主可能就是更好的工程选择；在另外一些部署形态里，通用宿主负责入口和通用编排，Zuno 只作为 Legal Backend（法律后端）提供专业业务语义，也可能比“所有东西都自己做”更合理。

Zuno 真正需要自己长期拥有的，是通用平台不会自动替一个法律项目负责的那部分东西：

**材料版本和知识就绪。** 文件到了系统里，不等于解析、OCR、索引和当前任务所需的能力全部准备好。Zuno 目标上把正式 DocumentVersion（材料版本）、可重建 KnowledgeGeneration（知识生成版本）和 task-level ReadinessDecision（任务级知识就绪判断）分开。

**候选信息和正式业务事实。** 检索、模型和专业能力可以提出 EvidenceCandidate（证据候选）、Finding Proposal（结论建议）或其他候选，但不能因为模型输出成功就直接成为正式领域事实。

**正式准入和可恢复因果。** 如果一个步骤必须产生正式法律业务结果，只有 Domain Owner（领域事实所有者）完成领域事务并留下匹配的 AdmissionReceipt（正式准入回执）以后，运行时才有资格认定对应正式提交完成。

**长期历史引用。** 检索阶段的 CitationLineage（检索引用链）解释“为什么这段内容被找到”；正式 WorkProduct（工作成果）需要保存当时真正采用的不可变材料版本和稳定位置。向量库、切分器、Embedding、Reranker 或 GraphRAG 可以重建，历史工作成果的依据不能跟着漂移。

**新证据带来的失效传播。** 一个答案今天成立，不代表新证据进入以后仍然成立。正式结果需要知道自己依赖什么，新材料才有可能触发有界重评，而不是静默沿用旧结果或一律全案重跑。

**现实副作用恢复。** 只读工具失败可以考虑重试；向外围系统提交正式结果时，如果 POST 超时，现实动作可能已经发生。此时 Outcome Unknown（结果未知）必须先 Reconcile（对账恢复），不能盲重试。

**研究成果到产品能力。** 论文模型、算法脚本、API 或 MCP 接口不能“能调就算 Skill”。目标路径是 Research Artifact（研究成果）→ Domain Capability（专业能力）→ Versioned Provider（版本化提供者）→ Conformance（契约符合性）→ Eval（评测）→ Eligibility（可用资格）。

**专业质量评测。** 模型 HTTP 200、JSON Schema 正确和 Top-K 有结果，都不是法律质量。还要看证据充分性、引用正确性、无依据主张、适用性、人工接受、恢复正确性、时延和成本。

因此，更准确的竞争关系不是“Zuno 全面替代通用平台”，而是：**通用能力优先复用；只有必须由项目承担长期事实责任、专业语义和恢复责任的部分，才值得进入 Zuno 的核心边界。**

## 5. Zuno 的核心差异，不是用了更多技术，而是多承担了哪些责任

很多架构介绍容易把“用了 LangGraph、GraphRAG、Milvus、Neo4j、MCP、Memory”当成差异化。但框架和中间件都可以替换，真正长期存在的是业务责任。

Zuno 当前 Target Architecture（目标架构）把核心差异收敛到几类责任上。

### 5.1 让正式业务状态和聊天记录分开

聊天记录只说明用户和模型说了什么。复杂法律工作还要知道业务上正式承认了什么。

当前目标领域内核只保留七类最小长期对象：Matter（事项）、DocumentVersion（材料版本）、Claim（主张）、Evidence（证据）、Finding（结论）、HumanDecision（人工决定）和 WorkProduct（工作成果）。这个内核故意保持小，不把所有 Event、Conflict、Dispute、LegalIssue 都立即做成永久业务实体。

原则是：只有确实拥有长期身份、生命周期、版本、审计、失效或正式准入语义的对象，才值得进入 Canonical Domain State（规范领域状态）。

### 5.2 让“知识处理完成”和“这次任务可以负责地使用知识”分开

一个向量索引任务完成，只能证明某一代派生知识做完了某件事，不等于当前任务已经可以基于“全部材料”给出完整结论。

例如 100 份材料里 98 份已经完成解析，剩下两份恰好是决定金额差异的关键附件。对“查询某一份合同第 8 条”可能已经足够，对“综合全部证据分析争议金额”就不能假装 Ready（就绪）。

这也是为什么 Knowledge Readiness（知识就绪）必须是任务级判断，而不是 `file.ready=true`。

### 5.3 让模型建议和正式业务提交分开

模型只能产生 Proposal（建议）。专业能力也只能产生候选。它们不能直接更新最终数据库状态、批准权限、执行未审批副作用、激活 PlanVersion（计划版本）或提交长期 Memory（记忆）。

正式业务提交必须经过领域规则、必要的人审和明确准入。这样即使模型输出“看起来正确”，系统也不会自动把它等同于业务事实。

### 5.4 让系统能够解释新证据为什么改变旧结果

如果 WorkProduct 依赖了材料 A v2、证据 E1 和人工决定 H1，新材料 A v3 或新正式证据 E2 出现以后，系统应该沿依赖关系判断哪些 Finding 或 WorkProduct 需要进入 stale / review-required（陈旧 / 需要复核），而不是把旧结果悄悄覆盖。

对专业系统来说，“什么时候旧结果失效”与“怎么第一次生成结果”同样重要。

### 5.5 让现实世界的不确定性有独立恢复语义

普通函数失败时，“重试”很自然；但现实副作用不一定允许这么做。

例如系统向外围系统提交一份正式结果，请求超时。本地不知道远端有没有成功。如果直接再次 POST，就有可能重复创建业务记录。Zuno 因此把 Prepare（准备动作）、Authorization / Approval（授权 / 审批）、Attempt（尝试）、EffectReceipt（效果回执）和 ReconciliationReceipt（对账回执）分开。

目标不是把 Tool Runtime（工具运行）设计得复杂，而是让“没有拿到响应”不被错误解释成“现实动作一定没发生”。

### 5.6 让复杂机制必须接受淘汰测试

Native Runtime（原生运行时）、GraphRAG、Long-term Memory（长期记忆）和 Specialist / Multi-Agent（专家 / 多智能体）都不是项目成立的前提。

如果一个通用宿主加法律能力已经能完成大部分任务，或者 GraphRAG 对特定 query class（问题类型）没有稳定收益，那么更合理的决策可能是继续复用通用宿主、缩小 GraphRAG 使用范围，甚至删除复杂机制。

Zuno 当前架构坚持的不是“复杂度越高越先进”，而是：**复杂度必须用质量、恢复、成本或安全收益证明自己。**

---

**前面讨论的是“为什么需要这些责任”，现在把抽象放回一条任务链。** 如果这些边界只能在架构图上成立，却不能解释一次真实任务怎样从材料进入、形成候选、被人工复核、正式提交、失效、恢复和交付，那么前面的设计仍然只是概念列表。

## 6. 一次复杂法律任务，从业务视角到底怎样走

理解 Zuno 最好的方法不是先背九个模块，而是看一条完整工作链。

假设法院侧用户提交一个复杂案件分析任务。系统首先需要知道这是哪个 Matter、任务允许访问哪些材料、使用哪些 DocumentVersion，以及这些材料对当前 Scope（任务范围）是否已经满足最低知识要求。如果关键附件尚未完成处理，系统应该明确缩小能力、等待或阻断，而不是悄悄用剩余材料给出“全案结论”。

进入分析以后，Knowledge（知识）层可以检索、重写检索表达、召回文本、关系或类案，并形成 EvidenceCandidate 和 CitationLineage。此时它仍然没有权力宣布“这就是正式证据”。专业 Capability（能力）可以执行事件抽取、对齐、冲突检测、证据比较或适用性分析，模型可以参与提取、推理、Critic（批判）或综合，但它们都只形成候选。

复杂任务如果需要多个步骤，Agent Runtime（智能体运行时）负责把目标拆成计划，处理依赖、并行、预算、失败、重试和必要的重规划。简单任务则不应该因为平台统一而强制进入复杂 DAG（有向无环图）计划。

当候选结果准备进入正式业务状态时，Legal Domain（法律领域）才进行正式准入。需要人工判断的地方由专业人员审核。成功以后，正式 WorkProduct 能够回到使用过的材料版本、证据、结论和人工决定，并保留历史引用。

如果后续新增证据，Domain 负责判定正式结果是否已经陈旧；Application / Integration（应用与集成）负责把这个失效事实送到外部消费者。即使某个外部系统暂时离线，也不能因为通知没送达就否认业务结果已经失效。

如果任务中还包含现实副作用，例如向外围系统提交正式结果，那么 Tool Runtime 负责独立保存动作准备、尝试、结果和对账事实；Security & Governance（安全与治理）负责当前是否允许执行、是否需要审批以及审计要求。

这条业务链最后才自然导出九个逻辑责任域。九模块不是为了画一张更漂亮的架构图，而是为了让每一种长期事实和故障都有唯一权威 Owner。

## 7. 三种产品形态都应该被允许，而不是强迫所有任务进入完整 Zuno

从 Build / Buy / Reuse（自建 / 采购 / 复用）角度，Zuno 至少应该允许三种合理形态。

**形态 A：通用宿主 + 法律 Skills / Capabilities。** 如果任务主要是简单问答、轻量检索和少量专业能力，通用平台已经足够，Zuno 不需要接管完整运行时和领域状态。

**形态 B：通用宿主 + Zuno Legal Backend。** 通用宿主继续负责 UI、会话和基础 Workflow，Zuno 负责材料版本、专业能力、正式领域状态、恢复和法律评测。这很可能是很多企业或法院系统更现实的集成方式。

**形态 C：Zuno Native Runtime + 一等领域状态。** 只有复杂任务确实需要动态计划、可恢复多步骤执行、安全并行、人工中断、持续授权和更强的运行控制时，才值得使用完整原生运行时。

三种形态不是“初级版、中级版、高级版”的价值排序。真正应该比较的是任务质量、故障恢复、人工接受率、时延、Token、成本和维护复杂度。如果 B 已经满足业务需求，C 反而可能是过度设计。

## 8. 什么情况下完整 Zuno 反而不值得使用

一个成熟架构必须能说清自己什么时候不应该被使用。

如果任务是一问一答、材料范围稳定、不需要长期领域状态、不发生高风险副作用、结果不需要正式准入，也没有跨天的失效和重评要求，那么通用 RAG 或通用 Agent 平台很可能更简单、更便宜、更容易维护。

如果 GraphRAG 对特定任务没有比 Hybrid Retrieval（混合检索）带来稳定收益，就不应该因为项目名字里有 GraphRAG 而默认启用。

如果长期 Memory 没有在真实任务中证明对连续工作有价值，短期上下文和显式 Domain State 可能已经足够。

如果 Specialist Agent 相比普通并行 Step / Subgraph 没有稳定提升，就不应该额外建设产品级自治 Multi-Agent Runtime。

如果九个逻辑模块被直接翻译成九个微服务，而没有独立扩缩容、故障隔离、团队边界或部署需求，那也是把逻辑边界错误地变成物理复杂度。

这些“可以删掉什么”的判断，是当前架构的重要组成部分。

## 9. 项目是怎样发展到今天的

现阶段能够恢复的历史主线是：

```text
已有产品和代码
  → Agent / Memory / Tool 等方向继续开发
  → Internal Demo
  → 客户侧 / 智慧法院项目组 Demo
  → 客户反馈：回答质量需要提高
  → 后续迭代
  → Court-side Testing
  → Pilot Validation
```

### 9.1 我加入时，项目不是从零开始

我约在 2026 年 3 月加入。加入时项目已经有代码和一个比较简单的自研前端，因此这不是 Greenfield（从零新建）项目，也不能把项目前期的产品方向和第一版系统全部算作个人成果。

这个起点反而更接近真实工程工作：先理解已有系统和数据，再在不破坏现有链路的情况下接入新能力、调试问题和继续迭代。

历史第一条需求、最早提交、第一版正式产品名称和当时完整技术栈尚未恢复。今天 `main` 的目录和依赖只能证明当前仓库，不能自动成为历史版本说明。

### 9.2 Internal Demo 说明“链路跑起来”，不说明质量已经验收

Internal Demo 是目前能够恢复的第一个重要阶段。它说明已有产品和能力曾经被项目组用于内部演示和迭代验证，但具体日期、参与人、环境、演示脚本和每项能力的完成程度还没有恢复。

因此这一阶段可以说“产品链路进入内部验证”，不能写成“已经达到某个准确率或正式质量门槛”。

### 9.3 客户侧 Demo 暴露了回答质量问题

之后项目进行过客户侧或智慧法院项目组 Demo。已经能够确认的一条反馈是：**回答质量还需要提高。**

目前没有材料支持把根因直接归到 Prompt、Retrieval、Model、Memory、Tool、引用或数据处理中的任何一个。也没有恢复前后准确率、Bad Case 集合或具体修复指标。

这段历史最值得未来继续取证。真正有价值的技术复盘应该能够恢复成：

```text
客户看到什么错误
→ 团队怎样复现
→ 根因在哪一层
→ 为什么采用某个修复
→ 修改了什么
→ 用什么样例 / 指标验证
→ 是否引入新的副作用
```

在这条链恢复以前，不能为了让项目故事更精彩而补写“通过 GraphRAG 或 Prompt 优化把准确率提升了 X%”。

### 9.4 法院侧测试比 Demo 更接近真实工作，但仍然不是 Production

客户反馈之后，项目继续迭代，随后进入法院侧人员测试。这个阶段说明系统曾经进入真实业务侧验证，但测试题数量、参与法院、人员角色、参考答案、Reviewer 协议、环境和性能数据都还没有恢复。

真实人员参与的价值在于暴露专业术语、材料表达、引用习惯、权限和工作流程问题；要把这些经验升级成可比较证据，还需要统一任务集合、评价规则和版本信息。

### 9.5 Pilot Validation 是试点，不是生产资格

项目后来进入 Pilot Validation。当前可以确认“走到过试点验证”，但没有资料支持正式 Production、稳定用户规模、部署 Endpoint、SLA、QPS、Latency、Token、Cost、HA 或 DR。

Pilot 真正值得恢复的问题包括：部署在哪里，谁使用了多久，处理什么任务，什么数据允许外发，发生过什么故障，怎样回滚，是否有人审兜底，以及用什么标准判断试点成功。

在这些证据出现以前，“进入 Pilot”与“Production Ready”必须继续严格分开。

## 10. 团队是什么形态，我在里面做了什么

目前能够恢复的核心研发规模约为 7–8 人。一名学硕学长承担主要技术负责人和任务协调角色，并把我带入项目。现有材料不足以把他定义成 CTO、总架构师或合同负责人，也不足以恢复每个方向的正式 Owner。

团队涉及 Agent、Knowledge / Retrieval、法律智能能力、Memory / Context、Tool Integration、后端、前端、测试和部署等方向。它更像一个研究成果工程化过程中形成的小型研发团队：成员会跨越算法、Agent、知识、后端和业务联调边界，而不是每个人只维护一个完全独立的服务。

目前可以明确描述我参与过的方向有：

- 部分 Agent 开发；
- Memory 相关的第一批重要工作；
- OpenViking 在 Memory / Context 区域的接入；
- Tool Calling Strategy 相关开发；
- 进入数据库查看或调试实际数据。

开发期间我也学习和接触过 LangGraph、GraphRAG。这能够说明为了推进相关工作理解过这些技术，但不能据此说完整 Agent Runtime、整个 GraphRAG、全部 RAG 或整个后端都是我独立实现的。进入数据库查看和调试数据，也不等于负责数据库总体设计。

这里需要刻意区分四种强度：**接触过、参与过、负责过、主导过。** 当前能够稳定证明的是方向级参与；任务级输入输出、具体代码、Bug、测试和结果仍需要继续从历史提交、任务记录或个人回忆中恢复。

同样，今天仓库里的总体架构、九模块文档、ADR 和文档治理经过后续系统化整理。它们可以证明我今天能够深入理解和维护这套 Target Architecture，但不能倒推“2026 年 3 月加入时，我就是整套总体架构的历史 Owner”。

如果面试官问“这个项目是不是你从零搭的”，准确回答应该是：项目已经存在，我是在已有系统基础上参与 Agent、Memory / Context、Tool Calling 和调试等工作；现在又对整个架构进行了系统化整理和深入理解。历史个人贡献与今天的架构维护能力应该分开讲。

## 11. 项目事实、当前实现和目标架构必须分成三条线

Zuno 的文档体系故意不把所有“听起来像事实”的句子放在一起。

### 11.1 History：历史项目事实

历史事实回答项目为什么出现、经历过什么、谁参与过什么。来源主要是项目材料、历史代码 / 提交、会议或 Demo 记录和明确回忆。

例如“经历过客户侧 Demo”“客户反馈回答质量需要提高”“进入过 Pilot Validation”“我参与过 OpenViking 接入”属于历史层。

### 11.2 Current：今天仓库和运行证据

Current 只能由当前 `main` 的代码、Migration、测试、Trace、Eval 或真实运行证明。

当前仓库存在 Python 后端、Web / API、Agent、Knowledge / Retrieval、Memory、Capability / Tool、数据库和测试入口；Observability 也已有 Contract foundation 和 Adapter / Test 基础。但“代码目录存在”不等于九模块 Target 已完整实现，更不等于 Production Ready。

具体 Current 必须回到 [`docs/evidence/`](../evidence/README.md)。

### 11.3 Target：今天接受的目标设计

Target 说明今天认为系统应该怎样设计，例如九个逻辑责任域、七对象最小领域内核、Knowledge Readiness、Single Controller（单控制器）、Formal Admission（正式准入）、Effect Recovery（外部效果恢复）和持续授权。

这些设计可以解释未来实现应该怎样收敛，却不能反过来声称历史 Pilot 已经拥有这些机制。

### 11.4 Unknown：不知道就是不知道

下面这些目前仍然没有可靠恢复：

- 历史第一版正式产品名称和第一条需求原文；
- 直接合同甲方、项目编号和完整参与法院名单；
- 22 家法院体系中到底哪些法院实际参与；
- 历史完整用户角色和权限模型；
- 每篇论文 / 专利具体进入了哪个产品版本；
- 历史实际使用过的完整技术栈；
- 客户“回答质量需要提高”的根因和修复指标；
- Pilot 的真实用户数、任务量、运行时间、部署环境和评价协议；
- 历史 QPS、Latency、Token、Cost、HA、DR；
- 我参与任务的具体 PR、Commit、接口、SQL、Bug 和测试闭环。

保留 Unknown 不会降低项目可信度。相反，在高级面试里，能够清楚区分事实、推断和目标，通常比给每个空白补一个听起来合理的故事更可信。

更严格的事实台账见 [`docs/governance/project-fact-provenance.md`](../governance/project-fact-provenance.md)。

## 12. 相比通用方案，我们今天到底证明了什么

这一章需要非常克制，因为“设计差异”最容易被说成“产品优势已经被证明”。

当前能够说的是：Zuno 的 Target 在几类通用宿主通常需要项目自行补充的法律业务语义上建立了明确责任，包括正式领域状态、材料版本和知识就绪、候选与正式证据分离、正式准入、历史引用、新证据失效传播、现实副作用恢复、研究成果工程化和法律质量评测。

当前**不能**无条件说：

- Zuno 比 Dify、Coze 或其他通用平台准确率更高；
- Zuno 的 Native Runtime 已经证明对所有任务更稳定；
- GraphRAG 已经证明明显优于 Hybrid / Vector / BM25；
- Multi-Agent 已经证明优于 Single Controller + 并行 Step；
- 长期 Memory 已经证明必须默认开启；
- Pilot 已经证明生产资格；
- 架构文档完整就说明实现已经完整。

真正需要的对照是至少比较三种形态：通用宿主 + 法律能力、通用宿主 + Zuno 法律后端、完整 Zuno 原生运行时。比较指标也不能只有“回答看起来更好”，还要包括法律质量、引用、人工接受、故障恢复、时延、Token、成本和维护复杂度。

如果最终测量证明某个复杂机制没有稳定收益，架构允许删除或降级它。这一点不是项目“失败”，而是工程收敛。

## 13. 如果我是大厂面试官，我会继续追问什么

这篇 Project 文档负责把项目级问题讲完整，但它不应该复制一套新的模块规格。真正高质量的面试准备是知道每个问题应该进入哪一层。

### 13.1 “为什么值得立项？”

先回答本项目的两条来源：法院侧法律智能化需求 + LIPLAB 长期研究资产；再解释研究成果进入长期业务需要工程层。不要用“Agent 很火”作为理由。

### 13.2 “为什么不用 Dify / Coze？”

先承认通用平台很有价值，再说明 Zuno 不重复建设通用宿主，而是只长期负责材料版本、正式领域状态、失效、Effect Recovery 和专业 Eval 等业务语义。最后主动说这些差异仍需 A/B 证明价值。

### 13.3 “为什么不是普通 RAG？”

用一条复杂法律任务说明：普通 RAG 能找到文本，但不能自然回答正式材料版本、候选和正式证据、人工决定、新证据失效、领域提交恢复和外部副作用。

Knowledge / RAG / GraphRAG 的深入问题进入 [`03 Knowledge & Evidence`](../modules/03-knowledge-evidence.md)。

### 13.4 “为什么用 Agent / LangGraph？”

不要说“因为 Agent 更智能”。回答复杂任务需要多步骤依赖、预算、并行、工具、人工中断和可恢复控制；简单任务仍然可以保持单步。LangGraph 提供 Send、Reducer、Checkpointer、Subgraph 等运行原语，但业务 Ownership 不是框架决定的。

深入问题进入 [`04 Agent Runtime & Control`](../modules/04-agent-runtime-control.md)。

### 13.5 “你们是 Multi-Agent 吗？”

产品上可以有多个专业 Agent，但单次 AgentRun 默认仍是 Single Controller。Specialist Agent 可以作为某个 Step / Subgraph 的执行方式，不拥有计划激活、正式领域提交、权限审批或最终发布权。

### 13.6 “文件上传以后为什么不能直接问？”

因为 DocumentVersion、KnowledgeGeneration 和 task-level Readiness 是不同语义。文件已上传、向量已写入，也可能因为 OCR 失败、旧 generation 仍在 Serving 或当前任务要求更高而不能宣称全范围 Ready。

### 13.7 “模型怎么把结论写数据库？”

模型不直接写正式业务状态。模型和 Capability 先产生 Proposal；Domain 进行正式准入，必要时经过 HumanDecision，并以同一领域事务里的 AdmissionReceipt 证明指定 run / plan / step 确实导致了正式提交。

深入问题进入 [`02 Legal Domain & Work Product`](../modules/02-legal-domain-work-product.md)。

### 13.8 “Domain commit 成功，Checkpoint 失败怎么办？”

不能把 Runtime Checkpoint 当业务真相。正式提交需要回查匹配的 AdmissionReceipt；如果领域提交已经成功，用 Domain durable fact 修复 Runtime control state，而不是重复提交业务事实。

### 13.9 “Tool 调用超时为什么不能直接重试？”

只读查询通常可以按策略重试；有现实副作用的操作可能已经远端成功但响应丢失，所以要进入 Outcome Unknown 并 Reconcile。深入问题进入 [`06 Tool Runtime & Effects`](../modules/06-tool-runtime-effects.md)。

### 13.10 “Retry、Replan、Reconcile 有什么区别？”

Retry：计划仍然正确，只是执行失败；Replan：原计划的假设、依赖或能力边界已经失效；Reconcile：现实世界的副作用结果未知，需要确认到底发生了什么。三者不能用一个“重试次数”字段解决。

### 13.11 “为什么模型不能做安全判断？”

模型适合产生 Proposal，不适合做权限、Approval、Schema Validation 或 Secret access 的最终权威判断。确定性 Security Gate、Approval Gate、Citation Check 和 Test 应尽量由非模型能力完成。深入问题进入 [`08 Security & Governance`](../modules/08-security-governance.md)。

### 13.12 “Trace 能不能当审计记录？”

不能。Trace / Telemetry 用于诊断和观测；高风险动作的 Mandatory Audit、Authorization / Approval、EffectReceipt 和 AdmissionReceipt 是耐久业务 / 安全事实。LangSmith 或 OpenTelemetry 失败不能抹掉已经发生的业务事实。

深入问题进入 [`09 Observability & Evaluation`](../modules/09-observability-evaluation.md)。

### 13.13 “为什么不是九个微服务？”

九个模块是逻辑责任域，不是部署拓扑。默认物理形态仍可以是模块化 Python 后端加必要 Worker；只有独立扩缩容、故障隔离、团队边界或安全部署需求被证据证明以后，才值得网络拆分。

### 13.14 “你本人到底做了什么？”

回到本文件第 10 章，只说目前能确认的方向级参与。不要把今天能够解释整个架构，倒写成历史上独立实现整个系统。

### 13.15 “你说这些已经实现了吗？”

停止讲 Target，直接进入 [`docs/evidence/`](../evidence/README.md)。如果 Evidence 只能证明 Contract foundation、Adapter、Mock Test 或局部运行路径，就只能说到那个程度。

## 14. 下一步最值得补的不是更多架构名词，而是真实工程闭环

Project、Architecture 和九模块现在已经能够覆盖大量系统设计问题。继续提升项目可信度，最有价值的是恢复少量高质量历史证据。

第一类是**质量闭环**。找到一到两个真实 Bad Case，恢复原始输入、错误表现、复现方法、根因、修改、回归测试和前后指标。这样才能把“客户反馈回答质量需要提高”变成一个真正可以深挖的工程案例。

第二类是**个人任务闭环**。从 Agent、Memory / OpenViking、Tool Calling 或数据库调试中恢复一到两个任务：原需求是什么，我负责哪部分，输入输出是什么，关键接口怎么设计，遇到什么异常，怎么测试，结果怎样。

第三类是**Pilot 闭环**。恢复环境、参与人员、任务量、运行时长、评价方式、真实故障、数据外发限制、人工兜底和验收条件。它能帮助判断历史项目究竟离 Production 有多远。

第四类是**对照测量**。以后用统一数据集比较 Generic Host + Legal Skills、Generic Host + Zuno Legal Backend 和 Zuno Native Runtime；对 GraphRAG、Memory、Specialist Agent 做消融实验。这样“架构假设”才能逐步升级为“工程证据”。
