# Zuno 产品定位、立项逻辑与差异化

这篇文档回答一个比“Zuno 用了什么技术”更重要的问题：**既然已经有通用大模型应用平台、工作流平台、RAG 框架和 Agent 宿主，为什么还值得单独建设 Zuno？**

答案不能是“因为法律场景更复杂”，也不能是“因为我们用了 LangGraph、GraphRAG 或 Multi-Agent”。技术框架不是立项理由。Zuno 能否成立，取决于三个条件是否同时存在：业务侧确实有一类长期、专业、可审计的法律智能工作；团队拥有能够转化为产品能力的领域研究资产；通用宿主虽然能解决模型调用、会话、工作流和基础检索，却不天然替项目承担法律业务事实、证据关系、正式成果和恢复语义。

这里还必须区分两件事。**“为什么值得做”是产品与架构判断；“是否已经证明比通用方案更好”是测量问题。** 当前文档可以说明 Zuno 设计上要多解决什么，但不能在没有正式 A/B、真实法院质量指标和生产证据时，把这些差异直接写成已经测量成立的优势。

## 1. Zuno 的立项不是从“我们想做 Agent”开始

项目背景已经能够确认两个来源：一端是天津法院智慧平台相关场景中的法律智能化需求，另一端是南京大学软件学院 LIPLAB 和葛季栋团队长期积累的智慧司法研究成果。两者叠加，才形成了 Zuno 的产品起点。[项目背景](./project-background.md)记录历史来源，[项目事实来源说明](../governance/project-fact-provenance.md)约束这些事实能说到什么程度。

如果只有算法，没有真实业务需求，最自然的结果可能是一组论文、Demo 或研究原型；如果只有业务需求，没有领域积累，也可能直接采购或组合成熟通用平台。Zuno 的立项空间出现在两者之间：团队已经有事件抽取、事件对齐、冲突检测、证据链、类案、法条推荐、法律评测等研究背景，而法院侧工作又要求这些能力最终能够进入真实材料、专业人员和业务系统组成的工作链。

因此，Zuno 真正要工程化的不是“聊天能力”，而是**研究成果怎样变成稳定、可组合、可验证的专业能力，并且在真实法律工作里留下可追溯结果。** 这也是为什么当前架构把 Research-to-Capability（研究成果到专业能力）作为 05 专业能力模块的重要方向，而不是把论文模型直接暴露给上层。

## 2. 为什么普通问答并不足以覆盖目标工作

对“合同第 8 条写了什么”这类问题，受控检索加模型生成往往已经足够。Zuno 的总体架构甚至明确要求这类任务保持简单，不应为了平台形式统一而强制进入复杂原生运行时。

真正让项目值得独立设计的是另一类任务。一个事项可能有原告材料、被告材料、补充协议、扫描件、沟通记录和后续新增证据；同一材料还有多个版本。模型找到了一段相似文字，不代表它就是正式证据；模型提出了一个结论，也不代表业务上已经承认。专业人员可能修改或拒绝模型建议，结果发布以后还可能因为新证据变得需要复核。

如果系统还要向法院外围系统提交结果，问题会再多一层：一次 POST 超时以后，现实世界可能已经发生了动作，只是本地没有拿到响应。此时“失败就重试”会带来重复副作用。

这些问题不是模型能力本身能解决的。它们要求系统长期保存并回答：

- 当前任务依据的是哪一版材料；
- 当前材料对这一次任务是否真的已经可用；
- 检索结果为什么被找到，正式结果最终又真正采用了什么依据；
- 候选证据和正式证据之间谁负责做业务准入；
- 一个正式结论依赖哪些材料、证据和人工判断；
- 新证据来了以后，旧结果哪些地方需要重新评估；
- 系统崩溃以后，运行检查点和正式业务提交谁更能证明事实；
- 外部动作结果未知时怎样避免重复执行；
- 权限变化以后，长任务后续步骤还能不能继续；
- 复杂机制究竟是否真的提高质量、恢复性或成本效率。

这组问题共同构成 Zuno 的产品边界。

## 3. 通用 Agent 宿主已经很有价值，Zuno 不应该重复建设它

Generic Host（通用 Agent 宿主）可以理解为已有的通用大模型应用或 Agent 承载环境。它通常可以承担用户入口、会话、任务提交、基础工作流、模型调用、RAG、工具调用、页面交互和部分运行观测。实际项目也完全可以把 Zuno 嵌入已有法院系统或通用宿主，而不是强迫所有用户换成 Zuno 自己的 UI。

这点非常重要，因为“通用平台已经存在”不是 Zuno 的反例，反而帮助项目缩小自建范围。一个成熟宿主如果已经能够稳定解决入口、会话、权限接入、基础 RAG 或工作流，Zuno 应优先复用，而不是再造一套通用平台。

所以面对“为什么不用 Dify、Coze 或其他通用工作流 / Agent 平台”的问题，最稳妥的回答不是说这些平台做不到。更准确的说法是：**如果任务只是普通问答或通用流程，它们可能已经足够；Zuno 只在需要自己拥有法律领域事实、证据版本、正式成果、失效传播、外部效果恢复和专业评测时，提供独立的法律后端语义。**

换句话说，Zuno 与通用宿主不是天然竞争关系。很多部署形态下，通用宿主可以在上面，Zuno Legal Backend（法律后端）在下面。

## 4. Zuno 真正试图多拥有的，是法律工作链中的“业务语义”

### 4.1 正式领域状态，而不是只有聊天记录

通用会话历史能够保存“用户和模型说了什么”，但复杂法律工作需要保存“业务上正式承认了什么”。Zuno 的目标领域内核只保留 Matter、DocumentVersion、Claim、Evidence、Finding、HumanDecision 和 WorkProduct 七类最小长期对象。

它们的价值不在于对象数量，而在于让工作成果能够长期回到材料版本、正式证据、专业结论和人工决定。模型、检索、Capability 或 Agent 都只能先产生候选，不能直接把候选写成正式业务事实。

### 4.2 材料版本和知识就绪，而不是“文件上传成功就算可用”

企业知识库和法律材料系统经常遇到一个隐蔽问题：文件已经上传，向量也已经写入，但关键附件 OCR 失败、某个旧版本仍在 Serving，或者这次任务要求的表格和跨文档关系还没有处理完成。

因此 03 知识与证据把 DocumentVersion、KnowledgeGeneration 和 task-level ReadinessDecision 分开。这里保护的是“这一次任务现在能不能负责地使用这些材料”，而不是某个索引任务有没有返回 success。

### 4.3 候选证据、检索引用和正式历史引用分层

检索模块可以解释一段材料为什么被找到，这属于 CitationLineage（检索引用链）；正式 WorkProduct 则需要长期保存当时真正采用的不可变材料版本和稳定位置，这属于 WorkProductCitationBinding（工作成果历史引用绑定）。

两者不能合并。向量库、切分器、GraphRAG、Embedding 或 Reranker 可以重建和替换，已经正式形成的工作成果不能因此失去自己的历史依据。

### 4.4 正式准入，而不是“模型输出就是结果”

Zuno 的核心边界之一是 Formal Admission（正式准入）。专业能力和模型可以形成 Proposal / Candidate，人工可以审核，但只有 02 法律领域真正完成领域事务并产生 matching AdmissionReceipt（匹配的正式准入回执）以后，运行时才有资格把需要正式业务提交的 Step 视为完成。

这让“模型生成成功”“运行节点结束”“正式业务结果成立”成为三个不同层级，系统崩溃时也能恢复。

### 4.5 新证据失效传播，而不是静态回答

一个法律答案在生成时正确，不代表三天后新增证据以后仍然正确。Zuno 目标上把 WorkProduct / Finding 的依赖关系保存下来，新正式证据进入以后，可以让受影响结果进入 stale / review-required 类状态，并做有界重新评估。

这类生命周期是面向长期专业工作的，而不是只面向一次聊天响应。

### 4.6 现实副作用恢复，而不是普通函数重试

如果一个 Tool 只是只读查询，失败通常可以安全重试；如果它向外围系统提交正式结果，超时就可能意味着“已经执行但响应丢失”。06 工具运行因此把 Action Proposal、PreparedAction、ToolAttempt、EffectReceipt 和 Reconciliation 分开，并明确 Outcome Unknown 禁止 Blind Retry（盲重试）。

这类能力不是为了“让 Agent 更复杂”，而是为了保护真实业务世界不被重复动作破坏。

### 4.7 法律质量评测，而不是只看模型接口成功率

模型 API 返回 200、JSON Schema 正确、检索 Top-K 有结果，都不能证明法律工作质量。09 评测要进一步看证据充分性、引用正确性、无依据主张、适用性、人工接受、恢复正确性，以及实现这些质量花了多少时延、Token 和成本。

同时，Native Runtime、Long-term Memory、Specialist / Multi-Agent 和 GraphRAG 都必须接受消融或对照实验。如果没有稳定收益，就应该删除、降级为 Optional 或继续交给通用宿主。

## 5. 因此，“相比通用平台的优势”必须拆成设计差异和已证明优势

面试或架构评审里最容易出现过度表述的是：“Zuno 比通用平台更专业、更稳定、更准确。”目前证据还不足以支持这种无条件结论。

更准确的表达是：Zuno **设计上试图在以下维度提供更强的法律业务语义**：

| 维度 | 通用宿主通常需要项目自行补充的内容 | Zuno Target 负责的内容 | 当前是否已证明优势 |
| --- | --- | --- | --- |
| 正式业务状态 | 项目自定义 | 七对象最小领域内核、版本和正式准入 | 设计已明确，质量优势未测量 |
| 材料可信使用 | 项目自定义 readiness | DocumentVersion + KnowledgeGeneration + task-level Readiness | 设计已明确，真实规模收益未测量 |
| 引用长期可追溯 | 项目自行保存 | 检索引用链与正式历史引用绑定分层 | 设计已明确，长期运行证据不足 |
| 新证据影响 | 项目自定义 | 领域失效真相 + 发布失效传播 + 定向重评 | 设计已明确，真实 Pilot 数据未恢复 |
| 人工专业判断 | 项目自行建模 | HumanDecision 与安全 Approval 分离 | 设计已明确，实际采用率未证明 |
| 外部副作用恢复 | 项目自定义幂等 / 对账 | PreparedAction / EffectReceipt / Reconcile | 有部分 Current 基础，生产闭环未建立 |
| 研究成果工程化 | 项目自行封装 | Research Artifact → Capability → Conformance → Eval → Eligibility | 目标路径明确，完整 E2E 未证明 |
| 法律质量评测 | 项目自行建设 | 法律 Eval + Release Evidence + Complexity Kill Test | 框架基础存在，正式 benchmark 仍受阻 |

所以这里应该说“**差异化设计**”或“**价值假设**”，而不是直接说“已经验证的竞争优势”。真正把这些差异升级为优势，需要 09 可观测性与评测给出可以复现的测量证据。

## 6. 最合理的产品形态不是只有一种

Zuno 当前最值得保留的是三种可以被比较的形态，而不是先宣布“自研完整平台一定最好”。

### A. 通用宿主 + 法律 Skills

适合简单问答、流程短、长期业务状态要求低的任务。优点是复用最多、交付快、平台成本低。若这一层已经满足业务，就没有理由引入完整 Zuno Runtime。

### B. 通用宿主 + Zuno 法律后端

通用宿主负责入口、会话和通用编排，Zuno 负责材料版本、知识就绪、专业 Capability、正式领域状态、引用、失效、安全和 Effect 语义。这很可能是很多法院或企业系统更现实的嵌入形态，因为它既保留现有产品入口，又获得 Zuno 的专业后端语义。

### C. Zuno 原生运行时 + First-class Domain State（一级领域状态）

只有复杂任务在动态计划、安全并行、Interrupt / Resume、Step Acceptance、Replan、复杂恢复等方面持续获得明显收益时，才有理由扩大原生 Runtime 的使用范围。

这三种形态应该通过同一数据、任务和预算做 A/B/C 对照，而不是靠架构偏好决定。当前 Native Runtime 的必要性仍然属于 measurement-gated（测量门控）问题。

## 7. 为什么 Zuno 不应该把所有“高级能力”都默认做进去

一个平台很容易因为 Agent、Memory、GraphRAG、多智能体、知识图谱、Sandbox、微服务看起来先进，就逐渐把它们全部变成默认依赖。Zuno 当前架构采取相反原则：**删除优先于增加，复用优先于自建，测量优先于长期保留。**

- 简单检索够用时，不因为有 GraphRAG 就强制走图检索；
- 单控制器 + 并行 Step 能解决时，不建设自治 Multi-Agent Runtime；
- Working / Session Context 已够用时，不默认提交长期 Memory；
- 同进程模块边界能保持 Ownership 时，不因为有九个逻辑模块就拆九个微服务；
- 通用宿主已经解决入口和基础编排时，不重新造一个通用宿主；
- 成熟 Provider 已经可靠解决通用能力时，通过 Adapter / Port 复用，而不是重写底层基础设施。

这也是面试中回答“你们为什么没有直接上更复杂方案”时最重要的一条设计原则：**复杂度本身不是能力，只有可测量的收益才是能力。**

## 8. 面对“为什么可以立项”的一个完整回答框架

如果需要在评审或技术面试中用几分钟回答，可以按四层展开：

第一层是业务来源：法院侧存在法律智能化工作需求，LIPLAB 同时拥有长期智慧司法研究积累，因此项目不是为了追逐 Agent 概念临时包装出来的。

第二层是产品缺口：通用宿主能够很好地承载大模型、RAG、工作流和工具，但复杂法律工作还需要项目自己拥有材料版本、证据关系、人工决定、正式成果、失效传播和外部效果恢复等业务语义。

第三层是架构策略：Zuno 不排斥通用平台，而是把自己收缩成法律后端和必要的原生 Runtime；简单任务继续走简单路径，复杂机制全部受证据门控制。

第四层是证据边界：目前可以证明项目背景、Pilot 阶段和一部分工程实现，但还没有正式 A/B 证明 Zuno 在真实法院任务上全面优于通用方案，因此把“设计差异”与“已测优势”分开表述。

这四层比“因为法律场景需要 Agent”更经得起追问。

## 9. 什么时候不应该选完整 Zuno

一个架构真正可信，还要能够说明什么时候不该用自己。

如果任务只有一次性问答、不要求长期正式领域状态、不涉及新证据失效、不需要高风险外部副作用、通用宿主已经满足权限与引用要求，那么完整 Zuno Runtime 很可能是过度设计。

如果团队无法维护正式领域模型、恢复语义和法律 Eval，只是想快速交付知识库问答，也应优先选择成熟通用平台，而不是复制 Zuno 的复杂架构外形。

如果法院侧已有成熟宿主和门户，Zuno 也不应该为了“产品完整”强制替换现有入口。更合理的是把专业能力和领域后端通过稳定 Contract 嵌进去。

这意味着 Zuno 的核心竞争力假设并不是“我们什么都自己做”，而是**知道哪些法律业务语义必须自己拥有，哪些通用能力应该交给成熟平台。**

## 10. Current、Target 和待证明问题

**已经有事实支持的部分**：项目来自 LIPLAB 智慧司法研究与天津法院相关合作背景；方向从立项上就包含法律智能平台、多专业 Agent 和研究成果工程化；项目经历了 Demo、法院侧测试和 Pilot Validation；当前仓库存在 Agent、Knowledge、Capability / Tool、Model、Security、Observability 等有限实现与测试基础。

**当前 Target 已经明确的部分**：九个逻辑责任域、七对象最小法律领域内核、知识就绪、正式准入、历史引用绑定、持续授权、外部效果对账、角色化模型网关、研究成果到 Capability、法律 Eval 和证据门控复杂度。

**仍然不能宣称已经证明的部分**：真实法院任务上的质量优势、GraphRAG 收益、长期 Memory 收益、Specialist / Multi-Agent 收益、原生 Runtime 相比通用宿主的净收益、真实生产规模、SLA / QPS / HA / DR、安全资格、正式 Benchmark 和 Production Readiness。

如果后续取得真实数据，这些问题应进入 [`docs/evidence/`](../evidence/README.md) 和 09 评测，而不是回头把 Target 文档改成“我们一直都已经做到了”。
