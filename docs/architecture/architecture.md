# Zuno 目标架构：从一条法律任务的失效过程理解系统边界

法律智能系统的架构难点，往往在答案离开一次请求以后才真正暴露出来。

设想一项合同争议分析。用户上传合同、补充协议、聊天记录和几份扫描附件，希望系统梳理付款义务、违约事实和可引用的材料。第一版产品完全可以很简单：应用服务确认访问范围，RAG 找到相关文本，模型组织答案，页面展示引用。对于“合同第 8 条写了什么”这类问题，这条路径已经足够。继续增加 Agent、状态机和服务，只会增加时延、成本和故障点。

同一项工作被拉长以后，系统开始遇到另一类问题：关键材料还没有处理完，研究模型准备被新的 LLM 替换，机器结论需要专业人员修改和接纳，新证据在任务运行期间进入，正式业务提交和运行进度没有同时落盘，不同模型开始受到质量、地域和预算约束，外围系统在 POST 后超时，用户权限又在等待期间发生变化。团队还会自然地想加入 GraphRAG、Reflection 或更多 Specialist，但“能实现”本身并不能证明这些复杂机制应该长期存在。每个问题都要求系统说明：现在究竟发生了什么，哪一份记录有资格证明它，以及复杂度为什么值得保留。

下面的场景描述 Target 设计要解决的问题，不代表这些机制已经全部在 Current 代码或真实法院环境中验证。Current 的实现、测试、Trace、Eval 和运行证据只以 [`docs/evidence/`](../evidence/README.md) 为准。

## Part A — Human Narrative（人类技术叙事）

### 先看系统边界：Zuno 位于几个彼此不能互相替代的世界之间

从系统上下文看，Zuno 并不只是模型外面的一层编排代码。它夹在几类拥有不同事实来源的系统之间：用户和法院 Host 发起工作，正式材料与法律成果需要长期保留，研究算法与模型 Provider 提供可替换的计算能力，外围法院系统、邮件或第三方 API 可能被真实改变，PostgreSQL、Object Store、Queue、Checkpointer、Secret Manager 和 Observability 平台则提供底层物理机制。

这些参与者对“真相”的控制能力并不相同。外部 Host 可以告诉 Zuno 谁在发起请求，却不能凭一个传入的 role 字段决定当前授权；模型 Provider 可以返回一次计算结果，却不能宣布它已经成为正式法律事实；HTTP 客户端看到 timeout，也不能据此宣布外围系统没有执行。反过来，Zuno 即使知道自己已经发送成功，也不能替外围系统声明它内部最终如何展示或采用结果。

因此总体架构的第一条边界不是九个模块，而是**谁有资格证明哪一种事实**。Zuno 负责把这些事实放在一条长期工作链里协调起来，却不把所有状态收编进一张全局表。外部系统的现实、正式法律业务、运行控制、知识派生、安全决定和产品交付各自保留自己的 Authority；跨边界只传播足够的身份、版本、因果和完成证明。

这也决定了为什么系统设计不能从框架图开始。LangGraph、Redis、向量数据库、模型 SDK、Queue 或 Kubernetes 都可以改变；“正式结果是否成立”“材料是否足以支持当前任务”“外部动作到底有没有发生”“下一次读取现在是否仍被允许”这些问题不会因为基础设施替换而消失。

### 从普通法律问答开始

一条短请求可以沿着很朴素的路径完成。用户提出问题，应用服务确认他当前能读哪些材料，检索系统找到原文，模型在这些材料上组织回答，发布前再检查引用和当前发布条件。这里没有需要运行几十分钟的计划，没有现实副作用，也没有必须长期保存的专业工作成果。受控 RAG、成熟模型 SDK 和普通后端已经能够承担大部分责任。

这种简单方案应该继续存在。只有请求真的跨越材料准备、长期等待、人工复核、正式业务结果或现实副作用以后，后面的机制才开始有价值。简单条款定位没有理由先构造动态执行图，也没有理由因为系统支持 GraphRAG 就默认走图检索。

合同争议分析很快会越过这条边界。同一个事项可能已经有合同 v1、v2、v3，补充协议刚刚上传，关键扫描附件仍在 OCR，聊天记录又在分析过程中补入。专业人员会修改机器建议，某个工作成果可能已经交付，外围系统也可能在 Zuno 崩溃以后继续保留先前动作的结果。此时，保存“最后一次模型输出”已经无法描述这项工作。

### 材料不齐时，流畅回答也可能没有资格代表全案

用户一共上传了一百份材料。九十八份已经完成解析和索引，两份关键扫描附件还没有 OCR。页面上的上传请求全部成功，向量库里也已经有大量内容。如果后台据此宣布案件材料已经 READY，系统就可能在证据范围并不完整时生成一份非常流畅的全案分析。

缺失材料是否阻断任务取决于用户正在做什么。查询合同第 8 条，只要对应合同正文已经可用就可以继续；计算全案违约金额时，尚未处理的附件可能正好改变付款日期。系统需要知道的不只是“有没有数据”，而是当前任务所需的材料和加工结果是否已经足够。

这里自然出现两种生命周期。合同 v3 作为正式业务材料，需要拥有稳定身份；OCR、切分、Embedding、图结构和索引属于围绕这份材料建立的派生知识，可以因为算法升级而重建。新一代派生知识构建完成，也只说明这一代加工结果可以服务查询；具体任务仍要根据材料范围和需要的能力判断现在是否足够。

工程实现把可重建的一代知识称为 `KnowledgeGeneration`，把面向具体任务的“现在是否够用”判断称为 `ReadinessDecision`。这两个名字压缩的是前面的业务区别：材料身份保持稳定，知识可以重建，而就绪程度取决于任务。

材料真正可用以后，系统才有资格讨论模型和研究算法做出的专业判断。

### 同一个专业任务可以更换实现，专业含义不能跟着漂移

课题组已有事件抽取模型能够从材料中返回结构化事件。后来团队希望换成新的法律 LLM，它也能返回相似的事件 JSON。最快的接法是在工作流里替换一个 Python class，或者给两个实现各写一个 wrapper。

接口能接上以后，专业问题仍然存在。两个实现怎样划分“事件”，空结果表示确实没有事件还是处理失败，各自支持什么材料和案由，错误会以什么方式出现，旧结果与新结果能不能直接比较，都不能从 JSON Schema 推出来。如果这些差异散落在 Planner、fallback 和下游判断里，每换一次模型都会让工作流重新学习一遍专业语义。

Zuno 因而先固定“事件抽取这项专业能力对上层承诺什么”，再允许研究模型、规则、LLM 或外部服务竞争实现。工程上把稳定的专业承诺称为 `Capability`，把具体实现称为 `Provider`。新的 Provider 先证明自己遵守这份承诺，再用冻结的数据、版本和任务范围证明它适合哪些任务；健康检查成功或能够返回合法 JSON，都不足以永久获得业务资格。

这条边界让研究资产可以进入长期工程系统，同时也保留替换空间。某个论文模型停维、外部服务退出或新 LLM 更合适时，上层依赖的专业含义不必跟着实现一起重写。如果专业定义本身发生变化，系统再显式形成新的能力版本，而不是把语义变化藏在同一个接口后面。

现在，机器已经找到相关材料，也形成了一个看起来合理的违约判断。真正困难的问题从“它算得怎么样”转向“这份结果是否已经成为业务愿意长期负责的事实”。

### 机器结论进入长期业务以后，系统必须能解释谁接受了什么

模型判断付款已经逾期，并生成事实摘要。专业人员复核后发现补充协议的签署时间被写错了一天，于是修改这处事实，接受其余判断，并把结果放进正式工作成果。

如果系统只覆盖保存最后一段文字，几周后就很难回答：机器原来建议了什么，专家修改了哪里，当时采用合同 v2 还是 v3，引用的是哪一页材料，新证据进入后旧成果为什么仍然存在。一个需要交付、复核和长期追责的结果，必须保存自己的形成过程和当时成立的业务上下文。

因此，检索和模型产生的内容先保持候选身份。只有在材料版本、专业规则、必要人审和当前安全条件都满足以后，法律业务才把需要长期负责的内容接纳为正式事实和工作成果。工程上把这个提交边界称为 `Formal Admission`。它保护的是业务权威，而不是给所有模型输出机械增加审批步骤；普通一次性问答仍然可以停留在短路径上。

下午又进入一份关键补充协议，付款日期的认定随之改变。上午形成的工作成果曾经真实存在，也可能已经被交付；现在它又不适合继续代表当前结论。系统应保留旧版本当时为何成立，同时形成需要复核、失效或被新版本取代的关系。直接改写旧记录会让审计、引用和已经发生的交付失去时间一致性。

同样，今天重建索引以后，Retriever 可能找到另一段 chunk。历史工作成果仍要回到当时真正采用的材料版本和稳定位置，而不是跟着今天的索引结果漂移。正式业务事实由此拥有自己的时间线，知识派生和运行过程可以继续重建。

一旦正式提交和运行控制同时存在，下一类故障就会把两种时间线直接撞在一起。

### 崩溃和晚到结果迫使系统区分业务事实与运行进度

假设专业人员已经确认结论，业务事务也成功写入新的正式工作成果。Runtime 正准备保存下一份 Checkpoint，进程却在这几毫秒里崩溃。新的 Worker 接管以后，只能看到旧 Checkpoint。如果它把旧控制进度当成整个系统的事实，就会再次执行正式提交。

恢复时要先查询拥有业务权威的耐久记录，确认那次提交是否已经发生；已经发生就修复 Runtime 的控制进度，没有发生才重新进入当前有效的提交路径。Target 让正式准入在同一业务事务里留下一个可以重新查询的完成证明，工程上称为 `AdmissionReceipt`。Checkpoint 继续记录控制流程走到了哪里，但它不负责宣布正式法律业务是否已经成立。

这个故障决定了恢复顺序：较新的业务事实不能被较旧的运行投影覆盖。Queue、Checkpoint 和 Worker 都可以在随后修复，只要恢复过程先回到拥有正式结果的 Authority 确认现实状态。

任务运行更久以后，因果问题还会出现在并行分支上。分析开始二十分钟后，新证据进入，当前计划需要改变；旧计划里的一个分支此时才返回，而且结果本身质量很好。系统不能仅凭“计算成功”接受它，也没有必要仅凭“晚到”直接丢弃。它需要检查这份结果基于哪一版材料和计划，原来的前提现在是否仍成立，再决定继续使用、重新验收还是重做。

为了让计划切换只有一个清楚的因果顺序，Target 让一个逻辑控制者负责激活当前计划和收敛重规划；专业计算本身仍然可以并行。新的证据需要改变计划时创建新的 `PlanVersion`，旧分支回来后再按当前前提判断资格。工程上把这个逻辑写者称为 `Single Controller`。它是一种控制责任，不要求部署成单独网络服务。

长任务此时已经拥有自己的控制时间线。接下来，同一任务里越来越多的模型调用会把“选哪个模型”也从一行 SDK 参数变成需要长期解释的决定。

### 同一案件开始依赖多种模型时，模型选择也需要独立约束

Planner 需要较强的推理能力，query rewrite 更在意速度和成本，结构化抽取可能适合更小、更稳定的模型。与此同时，某些案件材料不能发送到特定地域或 Provider，主模型可能临时限流，整个任务也可能已经接近预算上限。

如果每个调用点自己写死 model name、fallback 和 retry，质量、安全、费用和供应商故障就会散落进 Planner、Knowledge 和 Capability。主 Provider 503 时，一个局部 fallback 甚至可能把原本不允许外发的材料发送到另一个区域。

更稳定的做法是让调用方描述这次调用需要什么角色和约束，再从当前允许、质量有证据支持、预算也能接受的候选中选择实际模型。工程上由 `Model Gateway` 承担这项依赖控制，并记录真实使用的 Provider / Model、Attempt 和 Usage。它不拥有 Planner 的业务 Prompt，也不决定“事件抽取”在法律上是什么意思；这些语义仍留在真正使用模型的 Runtime 和 Capability。

如果系统长期只使用一个受控模型，没有多 Provider、独立 Role、复杂外发限制和预算路由，Gateway 可以缩成普通 adapter。它的存在来自模型依赖开始拥有独立变化速度和控制条件，而不是来自“多模型架构”这个标签。

到这里，系统内部已经能解释材料、专业结果、正式业务事实、运行计划和模型调用。向外围系统产生动作以后，Zuno 还必须面对一个自己无法单方面裁决的事实。

### 网络超时以后，失败状态不足以描述现实世界

系统准备把一份正式成果提交到外围法院系统。请求已经发出，连接却在响应到达前超时。本地只知道自己没有拿到确定响应，远端可能完全没有执行，也可能已经提交成功而响应丢失。

把 timeout 直接记成 Failed 然后自动重试，会把网络不确定性变成第二次业务提交。更安全的做法是在发送前先固定这次逻辑动作的身份、内容和幂等语义；越过发送边界以后，只要远端结果还无法确认，就保留“未知”这一事实。随后利用远端幂等键、业务唯一键、查询接口或必要的人工方式确认过去究竟发生了什么，再决定是否补做、结束或补偿。

工程上，发送前固定的逻辑动作叫 `PreparedAction`，确认后的现实结果由 Effect 记录；结果未知时进入 Reconcile。重复一个仍然安全的同一计算属于 Retry，输入或前提变化以后重新安排工作属于 Replan，已经可能发生的现实动作需要先查清过去属于 Reconcile。三种处理方式来自三种不同的失败来源。

这条边界也说明为什么调用方的 HTTP 状态、Runtime 的 Step 状态和现实世界结果不能被压成一个 `failed / succeeded`。越过外部边界以后，系统只能通过远端可观察事实、幂等协议和对账逐步收敛。

### 同一项任务对外会经历多个“完成”时刻

回到最外层的法院 Host。它最先看到的是“请求已受理”；Runtime 结束以后，系统可能已经有一份可供查看的草稿，但专业人员还没有完成正式接纳；Domain 随后形成正式 WorkProduct，外部发送又要等 Effects 确认现实动作；下午新证据进入以后，已经交付的旧版本还可能立刻变成需要复核，而此时 Host 恰好离线。

如果应用入口只维护一个 `success`，这些真实发生在不同时间、由不同 Owner 证明的状态会被压成一个含糊结论。Runtime 的完成不能替 Domain 宣布正式成果已经成立，Domain 的正式提交也不能证明外围系统已经收到；一次交付成功更不能让新证据出现后的旧成果继续保持当前有效。

因此需要一个面向外部消费者的组合责任：它接收请求、稳定任务身份，把各个 Owner 已经成立的事实翻译成可查询、可发布、可交付和可失效传播的产品语义。工程上把这类责任放在 `Application & Integration`。它可以告诉 Host “现在可以看到什么、应该使用哪一版、交付观察到哪里”，但不因此成为新的全局真相源；正式业务事实仍由 Domain 证明，现实副作用仍由 Effects 证明，当前授权仍由 Security 决定。

对于一次同步问答，这层可以薄到普通应用函数和 API adapter。只有长任务、正式成果、多 Host、异步交付或失效传播真的出现时，稳定的产品生命周期才需要成为长期责任。

### 二十分钟长任务把权限也变成时间问题

任务在 10:00 启动时，用户有权读取附件 A。系统随后等待 OCR、运行检索、调用模型并进入人工确认。10:12，Matter 归属或用户权限发生变化。10:20，后台 Worker 准备重新读取正文并向外部模型发送材料。

入口处那次合法鉴权只能证明 10:00 的读取当时被允许。10:20 的新读取、模型外发、Secret 获取或高风险 Tool 调用需要消费当前的授权条件。已经发生的合法历史保持不变，未来的受保护动作则跟随新的主体、资源、用途和政策状态。

专业人员对法律结论的认可也不会替代安全审批。法律业务判断回答“这份结论是否应当成为正式工作成果”，安全与治理回答“此刻是否允许执行这次读取、外发或现实动作”。两种决定可能出现在同一个页面和同一条工作流上，但恢复与审计时拥有不同 Authority。

新材料从另一方向改变当前有效性。昨天已经正式成立的工作成果，今天可能因为新的证据需要复核。系统保留它昨天为什么成立，同时阻止它在条件变化以后继续被静默当作当前答案。长任务中的权限、新鲜度和业务有效性都随时间变化，任何一次早先的成功都不能永久替后续动作做决定。

这条案件已经解释了系统为什么越来越复杂。最后还剩一个问题：这些已经做出来的复杂机制，是否真的应该永久留下。

### 已经实现的复杂机制，仍然可能应该删除

团队可以继续加入 GraphRAG、Reflection、长期 Memory、更多 Specialist、更强模型或更完整的 Native Runtime。它们都可能解决真实问题，也都可能只是增加 token、时延、存储、协调和新的故障面。Demo 能跑、代码已经合并，最多证明机制存在，不能证明它比更简单的 baseline 更有价值。

判断需要回到可比较实验。GraphRAG 应和 Hybrid Retrieval 在同语料、同任务和可比预算下比较；Reflection、Memory 或 Specialist 可以做 on/off ablation；更贵模型需要证明质量收益足以覆盖额外成本。某个机制长期没有稳定边际收益时，架构应允许关闭它、缩小适用范围或回到 baseline。

这里还需要区分两种证据。一次 Trace 可以帮助工程师解释某个请求经过了哪些 Step、模型和 Tool，却不能单独证明法律业务已经正式提交，也不能证明远端 Effect 真的发生。业务真相继续由对应责任域保存；Observability 负责把执行时间线关联起来，Evaluation 负责把质量、恢复、时延、成本和关键失败放进可重复的比较中。

工程上，这两类责任共同进入 `Observability & Evaluation`。它的价值之一就是给架构提供删除机制：复杂度没有因为“已经实现”获得永久席位，保留与否继续接受证据约束。

走完这条案件时间线以后，九类长期责任已经都有了具体来源。此时再给它们命名，比在第一页背模块表更容易理解。

### 这些反复出现的冲突才形成九个责任域

当前 Target 把这些长期事实分给九个逻辑责任域。这里的“九”来自已经接受的责任划分，不表示系统应该部署成九个进程、九个数据库或九个网络服务。

| 责任域 | 它长期回答的问题 |
| --- | --- |
| **01 Application & Integration** | 外部请求怎样被接收、发布、查询和交付，多个 Owner 的事实怎样组合成稳定产品行为 |
| **02 Legal Domain & Work Product** | 哪些材料和专业结果已经成为正式业务事实，历史版本和失效关系怎样保存 |
| **03 Knowledge & Evidence** | 正式材料怎样变成可重建知识，当前任务是否准备好，检索候选从哪里来 |
| **04 Agent Runtime & Control** | 长任务当前按哪个计划运行，哪些 Step 可以执行，等待、取消、Replan 和恢复怎样收敛 |
| **05 Capability & Skill** | “事件抽取、冲突识别、类案检索”等专业能力承诺什么，哪些实现当前有资格提供它 |
| **06 Tool Runtime & Effects** | 系统准备让现实世界发生什么，实际发出过什么，结果未知时怎样对账 |
| **07 Model Gateway** | 某次模型调用为什么选择这个 Provider / Model，真实调用和 Usage 是什么 |
| **08 Security & Governance** | 当前这一刻能不能继续读、外发、取 Secret、审批或执行受保护动作 |
| **09 Observability & Evaluation** | 一次执行发生了什么，以及某层复杂度是否通过可重复实验证明值得保留 |

这些边界先划分谁拥有哪类事实，再决定代码和部署怎样组织。默认实现可以是模块化 Python 后端，只有吞吐、资源、Secret 隔离、网络出口、故障半径、合规或部署生命周期形成真实约束以后，某些责任才值得拆成独立 Worker、进程或网络服务。

PostgreSQL、Object Store、Queue、Checkpointer、Secret Manager、身份系统、OpenTelemetry 和模型 SDK 等成熟基础设施优先复用。它们提供事务、存储、队列、身份、观测和调用机制；Zuno 只需要长期拥有基础设施无法替法律业务决定的语义，例如什么正式成立、哪些材料足够支持当前任务、旧计划是否仍适用、外部动作是否真的发生，以及下一次受保护操作现在是否仍被允许。

责任域只回答“谁负责哪类事实”。真正的总体架构还必须继续回答这些事实怎样被存储、怎样跨同步与异步边界传播、出现局部失败时怎样收敛，以及负载上升以后怎样扩容。

### 不同状态拥有不同恢复价值，不能被一张全局状态表压平

Zuno 同时维护几类性质不同的状态。正式材料、正式 Evidence、Finding、HumanDecision、WorkProduct 和 AdmissionReceipt 属于长期业务历史，一旦成立就不能因为 Worker 重启或索引重建而丢失。围绕材料构建的 OCR、chunk、embedding、graph 和索引是派生知识，可以从稳定材料与 ProcessingSpec 重新生成，但“当前哪一代允许对外服务”本身需要一个明确的完成事实。

Runtime 的 Plan、Step、Checkpoint 和等待状态又不同。它们用于恢复控制流程，却可以在必要时根据更强的 Domain、Effect、Knowledge 和 Security facts 修复。Cache 和 UI projection 更弱，只负责加速或展示；丢失以后应该能够从 Owner facts 重建，而不能反过来要求 Owner 世界服从旧缓存。

外部 Effect 是另一类不可替代事实。一个远端记录如果已经创建，本地恢复数据库并不能让它消失；本地备份里也不会自动包含外围系统当前的现实状态。因此 Effect ledger 必须记住逻辑动作、Attempt 和远端 correlation，遇到不确定结果时再去远端或人工渠道确认。安全决定也有自己的时间性：当前授权可以重新计算，但已经发生的 Approval、强制审计或治理事实如果承担审计责任，就不能被普通运行日志替代。

Observability 和 Eval 最后形成一层解释与测量状态。Trace、Metric 和实验结果可以帮助定位事故和判断复杂度收益，但它们不会因为数据量最大就升级成业务 Authority。这个状态分层直接决定了备份、重建、缓存、迁移和事故恢复应该先保护什么。

### 系统只在证据足够时提升事实强度

同一条案件里，很多危险错误都来自把“目前不知道”过早压成一个更强结论。两份关键扫描附件还没进入可查询范围时，当前检索没有命中不能升级成“全案不存在相关约定”；模型返回 200 和合法 JSON，不能升级成“专业判断正确”；Policy Engine 无法确认当前授权时，不能把旧 allow 延长成新的权限；外部 POST 越过发送边界后超时，也不能猜成“执行失败”。

这些情况属于不同责任域，却共享同一个架构纪律：**只有在当前边界要求的证据已经成立以后，系统才允许把一个较弱事实提升成较强事实。证据不足时保留较弱状态，而不是为了让流程继续而猜测。**

这条原则不意味着设计一个全局 `UNKNOWN`。材料覆盖不足时，03 需要扩大覆盖、暴露缺口或让上层 abstain；模型或 Capability 输出未经专业验收时，它仍然只是候选；授权新鲜度无法证明时，新的受保护动作 fail closed；现实 Effect 不确定时，06 必须 Reconcile。共同的是“不得无证据升级”，不同的是每类不确定性的 Authority 和收敛方式。

因此 Zuno 的很多状态看起来比普通 request/response 系统更细，不是为了状态机复杂度，而是因为法律业务里“没有证据证明成功”“没有证据证明失败”“没有证据证明不存在”“没有证据证明现在仍被允许”分别会导向完全不同的后续动作。

### 正式结果必须能回到一个可成立的因果世界

跨 Owner 不做全局事务以后，还有一个更隐蔽的风险：每一份引用都真实存在，却不代表它们能够组成同一个有效结果。

设想一个候选结论最初基于合同 V3、Knowledge generation G7、Capability C2 和当时的模型调用形成。专业人员随后开始复核。就在正式接纳前，合同 V4 进入并改变了付款日期；或者 SecurityEpoch 已经推进，使原来允许的数据用途不再适用于新的正式提交；又或者 Capability 的专业语义已经变更。旧候选、旧人审记录和新版本对象此时都可能分别是“真实记录”，但把它们直接拼成一个新的 WorkProduct，会制造一个业务上从未成立过的组合。

Formal Admission 因而不能只检查“这些 ref 是否存在”。它要重新验证**那些会影响业务正确性的依赖是否仍然适用于这次接纳**：正式材料和关键证据版本、候选产生时的知识与专业语义、需要的人审、当前安全条件以及预期的 DomainVersion，都必须沿着 causation 说明这次结果为什么仍有资格成立。无关变化不需要机械触发全量重算；真正改变前提的版本变化才要求拒绝、复核、重新验收或 Replan。

这里也不要求所有参与者在同一毫秒拥有一张全局快照。Zuno 要保护的是**因果一致性，而不是物理同时性**：系统能够证明这份正式结果使用了哪些历史输入、哪些条件在接纳时仍然有效、哪些后来变化只影响未来。工程 Reference 里的 version / freshness / causation refs、expected DomainVersion 和 matching `AdmissionReceipt` 都是在压缩这条证明链，而不是在模拟一个跨所有 Store 的大事务。

这也解释了为什么多个看似矛盾的事实可以同时成立。WorkProduct V5 可以曾经正式成立并已经交付，当前 Security 又可以禁止继续访问，新证据还可以让 V5 进入 stale / review-required。系统不需要选一个 global status 覆盖其他事实；Application 只把这些 Owner facts 组合成“现在用户应该看到什么”，历史本身继续保留。

### 可审计不等于未来重跑出同一段模型答案

模型让“恢复历史”又多了一层限制。一个外部 Provider 可以保持同一个 model name，却在后台升级权重、系统提示或推理策略；即使版本完全不变，采样、并发和服务端实现也可能让相同输入得到不同文本。几年以后重新调用一次模型，不能被当作对历史执行的重现。

对正式法律成果来说，更可靠的审计目标是重建**当时为什么能够做出这次决定**：使用了哪些材料和版本，哪一代知识与哪个专业语义参与了候选形成，实际调用了哪个 Provider / Model、使用了什么可获得的版本标识和配置、模型当时返回了什么，专业人员修改或接受了什么，接纳时哪些安全和业务条件成立，以及最后哪一份正式结果被保存和交付。

如果 Provider 提供不可变快照并且执行本身可确定，系统当然可以增加更强的重放能力；没有这种基础条件时，架构不承诺 bit-for-bit 或 token-for-token replay。后来的 rerun 是一项新的计算，可以用于回归比较、质量评测或重新分析，却不能覆盖历史上真正发生的模型 Attempt、HumanDecision 和 Formal Admission。

这种区分把 Provenance、Domain history 和 Evaluation 的职责分开了。Provenance 解释当时用了什么，Domain 保存当时正式接受了什么，Evaluation 判断今天重新运行是否仍满足质量要求；三者共同支持审计，却没有任何一个能够单独让一个非确定性模型变成可时间倒流的函数。

### 越过不可逆边界以后，只能追加新的事实

到这里可以把前面的多种恢复语义压成一条更基础的规则。候选结果、尚未激活的知识构建、还没有正式接纳的专业判断，都仍处在可替换区间；输入变化以后可以重新计算、拒绝、Retry 或 Replan。它们失败时，系统最多丢失一次计算，不会改写已经承担业务责任的历史，也不会改变外部世界。

Formal Admission 和现实 Effect 则跨过了不同类型的不可逆边界。Domain transaction 一旦正式提交，后来的 Cancel 只能停止未来工作，不能让 AdmissionReceipt 和已经形成的 WorkProduct 像从未存在过一样消失。一个外部动作一旦越过 send boundary 并且可能已经发生，后来的 Replan 也没有资格把现实世界随着旧 Plan 一起丢弃；结果未知时先 Reconcile，已经确认的结果需要保留自己的 Effect history。

不可逆不表示“永远有效”。新 Evidence 可以让旧 WorkProduct stale，新的 SecurityDecision 可以禁止未来访问，新的 generation 可以替换当前 serving。变化发生在**当前资格**上，而不是通过覆盖历史伪造“过去没有发生”。因此 Zuno 的历史事实通常通过新版本、新失效事实、新决定继续向前追加；当前可见性、可执行性和有效性则可以随着新的 Authority facts 被重新判断。

这也决定了修正方式。边界之前的问题通常通过 Retry、Replan、重新计算或拒绝解决；正式业务已经成立以后用新版本、invalidation 或 supersession 表达变化；现实 Effect 已经可能发生以后用 Reconcile 确认过去，确实需要撤回或纠正时再发起一项新的受控 Effect 或 Compensation。补偿动作同样拥有自己的授权、Attempt 和结果，它不是把旧 Receipt 改成“没发生”。

这条规则不要求把 Zuno 改造成一套全局 Event Sourcing 系统，也不需要增加新的 `IrreversibilityReceipt`。它只是要求恢复逻辑尊重已经跨过的 Authority 和现实边界：**控制状态可以修，当前资格可以撤销，历史事实不能通过工作流回滚被偷偷删除。**

### 一致性只在 Owner 边界内做强，跨边界靠完成证明和恢复收敛

一项真实任务可能同时触及 PostgreSQL、Object Store、vector / graph index、Runtime Checkpointer、Queue、模型 Provider 和外围法院系统。要求这些组件共享一笔全局事务，既不现实，也会把系统可用性绑在最慢、最不可控的参与者上。尤其外部 Provider 和法院系统根本不会参加 Zuno 的本地 2PC。

Target 因而把强一致范围收缩到真正拥有事实的边界。Domain 的正式提交在自己的耐久事务里保证业务版本与 matching AdmissionReceipt 一起成立；Knowledge 在新的 generation 完整验证以前不让它替换当前 serving；Runtime 只串行化自己的控制事实；Effects 在越过危险 send boundary 前固定动作和尝试身份；Security 保存自己能够证明的授权、Approval 和审计事实。

跨 Owner 以后，一致性靠稳定 identity、version、causation ref 和可查询完成证明收敛。Domain 已经提交、Runtime Checkpoint 还没更新时，不回滚 Domain，而是查询 Receipt 后修 Runtime；Knowledge 新 generation 构建失败时，继续服务最后一份完整 generation，而不是要求全部 Store 回滚；外部 POST 结果未知时保留 Unknown，等 Reconcile 后再修 Runtime 与 Application projection。

异步消息也遵守同一原则。Queue 可以重复投递，Worker 可以在处理后崩溃，网络也可能让 producer 不知道消息是否已经到达。系统不依赖“消息绝对只投递一次”，而是让每个边界有自己的稳定幂等身份和冲突检查。重复 delivery 最多重复观察或重新查询同一个 Owner fact，不应该制造第二份正式业务事实或第二个现实动作。

这种一致性模型可以概括为：**Owner 内部尽量做短而明确的强一致提交；Owner 之间接受短暂不同步，但必须有可追踪因果和确定的修复方向；一旦跨到外部现实，不确定性必须被显式保存，而不是用本地状态猜掉。**

### 同一条业务链会跨同步入口、异步计算和外部世界

简单问答可以在一次同步请求里完成：Application 接收请求，Security 检查当前访问，Knowledge 检索稳定材料，必要时调用模型，再返回受控答案。只要响应时间和业务语义允许，没有必要把它人为拆成队列和多阶段 Worker。

长任务则不同。Application 先稳定请求身份和 Scope，再把需要长期执行的工作交给 Runtime。Runtime 的逻辑 Controller 决定当前计划和可执行 Step，OCR、索引、专业能力、模型调用等计算可以由不同 Worker 池并行执行。这里的 `Single Controller` 只要求当前计划有一个清楚的逻辑写者，并不限制整个系统只能有一个进程，也不妨碍计算 Worker 横向扩容。

Queue 和 Worker 解决的是时间解耦与吞吐，不拥有业务成功。一个 Worker 完成 OCR 只说明一个派生处理项完成；模型 Worker 返回结果只说明一次模型计算结束；Tool Worker 发送请求后甚至可能仍不知道现实 Effect 是否发生。每个异步边界都必须把“任务被接收”“计算完成”“业务完成”和“外部现实完成”分开。

模型 Provider、搜索服务和外围法院系统位于更远的网络边界。它们有自己的限流、故障、地域、Credential 和数据政策。Zuno 可以在本地控制是否发起调用、选择哪个合格 Provider、记录哪次 Attempt，却不能把这些远端系统纳入自己的事务。Provider outage 的 fallback 需要继续满足质量与安全条件；外部 Effect timeout 则不能用换 Provider 的方式掩盖现实结果未知。

### 默认部署从模块化后端和按工作类型扩展的 Worker 开始

九个逻辑责任域不应该机械变成九个微服务。早期和中等规模下，更简单的 Target 部署是模块化 Python Backend，加少量按照资源特征划分的 Worker，以及成熟的平台原语。Application、Domain、Runtime 控制和相邻业务逻辑可以共处一个进程边界；OCR / ingestion、Knowledge rebuild、模型调用、外部 Tool、Eval 等工作在出现资源或故障隔离需求时再独立成 Worker。

扩容首先看瓶颈来自哪里。大量扫描材料让 OCR / parsing 积压时，增加 ingestion Worker 比拆 Domain 服务更直接；embedding 或索引重建吃满 CPU / GPU 时，扩 Knowledge Worker；模型流量受 Provider quota 约束时，增加本地进程并不会提高远端配额，应该做 admission、quota、fallback 和预算控制；外部法院接口限流时，Effect execution 需要按目标系统限制并发，而不是让更多 Worker 同时重试。

Backpressure 必须能够向上游显式传播。入口不能无限接受长任务然后让所有任务一起超时；Runtime 也不能在下游 Provider 已过载时继续无界派发。产品层可以表达 queued、deferred 或 rate-limited，Runtime 依据预算和资源决定暂停或降级，Model Gateway 和 Effect executor 则按各自 Provider / target 的容量约束工作。什么时候需要 tenant 级公平、优先级队列或更精细的 load shedding，仍应由真实负载证据决定。

逻辑模块只有在独立扩缩容、安全隔离、网络出口、Secret isolation、故障半径、合规或发布生命周期出现真实收益时，才值得进一步拆成独立网络服务。拆服务增加的是网络失败、版本兼容、分布式追踪和运维成本；它不是架构成熟度的默认指标。

### 系统级恢复先保护不可替代事实，再重建派生与投影

单个 Worker 崩溃只是最小故障。更大的事故可能包括 Runtime 进程重启、Queue 重投递、数据库 failover、索引损坏、模型 Provider 长时间不可用，甚至整套部署需要从备份恢复。总体架构必须说明这些故障发生以后什么先回来。

第一优先级是不能靠重算恢复的事实：正式材料身份和长期 Domain 结果、已经发生或仍然未知的 Effect ledger、承担治理责任的 Security / Approval / Audit facts，以及产品对外稳定身份。它们决定恢复以后系统不能重复做什么、哪些历史必须保留、哪些外部现实仍要确认。

Runtime Checkpoint 和控制状态随后恢复，但不能无条件当作最终真相。恢复过程先查询更强的 Owner facts，再修 Plan / Step projection。Knowledge 的 OCR、embedding、graph 和 index 在源材料与处理配方仍然可用时可以重建；Cache、搜索 projection 和部分 telemetry 更应该被视为可丢弃或可再生状态，而不是灾难恢复的第一锚点。

外部世界尤其不能靠本地备份恢复。数据库回到昨天，不会让今天早上已经发送到法院系统的记录自动消失。恢复后的 Effect 处理必须继续使用稳定动作身份对账；如果结果无法自动确认，就保持 Unknown 或进入人工渠道，而不是因为本地状态回退就重做。

HA / DR 也因此不能只写“数据库有主从”或“服务有多副本”。真正需要证明的是 failover 以后 Controller 是否避免双写、Owner facts 是否满足目标 RPO、恢复到什么 RTO、备份能否实际 restore、Queue / Checkpoint 与 Domain / Effect 的时间差怎样收敛，以及外部 Provider 不可用时系统是否会安全降级。Target 可以要求这些能力，Current 只有在 backup / restore、takeover / fencing、load 和外部依赖演练形成 Evidence 后才有资格声称已经达到相应等级。

更精确的 Authority、Contract、状态、完成证明、恢复顺序和跨 Store 约束在 [`reference.md`](reference.md) 以及各模块 Engineering Reference 中维护；总体视觉关系见 [`architecture-views.md`](architecture-views.md)。

### 把这些结构重新合回同一条案件

正常情况下，Application 先把外部请求归一化成可信主体、Matter 和任务范围，Security 判断当前访问是否允许，Knowledge 再确认这项任务需要的材料和知识已经具备。简单问题可以直接走检索和模型短路径；真正需要等待、并行分析、人工介入或正式提交的任务才进入 Runtime 的长期执行路径。

Runtime 在执行过程中调用专业 Capability、检索和 Model Gateway。它们产生候选和运行记录，需要长期进入法律业务的结果再交给 Domain 正式接纳。只要结果仍然只是草稿或候选，系统可以重算、替换 Provider 或调整检索路线；正式业务一旦成立，就由 Domain 的版本和引用保护其历史。

结果需要离开 Zuno 时，Application 决定产品上应该交付什么，Effects 负责真正可能改变外围世界的发送。Security 在新的受保护边界重新检查当前条件，Observability 用 correlation 串起这条时间线供诊断，Evaluation 再判断增加的复杂度是否有可重复收益。Trace 可以帮助解释事故，却不会替任何业务 Owner 宣布结果已经成立。

故障恢复沿着同一条链寻找更强的耐久事实。先确认正式 Domain 提交是否存在、外部 Effect 是否已经发生、当前安全条件是否允许继续、当前知识是否仍满足任务，再修 Runtime 的 Checkpoint 和计划投影，最后恢复 Application 对外状态。恢复顺序由事实 Authority 决定，而不是由哪一个状态最接近用户界面决定。

### 架构复杂度按约束逐层生长，也应该允许逐层退出

如果语料规模小、文本干净、没有多版本和复杂 Scope，Knowledge 可以只保留一个版本化 Hybrid Retrieval，GraphRAG 没有存在的必要。如果专业能力只有几个稳定内部函数，没有多 Provider 和独立质量门槛，Capability 可以薄到 Python Protocol 加测试集合。任务不跨越等待、恢复和正式提交时，Runtime 可以退回普通 workflow 甚至同步调用。外围 Tool 都是只读或拥有强幂等协议时，完整 Effect 生命周期也可以缩小。系统只使用一个受控模型时，Model Gateway 也可以只是很薄的统一 adapter。

这意味着 Zuno 不必以“完整九域全能力”作为每个部署的起点。最小形态可以是 Generic Host + 受控 RAG + Legal Backend；材料版本和异步加工变复杂以后再增强 Knowledge；出现长期正式成果以后再引入完整 Domain admission；任务跨越等待、重规划和恢复以后再增强 Runtime；现实副作用与长期权限变化真正出现以后再建立 Effects 和更强 Security；GraphRAG、Reflection、Memory、Specialist 和 Native Runtime 则最后接受 Evaluation 的边际收益检验。

Generic Host 已经提供成熟会话、UI、工作流和 Checkpoint 时应优先复用。PostgreSQL、Object Store、Queue、Secret Manager、OpenTelemetry、身份系统、Policy Engine 和模型 SDK 也优先复用成熟能力。Zuno 自己只保留这些基础设施不会替法律业务决定的 Authority、因果和恢复语义。

责任域回答的是“这类事实最终由谁负责”，并不要求每一类责任永久拥有复杂状态机或独立部署。测不到稳定收益，就缩小或删除实现复杂度；即使未来某个实现被删掉，只要对应业务问题仍然存在，必要的事实边界仍需由更简单的机制保护。

### Current / Target / Evidence / Unknown

**Target：** 当前接受的总体设计仍然是九个逻辑责任域，围绕事实 Authority、Owner 内局部一致性、跨 Owner 完成证明、因果一致性、显式不确定性、不可逆边界和恢复顺序协作。默认部署不要求九服务；模块化后端、按工作类型划分的 Worker 与成熟 Platform primitives 是更简单的起点，服务拆分由真实扩缩容、安全、故障和发布约束驱动。

**Current：** 代码库中已经存在部分 Agent、Knowledge、Model Gateway、Tool、评测和基础设施实现，也有历史测试与 Eval 证据；这些实现覆盖到什么程度，不能从 Target 文档反推。Current 只由 [`docs/evidence/`](../evidence/README.md)、代码、Migration、Test、Trace 和可复现 Eval 证明。

**Evidence：** 历史提交可以证明部分 PostgreSQL 迁移、知识流水线、GraphRAG 实验、Context / Memory、Tool Calling、模型与 Eval 基础工作。它们证明局部工程事实，不证明九个 Target 责任域已经全部落地，更不证明整体一致性、HA / DR、容量或 Production Ready。

**Unknown：** 真实长任务的系统级崩溃恢复、跨 Owner repair、外部 Effect 最终对账、完整持续授权、正式 Domain Admission、Backpressure / fairness、容量、真实 RPO / RTO、HA / DR、法院侧完整结果和生产资格仍需要对应 Evidence。设计文档把这些边界说明得再完整，也不能替代测试和运行证明。

单个责任域的连续 Human Narrative 见 [`docs/modules/`](../modules/README.md)；总体 Engineering / Agent 精确参考见 [`reference.md`](reference.md)。长期架构决策进入 [`docs/decisions/`](../decisions/README.md)，研究候选进入 [`docs/research/`](../research/README.md)。
