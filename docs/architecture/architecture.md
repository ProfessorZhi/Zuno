# Zuno 目标架构：从一条法律任务的失效过程理解系统边界

法律智能系统的架构难点，往往在答案离开一次请求以后才真正暴露出来。

设想一项合同争议分析。用户上传合同、补充协议、聊天记录和几份扫描附件，希望系统梳理付款义务、违约事实和可引用的材料。第一版产品完全可以很简单：应用服务确认访问范围，RAG 找到相关文本，模型组织答案，页面展示引用。对于“合同第 8 条写了什么”这类问题，这条路径已经足够。继续增加 Agent、状态机和服务，只会增加时延、成本和故障点。

同一项工作被拉长以后，系统开始遇到另一类问题：关键材料还没有处理完，研究模型准备被新的 LLM 替换，机器结论需要专业人员修改和接纳，新证据在任务运行期间进入，正式业务提交和运行进度没有同时落盘，外围系统在 POST 后超时，用户权限又在等待期间发生变化。每个问题都要求系统说明三件事：现在究竟发生了什么，哪一份记录有资格证明它，崩溃以后应该先相信谁。

下面的场景描述 Target 设计要解决的问题，不代表这些机制已经全部在 Current 代码或真实法院环境中验证。Current 的实现、测试、Trace、Eval 和运行证据只以 [`docs/evidence/`](../evidence/README.md) 为准。

## Part A — Human Narrative（人类技术叙事）

### 从普通法律问答开始

一条短请求可以沿着很朴素的路径完成。用户提出问题，应用服务确认他当前能读哪些材料，检索系统找到原文，模型在这些材料上组织回答，发布前再检查引用和当前发布条件。这里没有需要运行几十分钟的计划，没有现实副作用，也没有必须长期保存的专业工作成果。受控 RAG、成熟模型 SDK 和普通后端已经能够承担大部分责任。

这种简单方案应该继续存在。只有请求真的跨越材料准备、长期等待、人工复核、正式业务结果或现实副作用以后，后面的机制才开始有价值。简单条款定位没有理由先构造动态执行图，也没有理由因为系统支持 GraphRAG 就默认走图检索。

合同争议分析很快会越过这条边界。同一个事项可能已经有合同 v1、v2、v3，补充协议刚刚上传，关键扫描附件仍在 OCR，聊天记录又在分析过程中补入。专业人员会修改机器建议，某个工作成果可能已经交付，外围系统也可能在 Zuno 崩溃以后继续保留先前动作的结果。此时，保存“最后一次模型输出”已经无法描述这项工作。

### 材料不齐时，流畅回答也可能没有资格代表全案

用户一共上传了一百份材料。九十八份已经完成解析和索引，两份关键扫描附件还没有 OCR。页面上的上传请求全部成功，向量库里也已经有大量内容。如果后台据此宣布案件材料已经 READY，系统就可能在证据范围并不完整时生成一份非常流畅的全案分析。

缺失材料是否阻断任务取决于用户正在做什么。查询合同第 8 条，只要对应合同正文已经可用就可以继续；计算全案违约金额时，尚未处理的附件可能正好改变付款日期。系统需要知道的不只是“有没有数据”，而是当前任务所需的材料和加工结果是否已经足够。

这里自然出现两种生命周期。合同 v3 作为正式业务材料，需要拥有稳定身份；OCR、切分、Embedding、图结构和索引属于围绕这份材料建立的派生知识，可以因为算法升级而重建。新一代派生知识构建完成，也只说明这一代加工结果可以服务查询；具体任务仍要根据材料范围和需要的能力判断现在是否足够。

工程实现把可重建的一代知识称为 `KnowledgeGeneration`，把面向具体任务的“现在是否够用”判断称为 `ReadinessDecision`。这两个名字压缩的是前面的业务区别：材料身份保持稳定，知识可以重建，而就绪程度取决于任务。

材料真正可用以后，系统才有资格讨论模型和研究算法做出的专业判断。

### 同一个专业任务可以更换实现，专业含义不能跟着漂移

课题组已有事件抽取模型能够从材料中返回结构化事件。后来团队希望换成新的法律 LLM，它也能返回相似的事件 JSON。最快的接法是在工作流里替换一个 Python class，或者给两个实现各写一个 wrapper。

接口能接上以后，专业问题仍然存在。两个实现怎样划分“事件”，空结果表示确实没有事件还是处理失败，各自支持什么材料和案由，错误会以什么方式出现，旧结果与新结果能不能直接比较，都不能从 JSON Schema 推出来。如果这些差异散落在 Planner、fallback 和下游判断里，每换一次模型都会让工作流重新学习一遍专业语义。

Zuno 因而先固定“事件抽取这项专业能力对上层承诺什么”，再允许研究模型、规则、LLM 或外部服务竞争实现。工程上把稳定的专业承诺称为 `Capability`，把具体实现称为 `Provider`。新的 Provider 先证明自己遵守这份承诺，再用冻结的数据、版本和任务范围证明它适合哪些任务；健康检查成功或能够返回合法 JSON，都不足以永久获得业务资格。

这条边界让研究资产可以进入长期工程系统，同时也保留替换空间。某个论文模型停维、外部服务退出或新 LLM 更合适时，上层依赖的专业含义不必跟着实现一起重写。如果专业定义本身发生变化，系统再显式形成新的能力版本，而不是把语义变化藏在同一个接口后面。

现在，机器已经找到相关材料，也形成了一个看起来合理的违约判断。真正困难的问题从“它算得怎么样”转向“这份结果是否已经成为业务愿意长期负责的事实”。

### 机器结论进入长期业务以后，系统必须能解释谁接受了什么

模型判断付款已经逾期，并生成事实摘要。专业人员复核后发现补充协议的签署时间被写错了一天，于是修改这处事实，接受其余判断，并把结果放进正式工作成果。

如果系统只覆盖保存最后一段文字，几周后就很难回答：机器原来建议了什么，专家修改了哪里，当时采用合同 v2 还是 v3，引用的是哪一页材料，新证据进入后旧成果为什么仍然存在。一个需要交付、复核和长期追责的结果，必须保存自己的形成过程和当时成立的业务上下文。

因此，检索和模型产生的内容先保持候选身份。只有在材料版本、专业规则、必要人审和当前安全条件都满足以后，法律业务才把需要长期负责的内容接纳为正式事实和工作成果。工程上把这个提交边界称为 `Formal Admission`。它保护的是业务权威，而不是给所有模型输出机械增加审批步骤；普通一次性问答仍然可以停留在短路径上。

下午又进入一份关键补充协议，付款日期的认定随之改变。上午形成的工作成果曾经真实存在，也可能已经被交付；现在它又不适合继续代表当前结论。系统应保留旧版本当时为何成立，同时形成需要复核、失效或被新版本取代的关系。直接改写旧记录会让审计、引用和已经发生的交付失去时间一致性。

同样，今天重建索引以后，Retriever 可能找到另一段 chunk。历史工作成果仍要回到当时真正采用的材料版本和稳定位置，而不是跟着今天的索引结果漂移。正式业务事实由此拥有自己的时间线，知识派生和运行过程可以继续重建。

一旦正式提交和运行控制同时存在，下一类故障就会把两种时间线直接撞在一起。

### 崩溃和晚到结果迫使系统区分业务事实与运行进度

假设专业人员已经确认结论，业务事务也成功写入新的正式工作成果。Runtime 正准备保存下一份 Checkpoint，进程却在这几毫秒里崩溃。新的 Worker 接管以后，只能看到旧 Checkpoint。如果它把旧控制进度当成整个系统的事实，就会再次执行正式提交。

恢复时要先查询拥有业务权威的耐久记录，确认那次提交是否已经发生；已经发生就修复 Runtime 的控制进度，没有发生才重新进入当前有效的提交路径。Target 让正式准入在同一业务事务里留下一个可以重新查询的完成证明，工程上称为 `AdmissionReceipt`。Checkpoint 继续记录控制流程走到了哪里，但它不负责宣布正式法律业务是否已经成立。

这个故障决定了恢复顺序：较新的业务事实不能被较旧的运行投影覆盖。Queue、Checkpoint 和 Worker 都可以在随后修复，只要恢复过程先回到拥有正式结果的 Authority 确认现实状态。

任务运行更久以后，因果问题还会出现在并行分支上。分析开始二十分钟后，新证据进入，当前计划需要改变；旧计划里的一个分支此时才返回，而且结果本身质量很好。系统不能仅凭“计算成功”接受它，也没有必要仅凭“晚到”直接丢弃。它需要检查这份结果基于哪一版材料和计划，原来的前提现在是否仍成立，再决定继续使用、重新验收还是重做。

为了让计划切换只有一个清楚的因果顺序，Target 让一个逻辑控制者负责激活当前计划和收敛重规划；专业计算本身仍然可以并行。新的证据需要改变计划时创建新的 `PlanVersion`，旧分支回来后再按当前前提判断资格。工程上把这个逻辑写者称为 `Single Controller`。它是一种控制责任，不要求部署成单独网络服务。

到这里，崩溃恢复已经能够回答“系统内部哪份记录更可信”。向外围系统产生动作以后，Zuno 还必须面对一个自己无法单方面裁决的事实。

### 网络超时以后，失败状态不足以描述现实世界

系统准备把一份正式成果提交到外围法院系统。请求已经发出，连接却在响应到达前超时。本地只知道自己没有拿到确定响应，远端可能完全没有执行，也可能已经提交成功而响应丢失。

把 timeout 直接记成 Failed 然后自动重试，会把网络不确定性变成第二次业务提交。更安全的做法是在发送前先固定这次逻辑动作的身份、内容和幂等语义；越过发送边界以后，只要远端结果还无法确认，就保留“未知”这一事实。随后利用远端幂等键、业务唯一键、查询接口或必要的人工方式确认过去究竟发生了什么，再决定是否补做、结束或补偿。

工程上，发送前固定的逻辑动作叫 `PreparedAction`，确认后的现实结果由 Effect 记录；结果未知时进入 Reconcile。重复一个仍然安全的同一计算属于 Retry，输入或前提变化以后重新安排工作属于 Replan，已经可能发生的现实动作需要先查清过去属于 Reconcile。三种处理方式来自三种不同的失败来源。

这条边界也说明为什么调用方的 HTTP 状态、Runtime 的 Step 状态和现实世界结果不能被压成一个 `failed / succeeded`。越过外部边界以后，系统只能通过远端可观察事实、幂等协议和对账逐步收敛。

### 二十分钟长任务把权限也变成时间问题

任务在 10:00 启动时，用户有权读取附件 A。系统随后等待 OCR、运行检索、调用模型并进入人工确认。10:12，Matter 归属或用户权限发生变化。10:20，后台 Worker 准备重新读取正文并向外部模型发送材料。

入口处那次合法鉴权只能证明 10:00 的读取当时被允许。10:20 的新读取、模型外发、Secret 获取或高风险 Tool 调用需要消费当前的授权条件。已经发生的合法历史保持不变，未来的受保护动作则跟随新的主体、资源、用途和政策状态。

专业人员对法律结论的认可也不会替代安全审批。法律业务判断回答“这份结论是否应当成为正式工作成果”，安全与治理回答“此刻是否允许执行这次读取、外发或现实动作”。两种决定可能出现在同一个页面和同一条工作流上，但恢复与审计时拥有不同 Authority。

新材料从另一方向改变当前有效性。昨天已经正式成立的工作成果，今天可能因为新的证据需要复核。系统保留它昨天为什么成立，同时阻止它在条件变化以后继续被静默当作当前答案。长任务中的权限、新鲜度和业务有效性都随时间变化，任何一次早先的成功都不能永久替后续动作做决定。

走完这条案件时间线以后，长期存在的责任边界已经自然显现。此时再给它们命名，比在第一页背模块表更容易理解。

### 这些反复出现的冲突才形成九个责任域

当前 Target 把这些长期事实分给九个逻辑责任域。这里的“九”来自已经接受的责任划分，不表示系统应该部署成九个进程、九个数据库或九个网络服务。

| 责任域 | 它长期回答的问题 |
| --- | --- |
| **01 Application & Integration** | 外部请求怎样被接收、发布、查询和交付，多个 Owner 的事实怎样组合成稳定产品行为 |
| **02 Legal Domain & Work Product** | 哪些材料和专业结果已经成为正式业务事实，历史版本和失效关系怎样保存 |
| **03 Knowledge & Evidence** | 正式材料怎样变成可重建知识，当前任务是否准备好，检索候选从哪里来 |
| **04 Agent Runtime & Control** | 长任务当前按哪个计划运行，哪些 Step 可以执行，等待、取消、Replan 和恢复怎样收敛 |
| **05 Capability & Skill** | “事件抽取、冲突识别、类案检索”等专业能力承诺什么，哪些实现当前有资格提供它 |
| **06 Tool Runtime & Effects** | 系统准备让现实世界发生什么，实际发出过什么，结果未知时怎样对账 |
| **07 Model Gateway** | 某次模型调用为什么选择这个 Provider / Model，真实调用和 Usage 是什么 |
| **08 Security & Governance** | 当前这一刻能不能继续读、外发、取 Secret、审批或执行受保护动作 |
| **09 Observability & Evaluation** | 一次执行发生了什么，以及某层复杂度是否通过可重复实验证明值得保留 |

这些边界先划分谁拥有哪类事实，再决定代码和部署怎样组织。默认实现可以是模块化 Python 后端，只有吞吐、资源、Secret 隔离、网络出口、故障半径、合规或部署生命周期形成真实约束以后，某些责任才值得拆成独立 Worker、进程或网络服务。

PostgreSQL、Object Store、Queue、Checkpointer、Secret Manager、身份系统、OpenTelemetry 和模型 SDK 等成熟基础设施优先复用。它们提供事务、存储、队列、身份、观测和调用机制；Zuno 只需要长期拥有基础设施无法替法律业务决定的语义，例如什么正式成立、哪些材料足够支持当前任务、旧计划是否仍适用、外部动作是否真的发生，以及下一次受保护操作现在是否仍被允许。

更精确的 Authority、Contract、状态、完成证明、恢复顺序和跨 Store 约束在 [`reference.md`](reference.md) 以及各模块 Engineering Reference 中维护；总体结构和运行视图见 [`architecture-views.md`](architecture-views.md)。

### 把同一案件再走一遍

正常情况下，Application 先把外部请求归一化成可信主体、Matter 和任务范围，Security 判断当前访问是否允许，Knowledge 再确认这项任务需要的材料和知识已经具备。简单问题可以直接走检索和模型短路径；真正需要等待、并行分析、人工介入或正式提交的任务才进入 Runtime 的长期执行路径。

Runtime 在执行过程中调用专业 Capability、检索和 Model Gateway。它们产生候选和运行记录，需要长期进入法律业务的结果再交给 Domain 正式接纳。只要结果仍然只是草稿或候选，系统可以重算、替换 Provider 或调整检索路线；正式业务一旦成立，就由 Domain 的版本和引用保护其历史。

结果需要离开 Zuno 时，Application 决定产品上应该交付什么，Effects 负责真正可能改变外围世界的发送。Security 在新的受保护边界重新检查当前条件，Observability 用 correlation 串起这条时间线供诊断，Evaluation 再判断增加的复杂度是否有可重复收益。Trace 可以帮助解释事故，却不会替任何业务 Owner 宣布结果已经成立。

故障恢复沿着同一条链寻找更强的耐久事实。先确认正式 Domain 提交是否存在、外部 Effect 是否已经发生、当前安全条件是否允许继续、当前知识是否仍满足任务，再修 Runtime 的 Checkpoint 和计划投影，最后恢复 Application 对外状态。恢复顺序由事实 Authority 决定，而不是由哪一个状态最接近用户界面决定。

### 复杂度可以出现，也必须可以退出

如果语料规模小、文本干净、没有多版本和复杂 Scope，Knowledge 可以只保留一个版本化 Hybrid Retrieval，GraphRAG 没有存在的必要。如果专业能力只有几个稳定内部函数，没有多 Provider 和独立质量门槛，Capability 可以薄到 Python Protocol 加测试集合。任务不跨越等待、恢复和正式提交时，Runtime 可以退回普通 workflow 甚至同步调用。外围 Tool 都是只读或拥有强幂等协议时，完整 Effect 生命周期也可以缩小。

Generic Host 已经提供成熟会话、UI、工作流和 Checkpoint 时应优先复用。Zuno 不需要为了架构图完整而复制这些通用能力。逻辑责任域只有在独立扩缩容、安全隔离、故障半径、合规或部署生命周期形成真实约束时，才进一步拆成独立服务。

GraphRAG、Memory、Reflection、Specialist、更贵模型和 Native Runtime 都要和更简单 baseline 做可比实验。已经实现只证明团队付出了实现成本，不赋予机制永久保留权。某个机制在同任务、同语料和可比预算下没有稳定收益时，Evaluation 应支持关闭它、缩小使用范围或回到更简单路径。

### Current / Target / Evidence / Unknown

**Target：** 当前接受的总体设计仍然是九个逻辑责任域，围绕事实 Authority、完成证明、因果版本和恢复顺序协作。模块 Design Baseline 与 Cross-Module Consistency 已有文档基线，但 `module_detail_freeze: NOT_YET`，`implementation_authorization: NO`。

**Current：** 代码库中已经存在部分 Agent、Knowledge、Model Gateway、Tool、评测和基础设施实现，也有历史测试与 Eval 证据；这些实现覆盖到什么程度，不能从 Target 文档反推。Current 只由 [`docs/evidence/`](../evidence/README.md)、代码、Migration、Test、Trace 和可复现 Eval 证明。

**Evidence：** 历史提交可以证明部分 PostgreSQL 迁移、知识流水线、GraphRAG 实验、Context / Memory、Tool Calling、模型与 Eval 基础工作。它们证明局部工程事实，不证明九个 Target 责任域已经全部落地，更不证明 Production Ready。

**Unknown：** 真实长任务的系统级崩溃恢复、外部 Effect 对账、持续授权、正式 Domain Admission、容量、HA / DR、法院侧完整结果和生产资格仍需要对应证据。设计文档把这些边界说明得再完整，也不能替代测试和运行证明。

单个责任域的连续 Human Narrative 见 [`docs/modules/`](../modules/README.md)；总体 Engineering / Agent 精确参考见 [`reference.md`](reference.md)。长期架构决策进入 [`docs/decisions/`](../decisions/README.md)，研究候选进入 [`docs/research/`](../research/README.md)。
