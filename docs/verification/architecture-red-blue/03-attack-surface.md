# Architecture Red Team Attack Surface

红队不只盘问架构图，也盘问“为什么这个项目值得存在”和“这个团队能不能把它做出来”。以下攻击面按风险组织，不是固定题单。

## P01 产品背景与需求

```text
谁遇到了什么问题？
不用 Zuno 时如何完成？
为什么现在做？
用户愿意为什么结果付出迁移和学习成本？
成功是回答更漂亮，还是完成了一个可验收的工作成果？
```

红灯：只能说“AI 很火”“提升效率”，说不出用户、流程、失败代价和验收标准。

## P02 WorkBuddy / 通用 Agent 替代攻击

不是问“Zuno 是否全面超过 WorkBuddy”，而是问价值边界：

```text
WorkBuddy 已经能聊天、规划、调工具、做文档，为什么还需要 Zuno？
Zuno 的目标用户是否愿意放弃通用性换取什么？
是法律/合同领域的证据、Playbook、Matter、Finding、审计和权限深度吗？
这些差异是用户真实需要，还是我们自我描述？
最小验证实验是什么？
```

可能的 Agent Proposal：

```text
通用平台优化横向任务完成；Zuno 可以选择纵向法律工作流，
把合同版本、证据引用、企业 Playbook、Finding、律师确认和审计做成正式业务对象。
```

但如果没有真实用户、试点或对照数据，必须标记 `PRODUCT_POSITIONING_GAP`，不能写成市场事实。

## P03 团队人数与架构规模攻击

高危组合：小团队 + 11 逻辑模块 + 微服务 + 多模型 + GraphRAG + Tool Governance。

红队必须问：

```text
团队几个人？当前每人负责什么？
11 个是逻辑 Owner、代码模块还是部署服务？
当前最小可交付链路是什么？
如果只允许保留 3 个部署单元，如何组合？
哪些能力必须现在做，哪些 Defer？
```

正确方向通常不是删掉事实模块，而是区分：逻辑模块、物理运行域、当前实现和 Target 部署；若交付范围仍过大，就缩小产品场景和发布目标。

## P04 项目真实性、用户和落地

```text
现在谁在用？是真用户、内部试用还是演示？
数据从哪里来？是否包含敏感数据？
部署在哪里？谁维护？出现问题谁响应？
一个真实任务从输入到交付要多长时间？
如果没有用户，当前最接近落地的试点是什么？
```

红灯：把目标架构、合作背景、Demo、文档或 Mock Test 说成生产落地。

## P05 Ownership 与团队协作

```text
你亲自写了哪些代码或文档？
核心决策是谁做的？
模型、数据、部署、前端、后端和评测分别由谁负责？
你和其他 Agent/后端同学的边界在哪里？
一个模块出故障时谁处理？
```

红灯：所有模块都由“我负责”，或只会复述架构但无法说明任何一个具体实现和协作接口。

## P06 架构必要性与简化攻击

```text
为什么需要 Agent，而不是固定 Workflow？
为什么需要 Graph，而不是带 metadata 的关系表？
为什么需要 Memory，而不是 Session State？
为什么需要微服务，而不是模块化单体？
如果用户量只有 300，哪些设计仍然必要？
```

每个答案必须回到约束、收益、代价和可延期部分。

## P07 Build / Buy / Extend / Defer

凡是自研模块都追：

```text
有没有成熟开源方案？
为什么不 Adopt？为什么不 Fork？
作为底座后还缺哪个 Contract？
你们自研的 Delta 是什么？维护成本谁承担？
今天重做还会 Build，还是 Extend/Defer？
```

禁止用“业务特殊”结束回答，必须说出具体差异。

## P08 实现、状态和数据所有权

```text
输入、输出、状态、版本、存储和错误分别是什么？
谁是 Canonical Owner？谁只能消费 Projection？
一个请求跨模块时如何传递 Proposal / Snapshot / Receipt？
模型输出如何进入确定性 Gate？
```

## P09 可靠性、规模、成本和安全

强制注入：超时、重复消息、模型 429、索引落后、权限撤销、租户串数据、外部 Tool UNKNOWN、Token 成本翻倍。

红队要追到：Retry/Repair/Replan/Reconciliation 的区别、幂等、恢复点、降级、审计、限流、预算和告警。

## P10 开发过程与交付现实

```text
需求由谁拆？什么时候冻结 Contract？
谁写测试/Eval？谁验收？
第一次 Demo 和现在架构之间经历了哪些变化？
哪些技术债已知但暂不处理？
发布、回滚、故障响应和反馈如何进入下一轮？
```

Agent 可以提出目标流程，但必须和实际开发过程分开。

## P11 评测和证据

```text
你说更准，Baseline 是什么？
数据集怎么切？有没有污染？
Graph/Memory/Tool 增加了什么收益和代价？
失败案例如何分类？
没有数字时，当前能诚实证明到哪？
```

## P12 反事实红灯

```text
如果不允许外部联网怎么办？
如果只能用一个模型怎么办？
如果团队人数减半怎么办？
如果 WorkBuddy/开源框架提供了 80% 能力怎么办？
如果用户不愿意迁移数据怎么办？
如果只能先交付一个场景，你选哪个？
```

## 红灯判定

| 红灯 | 说明 |
|---|---|
| 价值红灯 | 产品没有清晰用户、任务、替代方案和验收结果 |
| 规模红灯 | 架构规模明显超过当前用户、团队和交付阶段，且没有演进拆分 |
| 真实性红灯 | Current/Target、个人/团队、Demo/生产混淆 |
| Ownership 红灯 | 无法说明谁决定、谁实现、谁维护 |
| 竞争红灯 | 只说竞品不好，不说用户为什么选择自己 |
| 工程红灯 | 没有失败、权限、成本、评测和运维闭环 |

红灯不是自动否决项目；它决定下一轮应该补事实、缩范围、改架构还是做验证。
