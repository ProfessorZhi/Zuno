# Project Context Intake：项目事实采集

红队开始前必须先知道“被审计的项目是什么”。没有项目背景、用户、团队和当前状态，Agent 只能做通用架构题，不能判断方案是否过度、是否落地或是否值得做。

## 一、必须由用户提供或确认的最小事实

这些内容不能由 Agent 猜测。用户可以回答未知，但必须明确标为 `UNKNOWN`，Agent 再用场景假设做敏感性分析，不能把假设写成事实。

| 优先级 | 必填事实 | 为什么必须问 |
|---|---|---|
| P0 | 一句话项目背景：解决谁的什么问题 | 没有问题定义，无法判断架构是否必要 |
| P0 | 目标用户、当前用户或试用对象 | 判断产品价值、权限、数据和落地范围 |
| P0 | 当前使用规模：用户数、事项/文档量、并发或明确 UNKNOWN | 判断单体、队列、缓存、模型成本是否过度 |
| P0 | 团队人数、角色、每个人负责范围 | 判断模块数量、交付速度和 Ownership 是否可信 |
| P0 | 用户本人负责什么，哪些不是本人负责 | 防止项目叙事把团队工作变成个人经历 |
| P0 | 当前状态：原型、内部试用、试点、生产或未部署 | 区分 Current、Target 和未来计划 |
| P1 | 技术/部署约束：数据是否出域、模型、环境、合规 | 决定 SaaS、私有化、模型和 Tool 选择 |
| P1 | 开发周期和当前阶段 | 判断范围是否现实，识别是否过度设计 |
| P1 | 真实协作方式：需求、评审、开发、测试、发布由谁完成 | 补全开发过程和团队协作关系 |

## 二、建议用户一次这样回答

```text
项目一句话背景：
主要用户 / 试用对象：
当前用户数或 UNKNOWN：
文档 / 任务 / 并发规模或 UNKNOWN：
团队人数与角色：
我本人负责：
明确不是我负责：
当前落地状态：
开发周期 / 当前阶段：
关键技术或合规约束：
真实开发流程和协作方式：
```

如果用户只想快速开始，先回答前 7 项即可；后续问题由红队根据第一轮回答继续追。

## 三、Agent 可以补充什么

Agent 可以在事实台账基础上提出，但不得直接当作项目事实：

### 1. 产品叙事 Proposal

把背景整理成：用户 → 场景 → 原痛点 → 当前方案 → 结果 → 未解决问题。若没有真实用户或指标，写成验证假设和下一步实验。

### 2. 场景与落地 Proposal

提出 1–3 个最小可落地场景，例如“内部合同审查试点”“私有知识库问答”“受控报告生成”，并说明所需用户、数据、权限和验收指标。不能写成“已经被法院/企业使用”。

### 3. 架构 Proposal

根据用户数、并发、数据敏感度、团队人数和交付阶段，提出最小可交付架构、Target 演进路线和删减方案。逻辑模块多不等于部署服务多。

### 4. 团队协作 Proposal

Agent 可以提出角色级协作矩阵：产品/业务、Agent、Knowledge、后端/基础设施、前端、数据/评测、Security/部署；不能凭空分配真实姓名或声称某人已经完成某项工作。

### 5. 开发过程 Proposal

可以提出从需求澄清、Contract、最小闭环、测试/Eval、试点、反馈到发布的目标流程；必须和“实际已经这样开发过”分开记录。

### 6. 竞品与替代方案 Proposal

可以分析 WorkBuddy、通用 Chat/Agent、开源 RAG/Agent 框架和内部自研的适用边界；不能在没有用户访谈、基准或部署事实时声称“明显更强”。

## 四、事实台账格式

每个重要 Claim 维护一行：

| 字段 | 内容 |
|---|---|
| `claim_id` | 稳定 ID，例如 `CTX-001` |
| `claim` | 要写进项目叙事或架构的句子 |
| `status` | `FACT_USER / FACT_REPO / PROPOSAL_AGENT / DECISION_PENDING / GAP` |
| `source` | 用户回答、代码、测试、文档、Trace、Eval 或未知 |
| `owner` | 项目事实 Owner |
| `red_risk` | 红队可能如何攻击 |
| `target_destination` | 架构、模块、README、Status、Evidence、ADR 或暂不回写 |
| `decision` | 接受、拒绝、缩小范围、补证据或待确认 |

## 五、采集停止条件

当以下信息已有明确值或明确 `UNKNOWN`，才进入红队盘问：

```text
项目问题和用户
团队人数与个人 Ownership
当前状态与目标状态
规模（即使未知）
关键约束
```

如果这些还没有，继续扩写架构只是把未知包装成设计，应该停在 Fact Intake。
