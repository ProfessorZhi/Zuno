## Part A — Human Narrative

### 当机器结论开始被人采用，系统就要对结果负责

一项合同争议分析已经接近结束。检索系统找到了付款条款，模型判断付款已经逾期，并生成了一段事实摘要。专业人员复核后发现，模型把补充协议的签署时间写错了一天。他改正这个时间，接受其余判断，并准备把结果放进正式工作成果。

如果这只是一次临时问答，保存最终回答就够了。用户关闭页面以后，系统没有义务长期解释模型最初说过什么，也不需要维护一个几个月以后仍会被引用的业务版本。很多法律问答可以继续保持这种简单形态。

正式工作改变了这个前提。成果可能被交付给别人、进入后续流程、被另一位专业人员复核，也可能在新材料进入以后失去当前有效性。几周后再看，系统需要回答：当时依据的是合同 v2 还是 v3，机器提出了什么，专业人员改了什么，最终采用了哪些内容，引用落在哪一页，以及后来发生了什么使旧结论需要复核。

02 的职责从这里出现。它保存法律业务愿意长期承认并承担后续责任的记录，而不是复制模型运行历史。检索、模型和专业算法先产生可重算的候选；材料版本、专业规则、必要人审和当前安全条件满足以后，需要长期存在的内容才进入正式业务状态。

工程实现把这个提交边界称为 `Formal Admission`。进入以后，正式 Evidence、Finding、HumanDecision 和 WorkProduct 拥有自己的版本、来源和后续有效性关系。名称只是对已经发生的业务变化做压缩：机器完成了一次计算，和法律业务决定长期采用某个结果，是两个不同时间点。

### 一次成功提交必须在调用方崩溃后仍然能够被证明

最危险的故障窗口并不是数据库事务回滚，而是数据库已经成功，调用方还没来得及记录这次成功。

假设 Runtime 把一份已经复核的结论交给 02。业务事务完成，新的正式工作成果已经写入；Runtime 正准备保存下一份 Checkpoint，进程在这几毫秒里崩溃。新的 Worker 接管以后只能看到旧 Checkpoint，于是很容易得出错误结论：正式提交还没有发生，应该再做一次。

如果 02 的成功只存在于已经丢失的 `200 OK` 响应里，恢复过程没有可靠办法区分“事务没发生”和“事务已经发生但响应方失忆”。Target 因而让正式提交在同一业务事务里留下可再次查询的完成证明，工程上称为 `AdmissionReceipt`，并把它与对应的 `DomainVersion` 和提交因果绑定起来。

重启以后，Runtime 先查询正式业务记录。匹配的提交已经存在，就修复自己的控制进度，不重复写业务事实；只有正式提交确实不存在时，才根据当前材料、当前版本和当前安全条件重新进入提交路径。Checkpoint 继续证明 Controller 上次记录到了哪里，Domain 的耐久记录证明法律业务世界是否已经改变。

同样的版本约束也保护并发修改。两个人都基于业务版本 V10 工作，一个先加入新 Evidence，另一个随后提交基于旧材料形成的 Finding。后一次提交如果完全不知道世界已经变成 V11，就可能把旧前提下的判断写进新事实集合。提交因此要声明自己基于哪个业务版本；版本已经变化时，调用方重新读取、合并或重新判断。

这里的冲突不是数据库实现细节。它表示专业判断所依赖的业务前提已经变化。DomainVersion 的价值就在于把这种变化从隐含时间差变成可检查的业务因果。

### 新证据改变当前结论，但不能改写上午发生过的历史

下午又上传了一份关键补充协议，它改变了付款日期的认定。上午形成的 WorkProduct V3 此时出现了两个同时成立的事实：V3 上午确实作为正式成果存在过；V3 现在已经不适合继续作为当前结论使用。

直接修改 V3，或者删除以后重新生成一个“看起来一直如此”的 V4，会破坏已经发生的时间线。已经交付的文档、审计记录和人工决定都会开始引用一个从未真实存在过的过去。02 因而保留 V3 当时为什么成立，再记录它因为哪条新事实进入复核、失效或被后续版本取代。当前视图可以指向 V4，历史查询仍然能够还原 V3。

引用也遵循相同原则。Retriever 今天重新运行，可能因为 OCR、chunk、Embedding、reranker 或索引版本变化找到另一段文字。历史工作成果需要回到提交当时真正采用的材料版本和稳定位置。Knowledge 可以保存这次检索为什么找到某个候选，Domain 在正式采用时则保存这份工作成果实际依赖的引用。工程参考分别把它们称为 `CitationLineage` 和 `WorkProductCitationBinding`。

新 Evidence 也不意味着全案必须无条件重算。只要正式结果保留了足以解释关键依赖的关系，系统可以判断哪些 Finding 和 WorkProduct 可能受影响，只重新检查相关路径。模型 token、Reflection 中间稿、一次临时 rerank 分数没有独立长期业务生命周期，就继续留在 Runtime、Capability、Model 或 Observability，而不是为了“完整”全部塞进 Domain。

### 专业判断和安全审批可以出现在同一页面，但改变的是不同事实

专业人员点击“接受这项 Finding”，表达的是法律业务判断。管理员批准“把这份成果发送到外围法院系统”，表达的是另一类决定：当前受保护动作是否被允许。两种按钮可能紧挨着，系统仍需要保留它们各自的责任。

专业人员的接受、修改、拒绝或要求补证形成业务上的 `HumanDecision`，并跟随被判断的对象和版本。外发、敏感读取或高风险动作所需的 `ApprovalDecision` 由 Security & Governance 管理。专家认可一份结论不会自动获得外发权限；安全管理员批准一次发送，也不会把尚未复核的模型文本变成正式法律事实。

业务记录本身也可能需要更正。材料元数据录错、人工决定需要修正、正式成果发现引用绑定错误时，直接覆盖旧行虽然简单，却会让曾经发生的业务行为消失。更正应保留原记录和原因，再形成新版本、取代关系或受治理的修正记录。

冲突材料同样可以同时存在。两份证言可能都经过正式接纳，却互相矛盾。Domain 保存它们各自的来源和业务身份，后续 Finding 与 HumanDecision 再解释专业人员如何处理冲突。正式接纳表示系统愿意长期负责“这条记录存在、来自哪里、当时为何被采用”，并不宣称现实世界已经没有不确定性。

### 只有需要长期业务语义时，完整 Domain Kernel 才值得存在

如果产品只做一次性问答，没有长期 WorkProduct、正式材料版本、人工专业决定和失效传播，一个轻量 answer record 已经足够。为了追求 DDD 形式完整而提前建立大量领域对象，只会增加 Migration、事务、版本和维护成本。

即使业务进入长期状态，一级对象也应该克制。一个对象值得进入 Canonical Domain，通常是因为它有独立生命周期，会被长期引用，需要人工操作，或者拥有必须被保护的版本与有效性语义。某个 Capability 的中间 JSON、一次 Eval 标签、Runtime 的临时 Step 结果或 UI projection 没有这些条件，就不应该升级成正式领域事实。

完整 Domain Kernel 的成本是真实的：正式提交事务、版本冲突、历史保留、引用稳定和失效传播都需要实现与测试。只有结果真的要跨运行、跨人员和跨时间继续存在，这些机制才开始回报它们的复杂度。

### Current / Target / Gap

**Target：** 02 拥有正式法律业务状态、DomainVersion、Formal Admission、AdmissionReceipt、WorkProduct 历史引用和正式失效关系；机器候选、Runtime 控制状态、知识派生和外部 Effect 仍由各自 Owner 管理。

**Current：** 文档中的七对象 Kernel、完整 Admission transaction、版本冲突处理和失效传播属于 Target 设计，不能因为文档完整就视为已经实现。现有代码、Migration 和测试能证明到哪里，只以 `docs/evidence/` 和代码证据为准。

**Gap：** 字段级冻结、真实并发冲突、Domain commit / Checkpoint crash-window 故障注入、Migration 方案、跨对象失效传播和真实法院工作流成本仍需要独立验证。
