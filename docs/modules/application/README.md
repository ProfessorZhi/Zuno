## Part A — Human Narrative

### 同一个“完成”，在用户、Runtime 和外部系统眼里并不是一回事

设想法院已有业务系统向 Zuno 提交一项合同争议分析。接口很快返回了受理结果，后台开始检查材料、检索证据并运行分析。十几分钟后 Runtime 已经结束，页面也拿到了一个答案；但专业人员还没有把其中的结论接纳为正式 WorkProduct。再过一会儿，正式成果形成并被推送给外围系统，下午又补入一份关键证据，02 随即判断这份成果需要复核，而外围系统此时恰好离线。

如果入口层只维护一个 `status=success`，这条时间线会迅速变得无法解释。它究竟表示请求已经受理，后台计算已经结束，正式业务结果已经成立，结果当前允许发布，还是外围消费者已经收到？这些状态发生在不同系统里，生命周期也不一样。

Application & Integration 存在于这里。它面对 Web、法院 Host、批处理任务、Generic Agent Host 和 API Client，把内部多个责任域已经成立的事实组合成稳定的产品行为，让调用方知道“我提交了什么、现在处于什么产品阶段、能看到什么、还能不能继续使用、交付到了哪里”。它不重新裁决 Knowledge、Domain、Security 或现实 Effect。

对同步问答，事情远没有这么复杂。用户问“合同第 8 条约定了什么”，访问范围清楚、材料已经就绪，也不需要长期保存正式成果时，一个普通应用服务完全可以调用检索和模型后直接返回答案。Zuno 不应该因为存在九个责任域，就强迫这类请求先经过完整长任务 Runtime。简单路径应该保持简单。

### 入口先稳定用户真正提交的任务

复杂请求常从一句“帮我分析这个案件”开始。对人来说这句话足够自然，对长期运行系统却缺少几个决定后续行为的条件：分析哪个 Matter，使用哪些材料，期望得到普通回答还是正式成果，谁在请求，以及这次调用属于哪个逻辑请求。

入口层需要把这些外部表达整理成稳定的任务上下文。这里的工作不是提前替下游做判断，而是让后面的判断有明确对象。用户后来把 Scope 从合同扩展到“合同加全部聊天记录”，Knowledge 的就绪条件会变化，Security 的可访问范围也需要重新计算；如果入口只是改一个 UI filter，却继续沿用旧任务前提，后面的每个模块都会在不同世界里工作。

外部 Host 传来的 user id、tenant、role 或 matter id 也只能先被视为 assertion。Application Adapter 可以完成认证协议、字段映射和 Host 兼容，但“这个主体现在能不能读材料或执行动作”仍由 08 根据可信身份和当前策略决定。把认证接入和授权结论分开以后，Web 请求、后台恢复和异步 Host 调用才不会各自长出一套权限语义。

客户端本身也会制造重复。浏览器可能在响应丢失后重新提交，API Gateway 可能超时，移动网络也可能让同一个请求到达两次。入口如果每次都新建 Run，用户的一次动作会被放大成多个后台任务，后续甚至可能形成重复正式交付。Target 因而给逻辑调用稳定身份：相同调用身份和相同规范化输入可以重新找到既有 invocation；同一个身份却带着不同任务内容时，需要显式暴露冲突，而不是悄悄把两个请求当成一件事。

这一步完成以后，Application 才决定请求应该走哪条产品路径。简单问答可以短路到受控 RAG；需要等待、并行、人工或长期恢复的工作交给 04；需要形成正式法律成果的结果最终进入 02。工程参考把这种产品级路由决定称为 `InvocationDecision`，它只负责选择产品流程，不获得下游事实的所有权。

### 长任务结束以后，Application 只组合已经成立的事实

后台运行结束时，入口层最容易做的一件错事，是把 Runtime 的 completed 直接映射成“分析完成”。对用户来说这句话通常意味着结果已经可以使用，但 Runtime 只能证明自己的计划与步骤结束了。

如果这次任务只产生普通答案，01 还需要确认当前材料范围、引用和发布条件仍然成立；如果任务目标是正式 WorkProduct，则必须等 02 的正式提交已经成立。一个模型成功返回、一条 Run 结束、一个正式结果被 Domain 接纳、一个页面允许展示，是一条链上的不同观察点。01 的角色是把这些观察点翻译成产品语义，而不是为了 API 简洁把它们压成一个布尔值。

工程参考把这四个完成层次压缩成一条精确边界：Run completed != Domain admitted != Answer publishable != Consumer displayed。它是前面产品生命周期的记号，不是另起一套状态真相。

这种边界也决定了产品版本和运行计划版本为什么不能混在一起。一个 Agent 产品可能升级默认 Prompt、可用能力或路由策略，新请求从此使用新的产品版本；已经运行中的任务仍然按照自己绑定的 PlanVersion 解释。入口可以知道“用户调用的是哪一版产品能力”，04 继续拥有“这次 Run 当前按哪一版计划执行”。产品发布不应该在后台把已经派发的计划原地改写。

用户点击取消也遵循同样原则。01 可以接受取消请求并要求 04 停止未来还可以安全停止的工作，也可以阻止尚未开始的交付；已经提交的正式 Domain 事实、已经发生的模型 Usage、已经确认的现实 Effect 不会因为页面显示 CANCELLED 就消失。如果业务需要撤销外部动作，应当形成新的受控动作，而不是让入口层修改旧历史。

### 正式成果离开 Zuno 后，业务有效性和网络送达继续分开

上午形成的 WorkProduct V5 已经交付给外围法院系统。下午补入新证据后，02 判断 V5 需要复核。这个失效事实应该立刻在 Zuno 内成立，即使外围系统此时离线。

01 负责把这种业务变化传播给消费者。Push 通知可以降低传播延迟，但消费者可能收不到；所以正式成果还需要提供当前有效性的 Pull 查询，让外部系统在真正使用结果时能够确认它是否仍然 current。Push 和 Pull 都是在传递 Domain 已经成立的状态，不会因为网络失败把 V5 从 stale 重新变回有效。

交付本身也需要稳定身份。同一份 WorkProduct 可能发给两个不同目标，同一个目标也可能因为网络错误产生多次发送尝试。产品层要能说明“我们准备向哪个消费者交付哪一版成果、使用哪一版对外 Contract”，这构成 Delivery 的长期产品语义。

真正改变外围系统状态以后，问题进入 06 的范围。假设 Zuno 请求远端创建一条记录，连接在响应返回前断开，01 不能根据自己的 HTTP 异常宣布交付失败并自动重发。远端可能已经创建成功。06 会确认现实动作究竟发生了什么，01 再用这个 Effect truth 更新 Delivery observation。这样“产品应该交付什么”和“现实世界实际上发生了什么”不会被同一个 retry loop 混在一起。

远端返回 acknowledgement 也有边界。它可以证明 Zuno 观察到对方接受了某次消息或调用，却通常不能证明对方内部最终采纳了这份结果，更不能证明某个远端 UI 已经展示。Integration 只保存自己真实知道的 observation 和 correlation，不替一个不受 Zuno 控制的系统声明内部业务真相。

### 多 Host 只增加适配成本，不应该复制业务语义

Web 可以同步等待几秒，法院 Host 可能异步提交后轮询状态，批处理可能只关心最终 artefact。REST、消息队列和 Host SDK 的传输形态不同，但 READY、PARTIAL、Draft、Formal、Stale、Cancelled 这些产品含义不应该因此出现三套解释。

Adapter 负责协议转换、字段兼容和版本协商，产品状态仍然来自同一组 Owner facts。Runtime queue 或模型配额过载时，01 还应把 queued、deferred、rate-limited 之类真实背压暴露给调用方，而不是无限受理后让所有请求一起超时。外部 Contract 的价值在于让消费者可以稳定理解系统行为，不在于把内部每个状态机原样透传出去。

如果 Zuno 只作为一个单体应用内部库使用，没有多 Host、长任务、异步交付和失效传播，01 可以缩回非常薄的 application layer。即使需要这些能力，它也默认只是逻辑责任，不要求独立部署成 Integration Service。只有协议隔离、吞吐、网络边界或独立生命周期形成真实需求以后，Adapter、Outbox、Queue 或单独服务才值得增加。

### Current / Target / Gap

**Target：** 01 负责组合其他 Owner 已经成立的事实，形成稳定的请求受理、产品路径、普通答案发布、正式成果发布、Delivery、失效传播和外部 Contract 语义；Knowledge readiness、正式 Domain 状态、Authorization 和现实 Effect 仍由各自责任域决定。

**Current：** 上述多 Host 生命周期、完整 Invocation / Delivery identity、Push + Pull 失效传播和复杂交付恢复属于 Target 设计。现有 Application、API、Host 集成或运行代码实际实现到哪一步，只以 `docs/evidence/`、代码和测试证据为准。

**Gap：** 仍需要真实 Host Contract、重复请求与断线重试测试、正式成果失效传播演练、外部交付边界、背压行为以及是否值得独立部署的容量证据。没有这些证据时，不把 Target 写成已验证产品能力。
