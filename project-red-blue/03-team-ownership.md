# 团队与 Ownership

## 现实分工和目标分工必须分开

面试中最危险的说法之一是把目标架构的模块表当成历史团队结构。红蓝队必须同时维护两张表：

- **Reality Ownership**：真实发生过的决策、实现、评审、部署和故障责任；只能由用户或证据确认。
- **Target Ownership**：为了让未来架构可维护而提出的模块 Owner、接口 Owner 和运行责任；属于 `[BLUE_PROPOSAL]` 或 `[TARGET_ACCEPTED]`。

## 现实分工表

| 责任 | 真实负责人 | 证据 | 状态 |
|---|---|---|---|
| 产品和范围决策 | 待用户填写 | 会议、任务、提交 | `[UNKNOWN]` |
| Agent / Workflow | 待用户填写 | 代码、提交、评审 | `[UNKNOWN]` |
| Knowledge / Retrieval | 待用户填写 | 代码、实验、指标 | `[UNKNOWN]` |
| 前后端和 API | 待用户填写 | 代码、部署 | `[UNKNOWN]` |
| 基础设施、发布和故障 | 待用户填写 | 发布记录、告警 | `[UNKNOWN]` |
| 本人实际贡献 | 待用户填写 | 具体提交和产物 | `[UNKNOWN]` |

## 假设团队的候选模型

下表只是假设，不是 Zuno 历史。比如一个六人团队可以是“2 后端、2 Agent/AI、1 前端、1 模型/基础设施”，也可以采用“全栈小队 + 平台支持”的分法。红队必须继续问：谁在当时真正做了什么，而不是接受岗位名称作为证据。

| 候选 | 适用假设 | 主要风险 |
|---|---|---|
| A：按技术域分工 | 人员稳定、模块边界较清晰 | 小团队容易产生单点 Owner 和交接成本 |
| B：按业务纵切分工 | 需要快速交付一个完整场景 | 横向基础能力可能重复建设 |

## 目标 Ownership 的检查项

对任何声称“我负责”的内容，红队要继续问：

1. 谁决定需求和范围？
2. 谁设计接口和数据模型？
3. 谁写了关键路径？
4. 谁评审和验证？
5. 谁发布和处理故障？
6. 个人贡献与团队成果如何区分？
7. 如果 Owner 离开，谁能维护？

目标架构中的模块 Owner 不能自动代表现实团队分工；如果二者不一致，应进入 `08-gap-register.md`。
