# Zuno Project Red-Blue Lab

## 这是什么

`project-red-blue/` 是 Zuno 的项目级红蓝对抗实验区。它不是新的架构事实源，也不是把面试题堆在一起的题库，而是用来攻击并修复项目叙事、落地可信度、团队协作、技术取舍和架构边界的工作流。

- **红队（Red Team）**：像大厂面试官、架构评审人、开源方案质疑者、投资人或业务负责人一样，从最新陈述出发连续追问。
- **蓝队（Blue Team）**：基于事实回应；事实不足时请求用户补充；对目标态、方案和修复路径给出明确标注的提案。
- **裁判（Referee）**：区分已确认事实、仓库证据、目标设计、蓝队提案和未知状态，决定是否需要同步到正式文档。

红蓝队的目标不是证明 Zuno “什么都有”，而是找出以下问题：

1. 项目为什么存在，真实用户和痛点是什么；
2. 当前团队是否真的能维护所声称的复杂度；
3. 逻辑模块、部署服务、团队职责和个人贡献是否被混为一谈；
4. 每个技术选择是否有替代方案、成本边界和失败处理；
5. 哪些内容是 Current，哪些只是 Target、Proposal 或 Unknown。

## 来源和标签

正式架构事实仍以 `docs/` 为准，项目红蓝材料不覆盖它们。所有陈述必须带来源标签：

| 标签 | 含义 |
|---|---|
| `[USER_CONFIRMED]` | 用户明确提供或确认的真实事实 |
| `[REPO_EVIDENCE]` | 能在仓库代码、测试、文档或证据中复核的事实 |
| `[TARGET_ACCEPTED]` | 已确认的目标架构或目标规则 |
| `[BLUE_PROPOSAL]` | Agent 提出的方案、叙事或假设，尚未当作历史事实 |
| `[UNKNOWN]` | 当前不能从证据推出，必须保留未知 |

Agent 不得把团队规模、用户数量、上线情况、个人贡献、客户和指标补写成历史。不能推断的内容必须进入 `01-project-facts.md` 的 `UNKNOWN`，再向用户提问。

## 工作闭环

```text
事实采集
  ↓
项目模型
  ↓
Claim Inventory
  ↓
红队攻击
  ↓
蓝队回应 / 提案
  ↓
裁判判定
  ↓
同步到唯一正式事实源
  ↓
再次攻击验证
```

红队会话默认只读，不修改事实、架构、简历、代码或测试。蓝队修复只有在用户确认事实或方案后，才进入正式文档和验证流程。

## 第一次运行

先填写 `01-project-facts.md` 中的 P0 事实，再让红队从 Claim Inventory 中逐条攻击。第一次只需提供真实信息，不需要用户自己设计架构：

```text
项目来源：
目标用户：
核心问题：
当前状态：
用户规模或 UNKNOWN：
团队人数与角色：
我负责 / 没负责：
约束：
真实证据：
保密边界：
```
