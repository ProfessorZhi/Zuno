# 蓝队修复协议

蓝队不是替红队把故事说圆，而是把攻击结果变成可验证的事实、范围收缩、方案比较或正式修复。

当用户忘记项目细节时，蓝队可以承担“背景重建助手”角色：从用户记得的关键词、已有仓库材料和可核验外部线索生成多个候选解释、规模区间和面试回答骨架；每个候选必须标 `[BLUE_PROPOSAL]`，列出支持证据、反证和核验动作。用户确认前，不得写入历史、简历或 Current 状态。

## 五类回应

| 回应 | 适用情况 | 结果 |
|---|---|---|
| `ACCEPT_FACT` | 用户确认且有证据 | 进入事实或证据记录 |
| `REJECT_PREMISE` | 红队前提不成立 | 说明反例和证据，不回避后续问题 |
| `SCOPE_DOWN` | 目标过大或复杂度不匹配 | 缩小用户、场景、模块或承诺 |
| `PROPOSE_DESIGN` | 需要新的目标方案 | 标为 `[BLUE_PROPOSAL]`，等待用户确认 |
| `REQUEST_EVIDENCE` | 事实或效果无法证明 | 建立证据任务，不用推测替代 |

## 修复流程

```text
复述红队风险
  ↓
判断是事实 / Target / Proposal / Unknown
  ↓
归类 Gap
  ↓
提出 1–3 个候选修复
  ↓
用户确认现实事实或接受目标方案
  ↓
形成最小修改计划
  ↓
同步到唯一正式事实源
  ↓
运行验证
  ↓
重新红队攻击
```

蓝队不能用目标 Ownership 冒充历史分工；不能把未来指标写成 Current；不能因面试叙事好听而增加没有落地依据的用户、团队或客户。

## 团队协作模型

可提出“产品/范围、领域能力、平台工程、前端交付、质量与发布”等角色接口，但必须标明这是 `[BLUE_PROPOSAL]`。只有用户确认现实团队结构后，才可写入项目事实。目标团队模型需要写清：决策人、实现人、评审人、发布人、事故响应人和替补关系。

## 事实同步路由

| 内容 | 正式去向 |
|---|---|
| 产品定位、范围和工作流 | 总架构 Part A / `01 Product` |
| Owner、Contract、Failure | 对应模块文档 / ADR |
| 技术取舍 | `docs/decisions/` / ADR |
| 用户、规模、质量和上线状态 | `docs/status/` / `docs/evidence/` |
| 面试叙事和攻击摘要 | `project-red-blue/` / `docs/verification/interview-qa/` |
| 团队治理和交付过程 | `docs/governance/` 或项目材料 |

架构含义变化时，按 `AGENTS.md` 更新架构 Markdown、图源和验证器；本目录本身不能成为第二份架构真相。

## 背景假设到架构差异化

如果用户确认场景确实涉及学校与法院内部协作，蓝队可以提出“内部法律工作平台”的目标设计：小范围私有部署、法院/研究团队分层权限、案件或事项隔离、原文证据与引用、人工复核、操作审计和可撤销外部工具。它们是从风险约束推导出的目标能力，不是对历史实现的描述。

红队随后必须反问：这些约束是否真实存在？一个成熟通用平台加权限配置是否已经足够？如果足够，就优先 `ADOPT` 或 `EXTEND`，不要把目标架构复杂度当作差异化本身。
