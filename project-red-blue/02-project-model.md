# 项目模型

红蓝队先建立项目模型，再决定从哪个角度攻击。模型中的每一层都要区分现实事实、仓库证据、目标设计、蓝队提案和未知状态。

## 十层项目模型

| 层 | 要回答的问题 |
|---|---|
| 背景 | 为什么出现这个项目，原始约束是什么？ |
| 用户 | 谁使用、谁受益、谁承担风险和成本？ |
| 问题 | 当前工作流哪里慢、错、贵或不可追溯？ |
| 范围 | 第一阶段做什么，明确不做什么？ |
| 团队 | 谁决定、实现、评审、部署和处理故障？ |
| 架构 | 当前系统如何运行，目标设计解决什么缺口？ |
| 取舍 | 哪些能力采用、复用、扩展、自建或延期？ |
| 交付 | 从最小版本到当前状态经历了哪些可证明阶段？ |
| 落地 | 谁在什么场景下使用，失败后如何回到人工流程？ |
| 证据 | 哪些数据、测试、Trace、反馈或提交支持结论？ |

对每一层至少追问：事实是什么、为什么重要、谁拥有、当前如何工作、失败怎么办、如何证明。

## 最小落地场景

第一次建模不从“平台支持多少能力”开始，而从一个可观察工作流开始：

```text
真实用户与任务
  ↓
当前人工流程与痛点
  ↓
最小 AI 辅助步骤
  ↓
用户确认或拒绝
  ↓
产出进入业务流程
  ↓
质量、延迟、成本和人工节省可测量
```

如果用户尚未确认真实场景，Agent 只能提出 1–3 个 `[BLUE_PROPOSAL]` 候选，不得选择其中一个当作项目历史。

## 学校与法院合作线索的安全推理

当面试准备中出现学校、教师、法院或研究团队名称，但用户忘记了具体背景，蓝队可以帮助恢复“可能的项目故事”，但必须把推理和事实分开。合理候选包括：

- 面向法院内部的法律文书、案例或法规检索与研究辅助；
- 学校与法院联合的司法研究、案例分析或教学实验平台；
- 面向内部工作人员的文档问答、相似案例发现、摘要和证据引用；
- 先由研究团队或法院小范围试用，再决定是否扩展到更多人员。

这些候选解释的共同优点是能解释“为什么需要权限隔离、原文证据、审计和私有部署”，但不能证明它们就是 Zuno 的真实背景。红队要继续问：合作是研究、试点、采购还是仅仅讨论？系统处理什么数据？谁实际登录？谁能确认结果？

同理，不能因为合作对象是法院就推断“全市法院使用”或给出精确用户数。蓝队只能提出内部试点的区间假设，并把核验动作指向原始面试记录、邮件、会议材料、部署记录或用户反馈。

## WorkBuddy 差异化的候选模型

“WorkBuddy 已经存在”不是自动否定 Zuno 的理由。蓝队可以提出待验证的差异化假设：Zuno 面向法律/司法内部高敏感数据，强调私有边界、事项和文档版本、条款/案例级证据、可审计的权限与人工复核，以及从检索到正式工作成果的闭环；WorkBuddy 的通用办公能力可以作为被复用或比较的基线。真正的差异化必须落到一个具体用户任务、一个不可接受的风险和一条可测量的结果上。

如果这些约束并不存在，红队应建议直接采用现成平台或把 Zuno 范围收缩，而不是为了“差异化”保留更多模块。

## Agent 可以补充什么

Agent 可以提出：

- 项目定位和目标用户假设；
- MVP 场景和人工兜底流程；
- 逻辑模块如何映射到少量物理服务；
- 团队角色和协作接口的候选模型；
- Build / Buy / Extend / Defer 对比；
- 交付、评测、上线和迭代路径；
- 竞争方案的待验证差异化假设。

每个提案必须同时写明：假设、解决的问题、代价、验证方式、如果不成立如何收缩。
