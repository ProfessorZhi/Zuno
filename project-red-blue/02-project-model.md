# 项目模型

红蓝队先建立项目模型，再决定从哪个角度攻击。模型中的每一层都要区分现实事实、仓库证据、目标设计、蓝队提案和未知状态。

## 十层项目模型

| 层 | 要回答的问题 |
|---|---|
| 背景 | 为什么出现这个项目，原始约束是什么？ |
| 用户 | 谁使用、谁受益、谁承担风险和成本？ |
| 问题 | 当前工作流哪里慢、错、贵或不可追溯？ |
| 范围 | 第一阶段做什么，明确不做什么？ |
| 团队 | 谁决定、实现、评审、部署和处理故障？ |
| 架构 | 当前系统如何运行，目标设计解决什么缺口？ |
| 取舍 | 哪些能力采用、复用、扩展、自建或延期？ |
| 交付 | 从最小版本到当前状态经历了哪些可证明阶段？ |
| 落地 | 谁在什么场景下使用，失败后如何回到人工流程？ |
| 证据 | 哪些数据、测试、Trace、反馈或提交支持结论？ |

对每一层至少追问：事实是什么、为什么重要、谁拥有、当前如何工作、失败怎么办、如何证明。

## 跨层 Alignment Gate

项目模型不是十张互不相关的表。红队必须检查相邻层和远距离层是否属于同一条因果链。

### G1 背景 ↔ 用户 ↔ 问题

如果项目背景说“法院内部知识工作”，用户和问题不能突然变成没有来源的企业 SaaS 采购流程。允许 Target 扩展到新领域，但必须明确“真实背景”和“目标领域 Profile”之间的关系。

### G2 用户规模 ↔ 架构复杂度

几百潜在内部用户不自动需要十几个独立服务、复杂分布式锁或大规模集群。逻辑模块可以很多，但物理部署、缓存、队列、分片和多活必须由吞吐、故障隔离、数据敏感度或团队边界驱动。

### G3 团队能力 ↔ 交付范围

六人团队可以设计 11 个逻辑模块，不代表六个人同时实现 11 个生产级子系统。必须能解释 MVP 留什么、哪些复用、哪些延期、哪些只是 Target Ownership。

### G4 业务工作流 ↔ 领域对象

领域对象必须来自业务动作和事实所有权，而不是为了架构完整创造名词。例如如果真实旗舰场景偏司法知识和证据辅助，Contract / Redline 不能成为唯一上位模型；如果合同审查只是 Target Domain Profile，应明确抽象层与 Profile 层。

### G5 竞品能力 ↔ Zuno Delta

WorkBuddy、Dify、OpenViking、Graphiti、GraphRAG 等已经覆盖的通用能力，不能再次用“我们也有 Agent / Memory / RAG”作为差异化。必须指出：哪些可以替换，哪些 Contract 必须由 Zuno 自己拥有，以及如果竞品补齐后 Zuno 是否还能成立。

### G6 Target ↔ Current ↔ Resume

Target Architecture 不能直接支持“我已经做了”的简历 Claim。每个个人贡献都必须能路由到代码、测试、提交、运行证据或明确的设计产物；否则降为 Target / Participation / Unknown。

任一 Gate 断裂都应进入 `PROJECT_ARCHITECTURE_ALIGNMENT_GAP`、`OVERENGINEERING_GAP`、`PRODUCT_POSITIONING_GAP` 或 `RESUME_CLAIM_RISK`，而不是靠更长的项目介绍掩盖。

## 最小落地场景

第一次建模不从“平台支持多少能力”开始，而从一个可观察工作流开始：

```text
真实用户与任务
  ↓
当前人工流程与痛点
  ↓
最小 AI 辅助步骤
  ↓
用户确认或拒绝
  ↓
产出进入业务流程
  ↓
质量、延迟、成本和人工节省可测量
```

如果用户尚未确认真实场景，Agent 只能提出 1–3 个 `[BLUE_PROPOSAL]` 候选，不得选择其中一个当作项目历史。

## 学校与法院合作线索的安全推理

当面试准备中出现学校、教师、法院或研究团队名称，但用户忘记了具体背景，蓝队可以帮助恢复“可能的项目故事”，但必须把推理和事实分开。合理候选包括：

- 面向法院内部的法律文书、案例或法规检索与研究辅助；
- 学校与法院联合的司法研究、案例分析或教学实验平台；
- 面向内部工作人员的文档问答、相似案例发现、摘要和证据引用；
- 先由研究团队或法院小范围试用，再决定是否扩展到更多人员。

这些候选解释的共同优点是能解释“为什么需要权限隔离、原文证据、审计和私有部署”，但不能证明它们就是 Zuno 的真实背景。红队要继续问：合作是研究、试点、采购还是仅仅讨论？系统处理什么数据？谁实际登录？谁能确认结果？

同理，不能因为合作对象是法院就推断“全市法院使用”或给出精确用户数。蓝队只能提出内部试点的区间假设，并把核验动作指向原始面试记录、邮件、会议材料、部署记录或用户反馈。

## Replaceable Infrastructure 与 Domain Control Plane

蓝队不得把“我们自己实现”当作价值。每个重要能力先判断它属于哪一类：

```text
Replaceable Infrastructure
    Graph Runtime、Model Provider、Vector / Search Backend、Memory Backend、Tool Adapter、通用 Agent UI 等。
    只要 Contract、部署、安全和迁移要求满足，就应该允许 Adopt / Extend / Replace。

Domain Control Plane
    只有那些直接承载业务事实、证据、版本、权限、人工决策、审计和恢复责任的领域语义，才有资格成为 Zuno 必须拥有的核心。
```

即使某个能力当前由 Zuno 实现，也必须回答“如果明天换成成熟开源/商业底座，哪些领域事实仍然不会丢”。答不出来时，红队应怀疑该能力只是可替换基础设施，不是产品差异化。

## WorkBuddy 差异化的候选模型

“WorkBuddy 已经存在”不是自动否定 Zuno 的理由，但“Zuno 也支持 Agent、MCP、Skill、文件和多步骤执行”同样不是差异化。蓝队只能提出待验证的差异化假设：Zuno 面向法律/司法内部高敏感数据，强调事项与文档版本、可追溯证据、人工决定、权限与审计，以及从检索到正式工作成果的领域闭环；通用平台可以作为 UI、Agent Runtime 或工具入口被复用。

真正的差异化必须落到：

```text
一个具体用户任务
+ 一个通用平台无法安全承担或无法表达的领域事实/责任
+ 一个可以验证的结果或风险下降
```

如果这些约束并不存在，红队应建议直接采用现成平台、把 Zuno 作为领域 Extension，或者缩小项目范围，而不是为了“差异化”保留更多模块。

## Agent 可以补充什么

Agent 可以提出：

- 项目定位和目标用户假设；
- MVP 场景和人工兜底流程；
- 法院 / 企业合同等不同领域 Profile 与通用法律工作抽象的候选关系；
- 逻辑模块如何映射到少量物理服务；
- 团队角色和协作接口的候选模型；
- Build / Buy / Extend / Defer 对比；
- 交付、评测、上线和迭代路径；
- 竞争方案的待验证差异化假设。

每个提案必须同时写明：假设、解决的问题、代价、验证方式、如果不成立如何收缩。
